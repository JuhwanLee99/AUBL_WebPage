# 실시간 기록용 IndexedDB 영속 입력 큐 기반

작성일: 2026-09-08

## 구현 범위

`src/shared/lib/durableScoringQueue.ts`에 브라우저 영속 큐를 추가했다. 실제 모달 Provider나 전송 API에는 아직 연결하지 않았고 운영 writer도 교체하지 않았다.

큐는 환경·프로젝트·UID·경기·testRunId·작성 세션·epoch별로 분리한다. IndexedDB의 streams와 inputs 두 저장소를 사용하여 메타데이터와 입력을 같은 트랜잭션으로 반영한다. 개별 입력을 별도 레코드로 저장하며 전체 대기열을 단일 JSON으로 계속 덮어쓰지 않는다.

## 접수·전송·ACK

- `enqueue`는 사건 및 복구용 상태를 포함한 직렬화 스냅샷에 순번을 부여한다. 영속 트랜잭션 완료 후에만 성공을 반환한다.
- 요청 하나가 전송 중이어도 다음 입력을 별도 순번으로 계속 접수할 수 있다. 전송 대기 입력은 여러 건이며 네트워크 요청은 경기별로 하나씩 순차 처리하는 계약이다.
- `freeze`는 입력 범위·기반 revision·요청 ID·payload·해시를 복제해 고정한다. 이미 고정된 요청을 최신 화면 상태로 교체하지 않는다.
- `acknowledge`는 해당 고정 요청의 ID·입력 범위·해시·다음 revision을 모두 대조한다. 일치한 입력만 제거하고 나머지는 유지한다.
- 입력 제거와 ACK·revision 기록, pending 해제는 같은 영속 트랜잭션이다. 실패하면 완료 표시나 입력 삭제만 따로 반영하지 않는다.
- ACK의 원래 확정 revision보다 서버 head가 앞서 있으면 원래 범위만 완료하고 나머지 큐는 충돌 상태로 보존한다.
- `block`은 입력·pending을 삭제하지 않고 신규 접수·요청 고정을 막는다. 자동 unblock이나 다른 계정으로 재전송은 없다.
- `recover`는 같은 스냅샷에서 메타데이터와 해당 범위의 대기 입력을 순서대로 반환한다.

## 책임과 제한

스냅샷의 사건 스키마·복구 상태와 요청 payload의 canonical hash는 후속 adapter가 생성·검증해야 한다. 현재 큐는 임의 내용을 야구 규칙에 맞는 사건으로 승인하지 않는다. `inputId`는 메타데이터이며 같은 ID의 중복 접수를 자동 병합하지 않는다. 실제 모달에서는 접수 중 중복 클릭을 막고 사용자 입력 재시도의 식별 계약을 연결해야 한다.

ACK 자체의 인증·서버 범위·세션 확인은 transport adapter의 책임이다. 큐는 자신에게 고정된 요청과 ACK의 바인딩을 대조하지만 임의 객체를 진짜 서버 응답으로 인증하지 않는다. 완료한 ACK를 다시 호출하면 pending 불일치로 거부하므로 transport는 복구된 lastAck와 중복 콜백을 구분해야 한다.

브라우저 영속 저장 실패 시 메모리 또는 localStorage로 성공 처리하지 않는다. 저장소 삭제·기기 분실까지 복구할 수 있다는 보장도 하지 않는다. `durability: strict` 지원과 실제 디스크 내구성은 대상 브라우저·모바일에서 검증해야 한다.

자동 트랜잭션 밖 네트워크 호출, 서버 전송, 주기적 재시도, manifest 생성, 종료 시 큐 비움·서버 봉인은 아직 연결하지 않았다. 새로고침 후 같은 세션을 복구하는 절차와 탭 간 소유권, 인계된 이전 큐 처리도 별도 과제다.

## 검증 및 다음 작업

최초 구현 이후 타입 검사와 아래 실제 Chrome IndexedDB 검증을 실행했다. 메모리 DB 스텁으로 내구성을 인증한 것은 아니지만, 실제 디스크 장애·강제 종료 복구까지 검증한 것은 아니다.

운영 DB 접근·배포·writer 교체는 없으며 `BLOCKED_BEFORE_LOGIN_BACKEND`를 유지한다.
