# 원자적 저장 필수 과제와 확대 검증 계획

작성: 2026-09-08. 운영 데이터 쓰기 및 배포 없음.

## 구현 경계

신규 `scoringAtomicMatches` 저장 계약은 원자적 스냅샷, revision CAS, 소유자/lockEpoch, 변경 불가능한 커밋 영수증, SHA-256 요청 식별, UTF-8 크기 제한을 제공한다. 같은 길이의 정정과 실행 취소도 새 revision으로 기록한다. 요청을 로컬 복구 큐에 먼저 보관하고 확인 응답 이후에만 제거한다. 오프라인, 응답 유실, 충돌, 권한 회수, 저장소 오류를 구분하며 자동 덮어쓰기나 자동 재시도를 하지 않는다.

Firestore 어댑터는 명시적으로 주입한 DB와 로그인 UID를 사용한다. `enabled`가 false이거나 관리자에 의해 준비된 스트림이 없으면 기존 경기를 임의로 전환하지 않는다. 새 저장 상태 컴포넌트는 주입형 outbox를 표시한다. **아직 운영 Provider의 기존 저장 경로와 관전자 읽기 경로를 교체하지 않았다.** 이번 작업은 신규 계약과 어댑터, 규칙, 복구 UI 및 격리 검증 단계다. 기존 운영 경로의 길이 기반 저장 위험이 해소되었다고 해석하면 안 된다.

새 스트림은 기록원/관리자용 비공개 데이터다. 일반 관전자 공개용 투영, 기존 이벤트의 누락 ID 정비, 스트림 생성/소유권 관리 화면, 기존 기록의 일관된 이관, 운영 플래그 연결은 다음 전환 단계에 필요하다. 서버는 보안 규칙으로 소유권과 revision/receipt 결합을 검사하지만 야구 규칙의 모든 의미를 판정하지는 않는다. 큰 경기의 700KB 초과는 분할 저장으로 임의 전환하지 않고 거절한다. 장기적으로 스냅샷 체크포인트와 사건별 저장으로 확장해야 한다.

원자성·트랜잭션 재시도·오프라인 동작은 [Firebase 트랜잭션 문서](https://firebase.google.com/docs/firestore/manage-data/transactions)를 따른다. 테스트 격리는 [Firestore 에뮬레이터 문서](https://firebase.google.com/docs/emulator-suite/connect_firestore)를 참고했다.

## 테스트 종류 확대

| 계층 | 기존 범위 | 이번 추가 범위 |
|---|---|---|
| 규칙/계산 단위 | 기존 코어 269건 | 출루율 SH/SF/CI 조합, 잘못된 숫자, 종료 필드 정규화, 40종 플레이의 독립 기대값, 입력 거절 22종, 32개 고정 시드의 1,280개 플레이 전이 |
| 저장 계약 단위 | 없음 | 동일 요청 재시도, 내용 변경 ID 충돌, 동일 길이 정정, 동시 작성, 취소 revision, 권한/epoch, payload 한도, 영속 큐 복구, 저장소 오류, 잘못된 ACK, 늦은 ACK |
| 모달 브라우저 E2E | 12 성공+3 거절을 두 viewport에서 실행, 30회 | 40 성공+25 거절+6 권한/복구 흐름+3 출루율 표시+8 저장 흐름을 두 viewport에서 실행, 164회 계획 |
| Firestore SDK/규칙 | 미실시 | 로컬 에뮬레이터에서 실제 트랜잭션, 동시 revision, 원자성, immutable receipt, 권한/역할 회수, 비공개 읽기, 오프라인, 응답 유실 복구, 한글 경기 ID |

종류 수와 조합 수를 구분한다. 시드 시뮬레이션이나 viewport 반복을 모두 서로 다른 야구 규칙 사례라고 세지 않는다. 브라우저 저장 흐름은 실제 outbox/UI와 메모리 전송 대역을 사용한다. Firestore 테스트는 실제 SDK/보안 규칙을 사용하지만 실제 운영 인증 및 운영 Provider를 통과하는 전체 페이지 E2E는 아니다.

추가 성공 사례: 장타·만루 홈런·실제/자동 볼넷·사구·타격방해·SH/SF 구분·실제/자동 삼진·일반/번트 파울·WP/PB·보크·CS·도루·실책 출루·주루 단독 복수 아웃·견제 제3아웃. 추가 거절 사례: 이동 누락, 안타 종류/도달 베이스 불일치, 실책 미연결, 중복 점유, 출발 위치 불일치, 도루 타점, 어필 종류/근거 오류, 볼넷/삼진/사구 투구 모순, 진루 없는 WP/SH, 득점 없는 SF, 아웃 주자 재이동.

## 실행과 안전

- `npm run test:scoring`: 네트워크·Firebase Provider 없이 순수 함수와 격리 소스 추출 테스트.
- `npm run test:scoring:e2e`: 별도 Vite, 외부 요청 및 쓰기 메서드 차단, 인증/환경설정 미사용. 결과는 `outputs/scoring-e2e/<시각>/`.
- `npm run test:scoring:firestore`: `demo-aubl-scoring` 프로젝트와 loopback 포트 8088만 사용. 운영 Firebase 설정으로 fallback하지 않음. SDK 클라이언트 정리 및 생성한 emulator fixture 삭제.
- `npm run typecheck`: 제품 TypeScript 검사. 테스트 성공과 타입 검사 성공은 따로 기록.

실행 결과는 별도 로그와 E2E 자동 생성 보고서에 기록한다. 이 문서는 실행 전 계획이며 통과를 선언하지 않는다. 구현 중 발견된 테스트 하네스 오류는 제품 오류와 구별해 보고하고 수정 승인을 받는다.

## 남은 필수 작업

1. 새 계약의 검증 실패를 정리하고 해결한 후 운영 Provider/관전자 읽기 전환을 설계한다. 동기화 도중 들어오는 스냅샷의 부분 노출도 방지해야 한다.
2. 대회별 규칙 프로필, 과거 어필/정정 재생, 타순 착오·교체 책임·자책점 재구성을 별도 의미론 테스트로 확장한다.
3. 새 스트림 이관·복구·소유권 인계와 실제 라우트 E2E를 분리 환경에서 검증한다. 이후에만 제한된 경기의 운영 전환을 승인한다.
