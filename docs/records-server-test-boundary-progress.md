# 서버 운영 테스트 경계 구현 진행

작성일: 2026-09-08

## 이번 구현

`functions/scoring_test_boundary.py`에 외부로 노출되지 않는 내부 서비스를 추가했다.

- 서버에 저장된 실행 명세의 구조, 최대 3경기·24시간, 참여자 및 작업 목록 검증.
- 서버 설정의 프로젝트·API와 명세의 일치 확인.
- 서버 시각 기준 승인·만료, active 상태, 참여자 역할 및 경기 허용 목록 확인.
- 명시적인 테스트 운영자 권한으로 disabled 실행만 등록. 등록 단계에서 호출 카운터 조작 금지.
- 긴급 중단 트랜잭션. 명세 일부가 손상되어도 중단 가능하고 closed 상태는 유지.
- 요청 ID·주체·경기·작업·해시를 묶은 호출 예산 예약 및 카운터의 원자적 갱신.
- 동일 예약 재시도는 예산을 다시 차감하지 않고, 다른 내용의 ID 재사용은 거부.
- 서버 고정 컬렉션 목록을 이용한 테스트 경로 구성. 일반 경기 경로 fallback 없음.

## 중요한 제한

**내부 정책·예약 서비스의 로컬 검증을 통과했지만 운영 준비 완료는 아니다.** 최초 구현 이후 아래 후속 검증을 실행했다. 외부 callable·HTTP endpoint, 기존 writer 및 관리자 UI에는 연결하지 않았고 운영 실행을 등록하거나 배포하지 않았다.

`SCORING_TEST_SERVER_ENABLED` 기본값은 비활성이다. 이 값을 켜더라도 실행 활성화 API는 제공하지 않는다. 기존 클라이언트 `production-test` 차단 및 Firestore namespace 전면 차단은 유지한다.

`operator_authorized`와 UID는 향후 진입점이 검증한 인증·전용 운영자 권한에서만 전달해야 한다. 클라이언트 payload에서 받으면 안 된다. 일반 관리자 역할을 테스트 운영자 권한으로 자동 승격하지 않는다.

요청 예약은 서버 기록 커밋이나 ACK가 아니다. 예약 이후 작업 실패도 예산을 소비하며, 재시도 예약 성공을 실제 기록 저장 성공으로 반환해서는 안 된다. 카운터는 서로 다른 접수 요청 수를 제한할 뿐 반복 HTTP 호출, 조회 비용, 업로드 바이트를 제한하는 rate limiter가 아니다.

예약과 실제 쓰기 사이에 중단·만료가 발생할 수 있다. 실제 writer는 쓰기 트랜잭션에서 실행 상태·서버 시각·세션·epoch를 다시 검증해야 한다. 경로 생성 역시 인가가 아니며 읽기·쓰기 각각의 서버 검사가 필요하다.

## 다음 검증 및 연결 작업

1. 정상·만료 경계·모순 입력·권한 행렬의 Python 단위 테스트.
2. Firestore 에뮬레이터에서 동시 예산 예약, 같은 ID 다른 내용, 중단과 요청 경합 검증.
3. 서버 인증 어댑터와 전용 운영자 인가 연결. 실행 명세의 버전·승인 감사 이력 추가.
4. 실제 writer의 트랜잭션 내 재인가 및 기록 커밋 영수증 연결.
5. 서버 내부 외부 연결 차단, 요청 빈도·업로드 예산, 승인된 활성화 절차 구현.

전체 정책과 선택 근거는 [아키텍처 결정 문서](records-controlled-production-architecture-decisions.md)를 따른다. 운영 진입 판정은 계속 `BLOCKED_BEFORE_LOGIN_BACKEND`다.

동시 중단 검증은 예약과 중단 중 어느 트랜잭션이 먼저 완료되든 일관성을 유지하고, 중단 이후의 신규 예약은 거부되는지 확인한다. 아직 존재하지 않는 실제 경기 writer의 저장 경합·최종 봉인까지 검증한 것은 아니다. 서버 인증·HTTP rate limit·업로드 예산·외부 연결 차단도 미검증 잔여 과제다.
