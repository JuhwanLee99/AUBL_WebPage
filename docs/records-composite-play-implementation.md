# 복합 플레이 모달 구현 및 검증 기록

작성일: 2026-09-08. 대상: 실시간 기록원 화면의 `복합 플레이 기록` 버튼.

후속 변경: [운영 준비도와 보완 작업](./records-production-hardening.md). 잠금·대기 복구, 종료 세부 기록 보존, 출루율, 공개 중계 표시를 보완했다. 아래 기존 검증 결과는 후속 변경 이전의 결과이며 이번 변경은 재검증 전이다.

## 1. 구현 범위 선언 (검증 실행 전 작성)

이 문서는 설계안과 구현 사실, 검증 결과를 구분한다. **모든 KBO 상황의 자동 판정과 전체 화면 전환이 완료된 것은 아니다.** 신규 통합 경로를 추가했으며 기존 개별 모달은 남아 있다. 단일 플레이의 연속 행위, 복수 기록 판정, 수동 근거 입력을 지원한다. 아래 제한 사항을 넘어서는 상황을 단순 메모만으로 처리 완료했다고 간주하지 않는다.

근거는 [KBO 2025 공식 야구규칙](https://6ptotvmi5753.edge.naverncp.com/KBO_FILE/ebook/pdf/2025_%EC%95%BC%EA%B5%AC%EA%B7%9C%EC%B9%99.pdf)의 경기 및 공식기록 조항과 [2026 KBO 주요 규정·규칙](https://www.koreabaseball.com/Kbo/League/GameManage2026.aspx)이다. 2026 변경 페이지는 피치클락 위반의 볼/스트라이크 부과와 리그별 차이를 명시한다. 2026 전체 규칙집 전수 대조를 완료했다는 의미는 아니다.

| 경로 | 구현 내용 | 확인할 사항 |

| 투수 | 실제 투구와 자동 판정 분리, 실제 아웃 수, 주자별 실점 책임 | 자책점은 미확정, 과거 투타 교체 책임 자동 판단 미구현 |

구형 함수는 강제로 제거하거나 주석 처리하지 않았다. 여전히 호출되는 함수가 있으며, 신규 모달 검증만으로 전부 미사용이라고 판단할 수 없다. 이전에 미사용으로 확인된 `classifyResult` 래퍼의 주석 보존은 유지한다.

## 3. 모달 기록 방법

1. `복합 플레이 기록`을 열어 시작 이닝·아웃·카운트·타자·투수를 확인한다.
2. 타격 판정을 선택한다. `1루타`와 타자주자의 최종 위치는 별개다. `타석 계속`은 투구/주루 단독 사건이다.
3. 이번 공의 결과를 입력한다. 이미 입력한 공을 다시 포함하지 않는다. 자동 볼/스트라이크와 선언 고의4구는 실제 투구수에 합산하지 않는다.
4. 독립적인 실책마다 행을 추가한다. 한 실책에 여러 주자 이동을 연결하면 팀 실책은 한 개다.
5. 주자별 버튼으로 행을 추가하고 앞/뒤 이동 버튼으로 실제 발생 순서를 정렬한다. 같은 주자의 후속 이동은 직전 위치에서 시작한다. 움직이지 않은 주자는 행을 만들지 않는다.
6. 아웃 행에는 태그/포스/타자 1루 도달 전/포구/삼진/어필 등의 성격을 지정한다. 자살 야수와 보살 경로를 별도로 넣는다.
7. 홈 도달마다 타점 인정 여부를 정한다. 제3아웃 성격과 순서에 따라 득점이 취소되면 타점을 강제로 인정할 수 없다.
8. FC·실책·희생타·방해의 근거를 입력하고 판정을 확정한다. 특수 판정은 규칙 조항 또는 심판 확인 근거도 필요하다.
9. 주자 책임투수를 확인한다. FC로 선행주자가 아웃되면 타자주자의 책임을 자동 추측하지 않고 명시적으로 확정한다. 빈 책임은 미상이지 현 투수 책임이 아니다.
10. 예상 점수/아웃/베이스, 문자중계, 타자/투수/수비 증분을 보고 최종 확인 후 적용한다.

닫은 초안은 컴포넌트가 유지되는 동안 보존한다. 입력 중 경기 상태가 바뀌면 새 상황으로 다시 작성해야 한다. 브라우저 새로고침을 견디는 영구 초안 저장은 구현하지 않았다. 적용 버튼의 성공 표시는 로컬 상태 적용을 뜻하며 서버 저장 성공 영수증은 아니다.

## 5. 검증 절차와 운영 데이터 안전

1. 위 구현 목록과 기대값을 먼저 작성한다.
2. `npm run test:scoring`으로 기존 회귀와 신규 순수 함수/격리 VM 테스트를 실행한다.
3. 전체 TypeScript 검사와 변경 파일 대상 ESLint를 실행한다.
4. 실제 결과를 아래에 추가한다. 실패 시 기대값을 느슨하게 바꿔 통과시키지 않는다.
5. 프로덕션 API, Firebase 초기화, 인증, 경기 생성/저장/삭제는 수행하지 않는다. fixture ID는 `LOCAL_TEST_COMPOSITE_DO_NOT_PUBLISH`다.

VM 테스트는 필요한 함수 선언만 추출하며 React store의 모듈 import나 production effects는 실행하지 않는다. 상태 적용 테스트에서 경기 진행 보조 함수 일부는 stub이므로 전체 reducer/Undo/Redo/영속화 E2E 검증으로 표현하지 않는다.

## 6. 아직 전체 대응으로 선언할 수 없는 항목

- 기존 개별 모달의 새 엔진 전면 전환과 오래된 플레이 어댑터 동등성 검증.
- 타순 위반, 대타/대주자/투수 교체의 시점별 책임, DH 소멸/복원, 자책점 이닝 재구성.
- 이전 사건을 참조하는 사후 어필/재심/정정 원장과 이후 모든 플레이의 재생. 현재 모달의 어필은 같은 플레이 내로 한정한다.
- 자동 안전진루권 거리 판정, 포스 해제/재형성, 인필드플라이 적용 요건, 방해 판정의 선택권과 원상복귀를 규칙 엔진이 완전하게 증명하는 기능.
- 끝내기 확정/단축/서스펜디드/몰수/타이브레이크를 포함한 경기 운영 프로파일.
- 불변 선수 ID 이관, 서버 revision 비교 후 원자적 저장, 중복 제출의 서버 측 보장.
- 실제 브라우저 모바일/데스크톱 조작, 실제 저장/재조회, 실제 경기 20건과 문자중계 500건에 대한 검증.

따라서 이번 산출물은 **복합 플레이 입력과 일관된 파생 기록의 신규 경로**다. 전체 상황 지원 완료나 운영 기본 경로 교체 승인을 의미하지 않는다.

### 7.2 검증 후 판정과 수정 대기

테스트 통과를 전체 제품 통과로 표시하지 않는다. 신규 모달의 두 타입 오류가 남아 있어 **배포 승인 보류**다. 반려 목록을 `(state.scoringRejections ?? []).length`로 읽는 수정이 필요하며, 발견 후 사용자에게 수정·재검증 여부를 문의했다. 이 문서 작성 시 수정은 아직 적용하지 않았다.

또한 현재 판정 선택에서 낫아웃 실패(포수 태그 또는 1루 송구 아웃)를 출루 성공과 명확히 구분하는 전용 표현은 보완이 필요하다. 이번 F05는 낫아웃으로 실제 1루에 도달한 경우만 검증했으며, 낫아웃 실패까지 검증 완료로 확대 해석하지 않는다.

규칙 판단을 입력할 수 있다는 것과 규칙의 모든 적용 요건을 자동 검증한다는 것은 다르다. 인필드플라이/방해/안전진루권/사후 정정/교체 책임 등 6절 항목은 계속 미완료이며, 전체 야구 상황 대응 완료를 선언하지 않는다.

## 8. 승인된 보완: 낫아웃 실패 및 선택적 반려 목록

### 8.1 재검증 전 변경 사항과 기대값

- 모달의 선택적 반려 목록 접근 두 곳에 빈 배열 기본값을 적용한다.
- `so_out` / `낫아웃 실패`를 추가한다. `so_reach`는 실제 1루 이상 도달을 요구하고, 출루 뒤 추가 주루 아웃은 별도 행으로 유지한다.
- 실패 행은 타석에서 직접 태그 아웃 또는 타자주자 1루 도달 전 아웃으로 입력한다. K/AB/PA/BF와 실제 아웃은 각각 한 번만 집계한다.
- 세 번째 아웃이 타자주자 1루 도달 전이면 태그 방식도 선행 홈 도달을 득점으로 인정하지 않는다. 출루 이후 추가 주루에서의 제3아웃 태그는 실제 시간 순서로 판단한다.
- KBO 9.12(d)(7)(B)(ii)에 따라 타자주자를 태그 또는 1루 송구로 처리하는 동안의 다른 주자 진루는 WP/PB가 아닌 진루/야수선택으로 입력하도록 제한한다. 1루 점유·2아웃 전 자동 삼진 아웃의 WP/PB 예외는 유지한다.
- 자동 스트라이크·번트 파울은 낫아웃 실패 주루로 입력할 수 없고, 해당 득점에 타점을 부여할 수 없다.
