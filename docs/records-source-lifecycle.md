# 실시간 참고 기록과 UniquePlay 공식 기록의 분리

작성일: 2026-09-08

## 1. 서비스 정책

자체 기록 엔진, 모달, 문자중계의 목적은 경기 중 실시간 서비스와 기록 시스템 개선이다. 자체 기록을 공식 통계의 대체 원천으로 승격하지 않는다. UniquePlay에서 수집한 **검수·게시된 종료 경기 상세 기록**을 서버가 확인한 뒤 공개 원천을 전환한다.

| 단계 | 일반 사용자 | 기록원 | 관리자 | 공개 원천 |
| --- | --- | --- | --- | --- |
| 실시간 기록 중 | 자체 중계·기록 조회 | 모달 기록 | 기록·관리 | AUBL 참고 기록 |
| 경기 종료, 공식 상세 미확정 | 자체 참고 기록 조회 | 기존 허용 범위 | 저장 확인·공식 자료 검수 | AUBL 참고 기록 |
| 공식 전환 완료 | 공식 기록만 조회 | 관리자와 동일하지 않음, 자체 원본 접근 불가 | 원본 비교·이슈 등록 | UniquePlay 고정 리비전 |
| 공식 API 장애 또는 재동기화 검수 중 | 직전 확정 공식 기록 | 자체 기록으로 복귀 불가 | 재조회·문제 조사 | 직전 확정 리비전 유지 |

- 일정만 수집된 경우, `NOT_COLLECTED`, `NOT_PUBLISHED`, `REVIEW_REQUIRED`, 진행 중 경기는 공식 전환 대상이 아니다.
- 공식 전환은 수집 성공과 별도 상태다. `matches.syncRevision`만 있다고 자체 기록을 숨기지 않는다.
- 경기별 공식 전환이 완료되면 자체 기록은 관리자에게도 읽기 전용이다. 개선 결과는 새 코드와 검수 이력으로 남긴다.
- 과거 공개 당시 사용자에게 전달된 데이터, 다운로드, 스크린샷은 회수할 수 없다. 전환 이후 서버 접근 및 현재 화면의 잔여 상태를 차단한다.
- 현재 단계에서 `recordMode: official`은 기존 경기 분류 값이다. 데이터 출처의 공식성은 별도 `recordSources`로 판단한다.

## 2. 구현한 저장 구조

| 경로 | 용도 | 전환 후 권한 |
| --- | --- | --- |
| `matches/{matchId}` | 공개 일정, 공식 점수, 원천 요약 | 공개 읽기, 브라우저 수정 불가 |
| `matchStates/{matchId}` | 자체 기록 상태 원본 | 관리자 읽기 전용 |
| `matchStates/{matchId}/feed`, `/events` | 자체 문자중계·모달 사건 원본 | 관리자 읽기 전용 |
| `recordSources/{matchId}` | 공식 원천, 리비전, 해시, 공개 상세 스냅샷 | 공개 읽기, 서버만 쓰기 |
| `recordArchives/{matchId}` | 최초 전환 당시 일정의 자체 기록 필드와 원본 위치 | 관리자 읽기, 서버만 최초 생성 |
| `recordArchives/{matchId}/officialRevisions/{revisionHash}` | 비교에 사용한 공식 리비전 이력 | 관리자 읽기, 서버 생성 |
| `recordArchives/{matchId}/issues/{issueId}` | 개선 이슈·검증 이력 | 관리자 추가·읽기, 수정·삭제 불가 |
| `recordSourceJobs/{matchId}` | 자동 전환 성공 또는 수동 검토 필요 상태 | 관리자 읽기, 서버 쓰기 |

`recordSources` 문서의 존재가 서버 접근 제어의 기준이다. 브라우저에서 출처 플래그를 바꾸거나 지워 원본을 재공개할 수 없다. 새 Atomic 저장 프로토타입의 소유 기록원 읽기·쓰기 역시 공식 전환 후 제한한다. 기록원 역할만 가진 계정에는 관리자 보관 권한을 주지 않는다.

Firestore는 문서 내 특정 필드만 비공개로 할 수 없다. 따라서 `matches`의 `postGame`, `manualEntryDraft`, `lineups`, `benches`, `notes`는 관리자 보관 문서에 보존하고 공개 문서에서 제거한다. 공개 점수는 공식 점수로 교체한다. 원본 `matchStates`와 하위 문서는 이동하거나 지우지 않고 접근 정책을 바꿔 보존한다.

## 3. 공식 전환 처리

구현 위치:

- `functions/record_source_policy.py`: 전환 적격성 확인, 공식 공개 필드 화이트리스트, 내용 해시.
- `functions/record_sources.py`: 관리자 호출 처리, 신뢰된 백엔드 조회, Firestore 트랜잭션.
- `functions/main.py`: `promote_uniqueplay_record_source` callable, `sync_record_source` 일정 변경 트리거.

처리 순서:

1. 관리자의 `admin` custom claim을 확인한다. 이메일이나 일반 기록원 역할은 대체 근거로 사용하지 않는다.
2. 저장된 `sourceProvider`, `sourceGameId`, `seasonId`로 설정된 HTTPS 백엔드의 공식 상세 API를 조회한다. 브라우저가 전달한 박스스코어나 URL은 신뢰하지 않는다.
3. 경기·시즌·팀 매핑, 완료 상태, 게시 리비전, `AVAILABLE`, `CLEAN` 또는 `RESOLVED` 검수 상태를 확인한다.
4. 팀 R/H/E, 점수판 합계, 중복 이닝, 미실시 이닝 득점 등을 확인한다. 출처가 모호하거나 자료가 불충분하면 전환하지 않는다.
5. 자체 경기 종료 여부와 최근 15초 내 상태 저장 여부를 확인한다. 진행 중인 자체 기록을 일정 상태만 보고 잠그지 않는다.
6. 트랜잭션에서 일정의 경기 매핑과 리비전을 재확인한다. 최초 보관 문서를 생성하고, 공식 스냅샷·해시·리비전 이력을 기록하고, 공개 일정에서 자체 기록을 제거한다.
7. 같은 리비전·같은 내용 재시도는 성공으로 반환한다. 같은 리비전인데 내용이 다르거나 원본 보관 상태가 불완전하면 중단한다.
8. 이후 브라우저의 원본 변경·삭제·공식 플래그 변경은 Security Rules로 거부한다.

리비전이 바뀌면 최초 자체 기록 보관본은 그대로 두고 공식 스냅샷과 공식 리비전 이력만 추가한다. 이전 리비전으로 되돌리는 별도 복구 도구는 이번 구현에 포함하지 않는다. 공식 자료에 문제가 있어도 자체 원본을 다시 공개하는 식의 롤백은 허용하지 않는다.

### 실패와 재시도

- 공식 API 오류, 매핑 불일치, 진행 중 경기, 미검수 상태, 과대 스냅샷, 저장 직후에는 전환하지 않는다.
- 트랜잭션 실패 시 공개 원천 지정과 자체 기록 필드 제거가 부분 적용되지 않는다.
- API 조회와 NAS 리비전 활성화와 Firestore 트랜잭션은 서로 다른 저장소 작업이다. 전체 시스템의 단일 트랜잭션이라고 주장하지 않는다.
- 자동 트리거가 활성화 시점 차이로 실패하면 `recordSourceJobs`에 `REVIEW_REQUIRED`를 남긴다. 관리자 비교 화면에서 다시 조회·전환한다. 자동 무한 재시도나 주기적 전체 경기 스캔은 추가하지 않았다.
- 자동 트리거의 작업 문서는 운영 보조 상태다. 실제 공개 여부의 단일 기준은 `recordSources`다.

## 4. 공개 화면·기록원 화면

- `useRecordSource`는 경기 ID별로 출처를 구독한다. 다른 경기의 이전 응답은 현재 출처로 사용하지 않는다.
- 오프라인 캐시에 공식 문서가 없다는 사실만으로 자체 원본을 읽도록 허용하지 않는다. 출처 확인 실패 시 공개를 보류한다.
- 공식 전환 시 공유 Store의 자체 상태, 중계, 사건, undo/redo 이력을 비우고 자체 구독·소유권 heartbeat·예약 저장을 중지한다.
- 이미 시작한 비동기 구독 응답은 구독 해제 후 Store로 재주입되지 않도록 취소 여부를 확인한다.
- 문자중계 화면은 공식 전환 전에는 실시간 참고 기록임을 표시하고, 전환 후에는 고정된 공식 상세를 표시한다.
- 전광판, 독립 전광판, 기록원, 구형 관리자 기록 수정 화면에는 원천 게이트를 연결했다. 공식 전환된 자체 모달을 다시 열어 원본을 수정하지 않는다.
- 공식 스냅샷을 저장하므로 공개 상세는 NAS 상세 API가 일시적으로 실패해도 자체 자료로 대체되지 않는다.

## 5. 관리자 비교·개선 루프

진입: CMS의 **공식·자체 기록 비교**, `/admin/record-comparison?matchId=...`.

1. 경기 선택 후 현재 공개 원천과 매핑된 UniquePlay 경기·일정 리비전을 확인한다.
2. 공식 후보의 팀, 점수, 경기 시각, 검수 상태를 확인하고 자체 경기 종료·저장 확인란을 선택한다.
3. 공식 전환 또는 새 게시 리비전 재동기화를 요청한다. 서버가 동일한 조건을 다시 검증한다.
4. 관리자 보관 자료와 고정된 공식 자료를 비교한다.
5. 차이의 원인을 `모달 입력`, `상태 전이`, `문자중계 파서`, `집계`, `매핑`, `유니크 원천`, `원인 조사`로 분류한다.
6. 비교 항목 키, 원본 이벤트 ID, 관련 이슈 ID, 재현 방법을 근거로 등록한다.
7. 코드를 수정한 뒤 해당 이슈의 회귀 테스트 이름과 결과를 후속 검수 이력에 추가한다. 공식 기록과 자체 원본은 변경하지 않는다.

### 비교 범위와 보수적 처리

| 영역 | 현재 비교 | 주의 |
| --- | --- | --- |
| 팀 | 득점·안타·실책 | 자체 상태 점수를 우선하고 저장된 자체 총계를 보조로 사용 |
| 이닝 | 이닝별 득점, 미실시 X | X와 0을 동일 취급하지 않음 |
| 타자 | 타수·안타·득점·타점·도루 | 이름+등번호가 양쪽에서 유일할 때만 자동 비교 |
| 투수 | 피안타·실점·자책·삼진·투구 아웃·사사구 | 이닝 표기의 `.1`, `.2`를 아웃 수로 변환 |
| 문자중계·사건 | 원본 JSON 및 이벤트 ID 조회 | 문서 ID 순서 100건 페이지; 시간·플레이 순서를 자동 추정하지 않음 |
| 타석 결과 | 공식 원본과 자체 원본을 각각 열어 확인 | 타석 대 타석 자동 정렬은 후속 범위 |

- 자료 없음과 0, 이름 중복과 실제 수치 차이를 구분한다.
- 등번호가 없는 과거 자체 기록은 이름으로 강제 매칭하지 않고 매핑 확인 대상으로 남긴다.
- 기존 자체 `postGame` 집계 자체가 잘못되었을 가능성도 비교 대상이다. 엔진을 재실행한 결과로 원본을 덮어써 차이를 숨기지 않는다.
- 원본 feed/events 전체는 필요에 따라 페이지를 추가 조회한다. 루트 문서의 구형 배열은 별도 표시하고 중복 합산하지 않는다.
- 이슈는 공식 리비전과 해시에 고정된다. 다른 리비전이 활성화된 뒤 오래된 화면에서 저장하면 서버가 거부한다.
- 최신 검수 이력 100건을 표시한다. 이슈 편집, 삭제, 자동 병합, 전체 이슈 페이지 탐색은 후속 범위다.

## 6. 기존 공식 DB 임포트 경로 정리

기존 `import_completed_match` Cloud Function은 경기 종료 시 자체 기록을 MariaDB로 POST했다. 새 원천 정책과 충돌하므로 배포된 함수 이름은 유지하고 동작을 중단했으며 구형 흐름은 주석으로 남겼다.

브라우저의 `triggerMatchImport`, `triggerBulkImport`도 API 경계에서 명시적인 안내 오류를 반환하도록 바꾸고 기존 본문은 주석 보존했다. 다른 화면에서 같은 함수를 호출해도 자체 기록을 공식 DB로 임포트하지 않는다. 기존 관리 화면의 임포트 버튼은 아직 안내 오류를 표시하는 상태이며, 삭제하지 않았다.

**이 저장소 변경만으로 NAS의 직접 임포트 API 호출이나 기존 MariaDB 데이터가 정리되는 것은 아니다.** NAS 백엔드에서 다음 계약을 적용해야 공식 통계 전반의 원천 분리가 완성된다.

- 자체 기록 임포트 엔드포인트를 비활성화하거나 별도 `AUBL_LIVE` 연구용 영역으로 한정한다.
- 순위·시즌 누계·선수 통계는 활성 UniquePlay 공식 리비전만 사용하도록 확인한다.
- 과거 자체 기록으로 적재된 공식 통계의 출처를 감사하고, 승인된 마이그레이션으로만 정리한다.
- 일정 재동기화가 `recordAuthority`, `officialRecordRevision`을 제거하거나 `postGame`, `manualEntryDraft`, 자체 라인업 등을 공개 `matches`에 다시 넣지 않도록 프로젝션 계약을 맞춘다. Admin SDK는 Security Rules를 우회하므로 이 확인은 필수다.
- 독립된 AUBL 경기와 UniquePlay 일정이 서로 다른 경기 문서라면 운영자가 canonical 경기 ID 매핑을 확정한다. 이름·날짜만으로 중복 경기를 자동 병합하지 않는다.

## 7. 아직 운영 승인으로 볼 수 없는 항목

1. 기존 실시간 저장은 core/feed/events 분리 저장이다. 이번 보관은 서버에 실제 저장된 자료를 고정하며, 전송 중이던 마지막 입력까지 모두 ACK되었다는 보증은 아니다. 15초 대기 및 관리자 확인은 보조 수단이고 Atomic 저장 전환을 대체하지 않는다.
2. 기존 완료 경기의 일괄 공식 전환은 하지 않았다. 최초 운영 적용 시 매핑·저장 확인 후 관리자 화면에서 경기별 전환한다.
3. 자동 전환 트리거는 배포·설정 전까지 꺼져 있고, 과거 경기나 트리거 실패를 자동 전체 재처리하지 않는다.
4. 선수 ID 교차 매핑, 타석 자동 정렬, 복합 플레이 원인 추론, 공식 리비전 롤백 UI는 후속 과제다.
5. 기권·몰수·미실시 등 상세 박스스코어가 없는 공식 결과는 자동 전환하지 않는다. 전용 공식 결과 스키마와 승인 절차를 별도 설계해야 한다.
6. Flutter 등 다른 클라이언트는 동일한 서버 권한 제한을 받지만 공식 스냅샷 표시와 권한 오류 UX는 별도 연동이 필요하다.
7. 이번 변경에 대한 타입 검사·단위 테스트·E2E·Security Rules 에뮬레이터 검증은 아직 실행하지 않았다. 이전 기록 엔진의 테스트 통과 수치를 이번 출처 전환의 검증 결과로 재사용하지 않는다.

## 9. 단계적 배포

1. NAS의 공식 통계 원천과 일정 프로젝션 계약을 먼저 확인한다. 운영 Admin SDK는 Rules로 막을 수 없다는 점에 유의한다.
2. 새 컬렉션 접근 제어, 함수, 웹 클라이언트를 검증하고 함께 배포한다. 이 문서 작성 시에는 배포하지 않았다.
3. `RECORD_SOURCE_PROMOTION_ENABLED=false`, `RECORD_SOURCE_AUTO_PROMOTE=false`가 기본값이다. 기능 배포 자체로 경기를 자동 전환하지 않는다.
4. 에뮬레이터 검증 후 승인된 환경에서 `RECORD_SOURCE_PROMOTION_ENABLED=true`로 관리자 전환만 연다.
5. 매핑과 서버 저장 완료가 확인된 경기부터 전환하고, 일반 사용자·기록원·관리자 계정으로 권한을 확인한다.
6. Atomic 저장 ACK와 NAS 활성화 타이밍까지 검증된 뒤에만 `RECORD_SOURCE_AUTO_PROMOTE=true`를 검토한다.
7. 문제가 생기면 자동 전환을 끄고 기존 공식 스냅샷을 유지한다. 보관 문서 또는 `recordSources`를 삭제해 자체 자료를 재공개하지 않는다.
