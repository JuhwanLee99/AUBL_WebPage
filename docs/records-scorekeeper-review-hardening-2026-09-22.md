## 1단계에서 해결한 문제

이전 체크포인트는 undo/redo 이력만 제외한 전체 상태였다. 접속자 수, 하트비트 시간, 경기 목록 변경도 기록 변경으로 판단했다. 저장 대기 중 표시 정보가 바뀌거나 새로고침 후 표시 정보가 갱신되면 정상 플레이가 거부될 수 있었다.

비교만 느슨하게 하면 복구 시 과거 권한·접속 정보가 현재 상태를 덮어쓸 수 있다. 따라서 비교 범위, 저장 범위, 실제 적용 병합을 함께 바꿨다.

### 명시적 필드 분류

`src/shared/lib/scoringCheckpoint.ts`에서 `DemoSnapshot`의 필드를 세 가지로 분류한다.

| 분류 | 대표 필드 | 처리 |
|---|---|---|
| `record` | 경기 ID, 이닝·볼카운트·아웃·주자, 점수, 사건·문자중계, 라인업·벤치·제외 선수, 경기 진행·시간 제한 | 체크포인트 저장·비교 |
| `access` | 기록원 UID, 역할, 잠금 갱신 시각, 일시정지 | 체크포인트에서 제외, 현재 접근 상태를 별도 검증 |
| `ambient` | 접속자 수, 중계 영상·지연 설정, 경기 목록, 기록원 표시 이름·이메일, 거부 진단 목록 | 기록 충돌 비교에서 제외, 현재 값을 보존 |

`history`와 `futureHistory`는 체크포인트에서 제외한다. `Record<keyof DemoSnapshot, ...>`로 선언했기 때문에 타입에 새 필드가 추가되면 분류도 추가해야 한다. 런타임에 분류되지 않은 필드가 나타나면 임의로 버리지 않고 `unclassified-scoring-field`로 거부한다.

경기 목록은 표시용 비교에서 제외하지만, 현재 경기의 공식 원천 전환·종료 상태는 접근 검증에서 별도로 확인한다. 경기 목록 전체를 비교하지 않는 것과 공식 전환을 무시하는 것은 다르다.

### 현재 권한 검증

`DurableCompositeIntake.validateAccess`는 현재 경기 ID·기록원 UID·일시정지·경기 시작/종료 상태를 확인한다. 경기 목록이 제공되면 현재 경기 존재 여부, 종료·취소 여부, UniquePlay 공식 전환 여부도 검사한다.

그 후 기존 호스트 `port.validate`를 호출한다. 실제 인증 UID·역할·서버 작성 세션·epoch의 검증 책임은 여전히 호스트/서버에 있다. 로컬 상태의 UID 검사만으로 실제 인증을 완료한 것으로 판단하지 않는다.

### 저장·적용·복구

- 새 payload는 `version: 1`을 유지하고 `checkpointVersion: 2`를 표시한다. 입력과 전체 scope는 유지하되 체크포인트에는 기록 필드만 저장한다.
- 현재 기록 상태가 같으면 접속자 수나 기록원 표시 정보 변경 때문에 새 입력을 막지 않는다.
- 저장 후 실제 적용 직전에 현재 상태를 사용해 제품 reducer로 다시 투영한다. 기록 결과가 처음 저장한 투영과 같은지 확인한다.
- 실제 적용은 현재 상태에 저장된 기록 필드만 합친다. 현재 경기 목록·접속 정보·권한 정보와 현재 상태에서 생성한 undo/redo 이력을 유지한다.
- 복구에도 같은 방식으로 병합한다. 과거의 기록원 UID·잠금 시간·공식 원천 상태를 덮어쓰지 않는다.
- 기록 비교는 계속 점수·라인업·주자·경기 진행 변경을 차단한다. 저장 대기 중 권한 회수나 공식 전환이 발생하면 입력을 적용하지 않고 `pending` 원본을 보존한다.

기존 전체 체크포인트 구현은 주석으로 남겼다. 구형 `checkpointVersion` 미지정 payload는 읽을 수 있도록 비교 시 새 분류를 적용하지만, 운영 원본을 자동 덮어쓰거나 이관하지 않는다. 모든 구형 실데이터 변형의 복구가 검증된 것은 아니다.

## 다음 단계의 구체적 기준

2단계는 `syncLiveScorePatch`, `syncScheduleMatchesWrite`의 성공 전 키 갱신과 `syncGameStateWrite`의 오류 무조건 재시도를 먼저 다룬다.

- 저장 성공은 요청 당시의 값에 대해서만 반영한다. 대기 중 더 최신 입력을 저장 완료로 표시하지 않는다.
- 동일 내용의 최초 저장 실패가 나중에 중복 방지 키 때문에 영구 누락되지 않게 한다.
- 오래된 요청 응답이 최신 저장 기준을 역행시키지 않게 한다.
- 권한 상실·공식 전환·다른 경기 이동은 재시도를 멈춘다.
- 일시적 통신 장애는 제한된 지연 재시도와 실패 상태를 남긴다.
- 기존 core/feed/events 분리 저장 자체의 원자성 문제를 해결했다고 오인하지 않는다. 최종적으로 신규 단일 writer로 대체해야 한다.

## 2단계 후속 완료: 저장 ACK 및 제한된 재시도 (2026-09-22)

이 절은 위 1단계 당시의 진행 현황을 갱신한다. 점수·일정 저장의 ACK 처리와 기존 경기 저장의 제한된 재시도 보강을 완료했다. 영속 큐 기반 원자적 저장 경로로의 전환 완료를 의미하지 않는다.

### 구현 범위

- `src/shared/lib/scoringWriteRetry.ts`: 점수·일정 요청을 직렬화하고, 해당 요청의 성공 응답 이후에만 저장 완료 키를 갱신한다. 전송 중 변경은 다음 요청으로 유지한다.
- 일시 오류는 1초·2초·4초·8초·16초 간격으로 재시도한다. 최초 전송을 포함해 최대 6회이며, 권한·인증·알 수 없는 오류는 자동 반복하지 않는다.
- 로그아웃·공식 전환·접근 세션 변경·화면 해제 시 오래된 응답의 완료 처리를 차단한다. 이미 서버에 전송된 요청 자체를 취소하거나 되돌린다는 의미는 아니다.
- `src/shared/state/demoStore.effects.ts`, `src/shared/state/demoStore.tsx`: 점수·일정 저장과 기존 경기 기록 저장에 접근 재확인 및 중단 처리를 연결한다.
- 저장 결과 상태는 조회 함수로 제공한다. 재시도·차단 상태를 실제 사용자 화면에 표시하는 작업은 별도다.

### 이번 승인에 따른 추가 수정

1. 테스트 번들에 `firebase/auth` 모의를 추가했다. 예상하지 않은 토큰 조회는 즉시 실패하며 실제 Auth 또는 운영 Firestore에 연결하지 않는다.

## 3단계 후속 완료: 주루 모달의 반영 확인과 초안 보존 (2026-09-22)

### 변경 내용

- `RunnerMatrixButton.tsx`는 액션 호출 직후 초안을 지우지 않는다. 현재 경기의 `runnerPlay.input.id`가 제출 ID와 일치하는 사건으로 반영된 것을 확인한 후 닫는다.
- 제출 중 입력과 중복 제출을 차단한다. 동일 경기의 새 `runner_matrix` 반려 기록 또는 동기 예외가 발생하면 초안과 오류 안내를 남긴다. 다른 종류의 반려 기록은 해당 제출의 반려로 취급하지 않는다.
- 8초 동안 결과가 확인되지 않으면 지연 안내를 표시한다. 시간 초과를 실패 또는 성공으로 단정하지 않으며, 재제출을 계속 차단한다. 뒤늦게 해당 사건이 반영되면 정상 종료한다.
- 닫기·ESC는 초안을 유지한다. 확인 후 명시적으로 초안을 버리는 버튼을 별도로 제공한다. 제출 직후 대기 중에는 닫기를 막고, 지연 안내 이후에는 초안을 보존한 채 닫을 수 있다.
- 초안이 남아 있으면 페이지 이탈 경고를 등록한다. 로컬 기록 반영 확인과 서버 저장 완료가 다름을 화면에 명시했다.

### 적용 구조

- 신규 분기를 선택한 인스턴스에서 세션 옵션이 사라져도 기존 Provider로 자동 복귀하지 않는다. 차단 안내를 표시한다.

- 복합 모달은 Provider가 제공하는 영속 접수 함수를 우선 사용하고, 연결 상태·차단 사유·기기 복구 패널을 보여준다.
- 신규 경로에서 기존 액션은 본문 실행 전에 차단한다. 현재 지원 범위는 복합 플레이와 명시적 복구이며, 기존 볼·주자 단독 입력·교체·종료·undo/redo 등은 자동 우회하지 않고 미반영 안내를 표시한다.

## 6단계 진행 중: Provider 자동 전송과 ACK 연결 (2026-09-22)

- 선택형 `publication` 설정을 받은 영속 Provider에 자동 전송 제어기를 연결했다. 기기 접수 성공과 서버 전송 성공을 분리하고, 전송 오류는 모달 접수 실패로 바꾸지 않는다.
- 큐의 특정 입력 순번에 저장된 after 스냅샷에서 state/feed/events/stats를 생성한다. live 배열 길이로 전송 완료를 판단하지 않는다.
- 128KiB 불변 블록 업로드 후 manifest를 고정하고 기존 adapter의 prepare/flush 및 ACK 검증을 사용한다. 전송 중 들어온 입력은 다음 커밋으로 처리한다.
- ACK 유실은 고정된 요청으로 재시도한다. 실패 시 자동 무한 재시도하지 않고 큐와 오류 안내를 남기며 화면에서 재시도할 수 있다.
- writer는 전체 전송 작업이 끝날 때까지 로컬 잠금을 보관한다. 업로드 뒤 권한을 잃으면 새 커밋을 시작하지 않는다.
- 서버 revision이 초기 화면 revision보다 진행된 로컬 큐를 발견하면 신뢰 가능한 서버 체크포인트 조회를 요구한다. 오래된 초기 화면으로 자동 진행하지 않는다.

### 6단계 추가 보완: 인계 후 업로드 예약 ID 충돌 해소 (2026-09-22)
