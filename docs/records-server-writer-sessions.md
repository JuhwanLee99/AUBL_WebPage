# 서버 기록 세션과 명시적 인계

작성일: 2026-09-08

## 구현 범위

`functions/scoring_test_sessions.py`에 비공개 내부 세션 서비스를 추가했다. 실행 인가·승인 해시 검증과 기존 제한 재시도 트랜잭션을 사용한다.

- 첫 작성 세션은 경기별로 create하여 epoch 1을 얻는다.
- 같은 UID·같은 session ID는 현재 세션을 재조회한다. 같은 UID라도 다른 session ID는 자동 인계하지 않는다.
- 세션이 비활성이거나 존재하지만 충돌하는 경우 새 세션으로 자동 대체하지 않는다.
- 명시적 인계는 전용 테스트 운영자 권한과 해당 실행의 관리자·review 권한을 모두 요구한다.
- 새 작성자는 실행 참여자 중 record 권한이 있는 관리자 또는 기록원이어야 한다.
- expected epoch를 검사하고 세션 변경·인계 영수증을 한 트랜잭션으로 저장한다.
- 인계마다 새로운 session ID와 증가한 epoch를 사용한다. 이전 세션은 `assert_writer` 검사에서 거부된다.
- 같은 인계 요청 ID·동일 내용은 기존 영수증을 반환하고, 다른 내용은 거부한다.

## 정책 선택

시간 경과에 의한 자동 작성권 탈취는 구현하지 않는다. 오프라인 기록원의 큐가 남아 있을 수 있기 때문이다. 연결이 끊겼다고 바로 새 작성자에게 권한을 주지 않고 관리자가 남은 입력을 확인한 후 명시적으로 인계해야 한다.

인계 요청의 재조회는 과거 영수증을 반환한다. 그 이후 다른 인계가 있었으면 과거 영수증의 epoch는 최신 작성권이 아니다. 실제 쓰기마다 현재 서버 세션과 대조해야 한다.

클라이언트는 탭별 고유 session ID를 사용해야 한다. 동일 ID를 다른 탭에 복제하면 서버는 두 탭을 구분할 수 없으므로 브라우저 탭 소유권·재시작 복구 계약도 별도로 필요하다.

## 아직 연결하지 않은 부분

세션 생성·인계의 초기 검증 이후 새 블록 전송 서비스에 필수 검사를 연결하고 아래 후속 검증을 통과했다. 기존 모달 Provider writer에는 연결하지 않았으므로 실제 모든 쓰기가 이전 epoch를 차단한다고 주장하지 않는다.

후속 저장 통합은 업로드 전 세션 검사와 최종 저장 트랜잭션에서 세션 문서 읽기·검사를 모두 포함해야 한다. 최종 manifest 커밋, 봉인·재개, IDB 큐 인계, 외부 endpoint, 세션 작업의 호출 빈도 제한도 남아 있다.

전용 운영자 boolean과 UID는 검증된 서버 인증에서만 전달해야 하며 클라이언트 payload를 신뢰하지 않는다. 실제 claim 발급·회수 및 로그인은 아직 연결하지 않았다.

## 검증 상태

최초 구현 이후 아래 후속 검증을 실행했다. 동시 최초 획득, 같은 계정의 두 세션, 비관리자·비참여자 인계, stale epoch, 동일 요청 재시도, 인계 경합, 이전 세션 거부와 인계 원본 보존을 포함한다.

외부 API·운영 활성화·배포는 없으며 `BLOCKED_BEFORE_LOGIN_BACKEND`를 유지한다.

## 후속 검증 결과

2026-09-08 실행:

| 구분 | 결과 | 범위 |
|---|---|---|
| 단위 | 135건 통과, 실패·제외 0건 | 기존 129건 + 작성자 검증 6건 |
| Firestore 에뮬레이터 | 31건 통과, 실패·제외 0건 | 기존 24건 + 세션/인계 통합 7건 |

동시 최초 획득에서는 하나의 세션만 성공했고, 동시 인계에서는 하나의 인계만 성공하여 epoch가 한 번 증가했다. 같은 인계 요청의 재조회는 중복 변경을 만들지 않았고, 다른 내용의 요청 ID 재사용은 거부했다. 후속 인계 이후 과거 영수증을 재조회해도 최신 세션은 유지되며 이전 세션의 `assert_writer` 검사는 실패했다.

에뮬레이터 테스트는 세션·인계 영수증·업로드 블록·예약·실행 문서를 해당 테스트 범위에서 삭제하고 재조회로 부재를 확인했다. 운영 데이터·권한·외부 네트워크에는 접근하지 않았다. 원본 로그는 `outputs/server-writer-sessions-2026-09-08/`에 보관했다.

이번 결과는 세션 서비스와 검증 함수의 통과다. 아직 실제 블록 업로드 및 경기 writer가 이 검사를 필수로 호출하지 않으므로, 전체 저장 경로의 이전 세션 차단이 완료되었다고 판단하지 않는다. 다음 작업은 업로드 시작 전과 최종 저장 트랜잭션에 세션 검사를 연결하고 인계와 저장의 경합을 검증하는 것이다.

## 후속 구현: 블록 저장에 세션 필수 연결

위 135건·31건 결과 이후 `ScoringTestTransferService.stage_block`에 `writer_session_id`와 `lock_epoch`를 필수 인자로 추가했다. 구형 호출을 세션 없는 상태로 자동 허용하거나 세션을 자동 생성하지 않는다.

- 스트림을 읽기 전 현재 작성자·세션·epoch·경기 범위·승인 해시를 검사한다.
- 업로드 검증 후 예산 예약 전에 세션을 다시 검사한다.
- 최종 블록 저장 트랜잭션이 실행 문서와 세션 문서를 함께 읽고 동일 조건을 다시 검사한다.
- 인계 트랜잭션이 같은 세션 문서를 변경하므로 저장과 인계의 충돌은 트랜잭션 재시도 후 새 epoch로 검증된다.
- 업로드 예약 payload 해시에 세션·epoch를 포함하여 인계 전후 동일 요청 ID를 다른 세션으로 재사용하지 못하게 한다.
- 최초 블록 작성자의 세션·epoch를 원본 메타데이터로 보존한다. 동일 내용 재사용 시 원본 작성자 정보는 덮어쓰지 않는다.

인계가 예산 예약 후 완료되면 예약 비용은 남을 수 있지만 이전 세션의 최종 저장은 거부해야 한다. 이는 다음 검증의 필수 기대값이다.

이번 연결 변경은 아직 테스트하지 않았다. 기존 업로드 테스트 호출도 필수 세션 인자를 제공하도록 보완해야 하며 이전 31건 통과를 현재 인터페이스의 통과 결과로 사용하지 않는다. 다음 검증은 세션 누락·다른 탭·이전 epoch의 읽기 전 차단, 스트림 검증 중 인계, 예약 후 인계, 새 세션 재시도·기존 요청 ID 충돌, 기존 회귀 전체다.

경기 manifest/head 커밋·봉인, 실제 모달 Provider writer, IDB 큐, 운영 endpoint는 여전히 미연결이다.

## 블록 저장 세션 연결 재검증

2026-09-08, 위 연결 변경 이후 기존 업로드 테스트 helper에서 명시적으로 세션을 획득하고 필수 세션 ID·epoch를 전달하도록 보완했다. 제품 코드가 세션을 자동 생성하도록 변경한 것은 아니다.

| 구분 | 결과 | 범위 |
|---|---|---|
| 단위 회귀 | 135건 통과, 실패·제외 0건 | 기존 서버 정책·인가·자원·전송·세션 |
| 에뮬레이터 | 37건 통과, 실패·제외 0건 | 기존 31건 + 업로드 세션 경계 6건 |

검증한 새 경계:

- 세션 없음, 다른 탭, 이전 epoch는 스트림 읽기 전에 거부되며 예산·블록을 생성하지 않는다.
- 스트림 읽기 중 인계되면 예산 예약 전에 거부된다.
- 예약 직후 인계되면 예약 예산은 보존되지만 블록 저장은 거부된다.
- 새 세션이 이전 요청 ID를 재사용하면 해시 바인딩 충돌로 거부된다.
- 새 요청 ID로 동일 내용 블록을 재사용할 수 있지만 최초 작성자의 세션·epoch·원본 필드를 덮어쓰지 않는다.
- 실제 동시 업로드·인계는 저장이 인계보다 먼저 확정되거나 이전 세션 저장이 거부되는 두 합법적 결과만 허용한다. 이후 이전 세션의 신규 업로드는 거부한다.

테스트에서 생성된 세션·인계·블록·예약·실행 문서를 로컬 demo 에뮬레이터에서 삭제하고 재조회로 부재를 확인했다. 운영 데이터·외부 네트워크·배포에는 접근하지 않았다. 로그와 요약은 `outputs/server-writer-upload-2026-09-08/`에 보존했다.

이는 비공개 준비 블록의 세션 경계 검증이다. 실제 경기 저장·공개 revision·봉인·IDB 복구의 완료 판정이 아니다. 다음 저장 계층 과제는 불변 manifest와 요청별 커밋 영수증 및 head의 원자적 전환 계약이다. 전체 운영 진입 상태는 계속 `BLOCKED_BEFORE_LOGIN_BACKEND`다.
