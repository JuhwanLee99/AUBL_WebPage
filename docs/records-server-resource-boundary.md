# 서버 호출·업로드 예산과 외부 연결 대상 정책

작성일: 2026-09-08

## 이번 구현

기존 서버 예약 트랜잭션에 자원 예산 계산을 연결했다. `functions/scoring_test_resources.py`는 자원 상태 전이와 외부 연결 대상의 사전 검사를 담당한다.

- 서버 시각을 기준으로 고정 60초 구간의 요청 횟수를 제한한다.
- 기존 서로 다른 요청 수 한도는 유지한다. 같은 요청 재시도는 전체 요청 예산을 다시 차감하지 않지만 구간별 호출 횟수는 소비한다.
- 업로드 예약 바이트를 전체 실행 한도와 대조하고 예약·영수증·카운터를 같은 트랜잭션에 반영한다.
- 동일 요청의 업로드 크기가 바뀌면 충돌로 거부한다. 같은 크기의 재시도는 업로드 예산을 다시 차감하지 않는다.
- 잘못된 카운터, 서버 시각 후퇴, 명세와 전체 요청 한도 불일치를 거부한다.
- 승인 사본이 없는 구형 내부 등록은 업로드 예산을 0으로 제한한다. 분당 요청 상한은 기존 전체 요청 한도를 사용한다. 운영 활성화 허용을 의미하지 않는다.

## 선택한 제한 방식과 보장 범위

고정 시간 구간 카운터를 사용하여 제한 상태의 크기가 요청 횟수에 비례해 증가하지 않게 했다. 경계 직전·직후에는 두 구간의 요청이 짧은 시간에 몰릴 수 있다. 따라서 임의의 연속 60초 동안 항상 같은 상한을 보장하는 sliding-window 제한이라고 표현하지 않는다. 활성화 전 운영 명세에 이 의미를 명시하고 승인해야 한다.

이 제한은 인증·실행·요청 바인딩 검사를 통과한 예약 및 재시도에 적용된다. 거부된 트래픽의 DB 조회나 인증 비용을 차단하는 인프라 rate limiter는 아니다. 외부 endpoint 앞단의 요청 제한은 별도로 필요하다.

업로드 바이트는 **예약 예산**이다. 실제 업로드 endpoint는 아직 없으며 클라이언트가 신고한 바이트를 신뢰해서는 안 된다. 서버가 검증한 불변 업로드 메타데이터의 크기와 실제 스트림 크기 제한을 연결해야 실제 저장·트래픽 예산을 집행할 수 있다. 현재 callable 어댑터는 업로드 크기 필드를 받지 않는다.

업로드 실패 예약의 자동 환불은 하지 않는다. 삭제·환불·재예약을 이용한 한도 우회를 피하도록 후속 정리 계약을 별도로 설계한다.

## 외부 연결 대상 사전 검사

로컬 모드는 명시적으로 승인한 HTTP loopback origin만, 운영 테스트 모드는 서버 설정과 승인 명세가 정확히 일치하는 HTTPS origin만 받는다. URL 누락 시 운영 기본 API로 fallback하지 않는다. 상대 경로에는 다른 호스트, traversal, 인코딩 우회, query 및 fragment를 허용하지 않는다.

이 함수는 URL 검증일 뿐 네트워크 격리가 아니다. 실제 HTTP transport 연결, redirect 비활성화, DNS/IP 제한, 응답 크기·timeout, Functions/NAS 기존 직접 호출 교체는 미완료다. 이 단계에서 실제 외부 호출이나 운영 NAS 연결을 수행하지 않았다.

## 검증 상태 및 다음 작업

최초 후속 검증에서 에뮬레이터 동시성 2건이 실패했다. 이후 제한된 새 트랜잭션 재시도를 적용하여 아래 재검증에서 통과했다. 최초 실패 기록은 보존한다.

다음은 고정 구간 경계·재시도 rate 차감·동시 업로드 예약·예산 초과·URL 우회 입력 단위 테스트와 기존 승인/예약 에뮬레이터 회귀다. 외부 API 공개·실행 활성화·운영 배포는 하지 않으며 전체 상태는 `BLOCKED_BEFORE_LOGIN_BACKEND`를 유지한다.

## 잠금 경합 보완 및 재검증

위 미통과 판정은 최초 실행 시점의 기록이다. 이후 사용자의 수정·재검증 승인으로 `functions/scoring_test_transactions.py`를 추가하고 예약·중단 트랜잭션에 적용했다.

확인한 SDK 구현은 커밋 `Aborted`에 대해 같은 재시도 계열의 트랜잭션 ID를 사용하며 별도 지연 없이 다시 시도한다. 실패 로그에는 커밋 잠금 시간 초과와 5회 시도 소진이 반복되었다. 에뮬레이터 내부 잠금의 정확한 근본 원인까지 확정한 것은 아니다.

수정은 총 시도 수를 5회로 유지하면서 SDK 내부 시도를 1회로 제한하고, rollback 후 짧은 무작위 지연을 거쳐 새 트랜잭션으로 재시도하는 방식이다. 테스트 스레드를 직렬화하거나 동시성 조건을 제거하지 않았다. 서버 상태·권한·예산은 매 시도 다시 읽고 검증한다.

- 직접 발생한 `Aborted` 및 SDK가 `Aborted`를 원인으로 감싼 `ValueError`만 재시도한다.
- 권한·명세·예산 오류와 일반 입력 오류는 재시도하지 않는다.
- 커밋 성공 여부가 불확실한 deadline 오류는 자동 재시도하지 않는다. 상위 요청 계층의 동일 ID 복구 계약이 필요하다.
- 지연은 트랜잭션 밖에서 수행한다. 최종 실패는 숨기거나 성공으로 바꾸지 않고 그대로 반환한다.

재검증 결과:

| 검증 | 결과 |
|---|---|
| 정책·어댑터·자원·재시도 단위 | 97건 통과, 실패·제외 0건 |
| 승인·예약·자원 에뮬레이터 | 17건 통과, 실패·제외 0건 |

이전에 실패한 동일 요청 동시 재시도 및 동시 업로드 예약도 포함한다. 테스트 데이터 삭제·부재 확인은 에뮬레이터 테스트 정리 절차에서 통과했다. 운영 접근·배포는 수행하지 않았다.

재검증 로그는 `outputs/server-resource-boundary-retry-2026-09-08/`에 별도로 보관한다. 한 차례의 통과를 운영 부하·장기 반복 안정성의 증거로 확대하지 않는다. 실제 HTTP transport, DNS/IP·redirect 통제, 업로드 스트림 크기 제한, endpoint 인증과 활성화 계약은 계속 남아 있으며 전체 운영 진입 상태는 `BLOCKED_BEFORE_LOGIN_BACKEND`다.
