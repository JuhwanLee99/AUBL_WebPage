## 2. 구현 범위

- 관리자 화면에 실행 ID, 마지막 갱신, 중단 사유, 확인 체크박스, 중단 요청과 같은 요청 재확인 버튼을 추가했다.
- 5분 이상 미갱신은 경고로만 표시한다. 시간 경과를 실제 워커 중단 증거로 사용하지 않는다.
- 관리자 전용 `GET /api/admin/sync/unique-play/runs/{runId}/cancellation`으로 지원 설정과 기존 중단 요청을 조회한다.
- 관리자 전용 `POST /api/admin/sync/unique-play/runs/{runId}/cancel`로 중단을 요청한다.
- 내부 워커 `POST /runs/{runId}/cancel`을 추가했다. 기존 서비스 토큰 인증을 그대로 적용한다.
- 최초 요청은 실행 ID·상태·마지막 갱신 시각을 확인한다. 중단 사유는 8~500자이며 요청 ID는 UUID다.
- 이미 서버에 후보가 저장됐거나 게시된 실행은 거부한다. 검토·검증·게시·활성화 단계의 취소는 이번 기능 범위가 아니다.

## 3. 상태만 바꾸지 않는 이유와 처리 순서

### 대안 비교

| 방식 | 문제점 또는 선택 이유 |
| --- | --- |
| 실행 행 삭제 | 감사 이력과 원인 조사 근거가 사라지며, 실행 중인 수집이나 늦은 콜백은 멈추지 않는다. 제외. |
| DB 상태만 즉시 종료 | 워커가 계속 수집할 수 있고 새 수집과 충돌한다. 종료 표시와 실제 동작이 달라진다. 제외. |
| HTTP 요청만 취소 | 브라우저 수집과 이미 서버에 도착한 요청의 처리를 보장하지 못한다. 단독 사용 제외. |
| DB 행 잠금 중 워커 종료 대기 | 워커가 보내던 콜백이 같은 DB 잠금을 기다리면 종료 확인이 지연될 수 있다. 제외. |
| DB 반영 차단 커밋 후 워커 종료 확인, 최종 종료 커밋 | 요청 이력·재시도·늦은 콜백 차단을 보존하면서 네트워크 대기에 DB 행 잠금을 유지하지 않는다. 선택. |

### 실제 구현 계약

1. 지원 프로토콜을 확인한다. 최초 요청 전에 워커가 영속 프로토콜 2와 중단 프로토콜 1을 지원하는지 확인한다.
2. 첫 번째 DB 트랜잭션에서 실행 행을 잠그고 동시 변경을 검사한다. `CANCEL_REQUESTED`와 `CANCELLING` 진행 단계를 기록하고 중단 영수증을 함께 커밋한다.
3. 이 시점에는 기존 QUEUED/RUNNING 상태를 유지한다. 기존 활성 실행 차단 정책을 유지해 중단 확인 전 새 수집을 시작하지 않도록 한다. 화면은 오류 코드에 따라 중단 확인 중임을 별도로 설명한다.
4. 영속 콜백 경로는 `CANCEL_REQUESTED` 이후 새로운 progress/candidate/failed를 거부한다. 이전에 확정된 동일 영수증의 ACK 재조회는 데이터 재반영 없이 허용한다.
5. DB 잠금을 해제한 뒤 워커에 중단을 요청한다. 워커는 먼저 CANCELLING 상태를 디스크에 보관하고 수집의 AbortSignal, 브라우저 종료, 콜백 전송 및 재시도 대기를 중단한다.
6. 실제 수집과 전송 작업이 빠져나온 뒤 FENCED 상태를 영속 저장한다. 종료 확인의 제한 시간을 넘기거나 브라우저 종료가 확인되지 않으면 성공 증거를 반환하지 않는다.
7. 백엔드는 실행 ID·중단 요청 ID·프로토콜·fenced·stopped가 모두 일치하는 응답을 받은 후 두 번째 DB 트랜잭션에서 CANCELED / ADMIN_CANCELLED로 확정한다.
8. 공식 리비전과 기존 경기 기록을 변경하지 않는다. 실행과 영수증, 워커에 남은 미확정 전송 자료는 삭제하지 않는다.

## 4. 응답 유실·재접속·경합 정책

- 첫 DB 커밋 이후 워커 호출에 실패하면 CANCEL_REQUESTED를 유지한다. 중단 실패를 이유로 결과 반영 차단을 자동 해제하지 않는다.
- 워커 종료 응답 유실 또는 마지막 DB 커밋 실패는 같은 cancellationId로 다시 확인한다. 실제 종료 전에 완료라고 표시하지 않는다.
- 기존 중단 요청 ID와 사유는 서버에서 다시 조회할 수 있다. 새로고침이나 다른 관리자 접속 후에도 해당 요청을 이어서 확인한다. 원래 영수증의 요청자는 바꾸지 않는다.
- 최초 요청의 expectedStatus/expectedUpdatedAt은 동시 변경 방지용이다. 같은 요청 재시도에서는 실행 ID·중단 ID·사유의 지문을 비교하고 현재 중단 상태를 확인한다.
- 중단 ID를 재사용하면서 다른 실행이나 사유를 보내면 거부한다. 다른 ID로 기존 중단 요청을 덮어쓰지 않는다.
- 중단이 저장된 워커가 재시작되면 수집이나 콜백을 재개하지 않는다. 이전 프로세스가 종료됐다는 단일 워커 소유 조건에서 FENCED로 마무리한다.
- 최초 디스크 접수 중이면 중단을 즉시 성공시키지 않고 RUN_BUSY로 재확인을 요구한다.
- 서버에 이미 저장된 후보와 공식본은 중단할 수 없다. 서버에 도착하지 않은 워커 대기 후보는 중단 시 디스크에 보존하되 이후 전송하지 않는다.
- 기존 inactive-only 복구와 새 중단 요청이 서로 덮어쓰지 않도록 복구 경로에도 CANCEL_REQUESTED 거부 조건을 추가했다.

## 5. 운영 적용 전제와 남은 작업

현재 운영은 새 백엔드 및 워커 기능 배포 전이다. 버튼을 프런트엔드에만 배포해도 기존 운영 실행을 안전하게 종료할 수 없다.

- 중단 기능은 `uniqueplay.require-durable-callbacks=true`일 때만 허용한다. 기본값 false는 유지했다. 구형 콜백이 열려 있으면 새 중단 차단 조건을 우회할 수 있으므로 자동 폴백은 없다.
- 새 백엔드의 V8 영수증 테이블, 새 워커 이미지, `SYNC_STATE_DIR` 영속 볼륨 및 쓰기 권한이 필요하다.
- 워커 상태 디렉터리 하나는 프로세스 하나가 소유한다. 구형 워커가 동시에 살아 있는 상황에서는 새 워커의 ABSENT 응답을 이전 작업 종료 증거로 사용하면 안 된다.
- 운영 배포 전에 최신 백업과 롤백 계획을 확보하고 기존 CORS·인증·DB 연결 설정을 보존한다.
- TrueNAS 저장 앱 설정과 Portainer 런타임 설정의 차이가 남아 있다. 재배포로 구형 이미지와 설정이 되돌아올 위험은 별도로 통제해야 한다.
- 검증 후 지원 버전을 배포하고 구형 콜백을 차단한 다음, 위 대상 실행의 최신 상태를 다시 확인해 중단한다.
- 종료 후 CANCELED, 활성 실행 해제, 기존 공식 리비전 유지, 늦은 콜백 차단을 확인한다. 이 확인 전까지 운영 실행 정리 완료로 보고하지 않는다.
- 이번 중단 작업은 신규 재수집·후보 게시·공식 활성화나 A조 순위 정정을 포함하지 않는다.

## 6. 검증 현황 및 승인 후 확인할 사례

후속 배포 준비에서 타입 검사, 워커 130건, 중단 화면 16건, 기존 증분 수집 화면 8건이 통과했다. 실제 DB 검증과 배포 빌드는 아래 수정 승인 이후 진행해야 한다. 이전 영속 저장 검증의 백엔드 69건 통과는 이번 변경의 검증 결과가 아니다.

| 검증 영역 | 필요한 확인 |
| --- | --- |
| 권한 | 익명 401, 비관리자 403, 관리자만 조회·중단 가능 |
| 미지원 배포 | 구형 워커, 비활성 영속 콜백, API 404에서 DB를 임의 종료하지 않음 |
| 정상 수집 중단 | 브라우저 종료 및 active/draining 해제 후에만 성공 |
| CONNECTING 정리 | 대상 실행만 종료하고 원래 run ID·사유·공식본 유지 |
| 최초 접수 경합 | 디스크 접수 중 중단·재요청에서 거짓 ACK와 수집 재시작 없음 |
| 지연 콜백 | 취소 차단 커밋 이후 progress/candidate/failed의 신규 반영 거부 |
| 후보 경합 | 후보 DB 커밋이 먼저면 중단 거부, 중단 차단이 먼저면 후보 반영 거부 |
| 전송 대기 | HTTP 대기와 재시도 지연을 실제로 중단하고 이후 재전송하지 않음 |
| 두 DB 커밋 | 최초 영수증 실패 시 차단도 롤백, 최종 커밋 실패 시 같은 ID로 복구 |
| 응답 유실 | 종료 응답을 잃어도 같은 요청을 재확인해 중복 이력 생성 없음 |
| 브라우저 종료 실패 | CANCELED로 오판하지 않고 운영자 확인 필요 상태 유지 |
| 프로세스 재시작 | CANCELLING/FENCED 실행의 자동 수집·콜백 재개 없음 |
| 관리자 재접속 | 서버에 남은 요청 ID와 사유로 이어서 확인 가능 |
| 화면 경합 | 더블 클릭, 폴링, 다른 실행 불러오기에서 잘못된 대상 중단이나 오래된 상태 덮어쓰기 없음 |
| 범위 보호 | 검토·게시·활성·공식 데이터는 취소 대상으로 처리하지 않음 |

필수 검증이 통과하기 전에는 운영의 해당 실행이 정리됐다고 판정하지 않는다.

## 7. 후속 배포 준비 실행 결과

사용자가 배포 전 필요한 작업과 운영 배포 진행을 요청했다. 현재까지 실행한 결과는 다음과 같다.

| 실행 | 결과 | 증거 |
| --- | --- | --- |
| 프런트엔드 타입 검사 | 통과 | `evidence/uniqueplay-cancellation-2026-09-13/typecheck.log` |
| 기존 워커 및 새 중단 단위 테스트 | 130건 통과, 실패·제외 0건 | `evidence/uniqueplay-cancellation-2026-09-13/worker.tap` |
| 관리자 중단 화면 | PC·모바일 16개 시나리오 통과 | `evidence/uniqueplay-cancellation-2026-09-13/cancellation-ui-results.json` |
| 기존 증분 수집 화면 회귀 | PC·모바일 8개 확인 통과 | `evidence/uniqueplay-cancellation-2026-09-13/scope-ui.log` |

첫 중단 화면 테스트 실행은 로컬 포트 바인딩이 샌드박스에서 거부되어 시작하지 못했다. 로컬 실행 권한을 승인받아 다시 실행했고 16개 시나리오가 통과했다. 화면 테스트의 모든 외부 요청은 차단했으며 실제 운영 API에 쓰지 않았다. HTTP 503과 잘못된 ACK를 이용한 실패·재확인 시나리오는 하네스 모의 응답이며 실제 운영 장애 복구 결과로 계산하지 않는다.

### 발견하여 수정 승인 요청한 두 항목

1. `UniquePlayCancellationService.control()`이 `getDeliveryId()`를 사용하지만 실제 영수증 엔티티의 접근자는 `getId()`다. 실제 DB 테스트 전에 컴파일 오류를 수정해야 한다.
2. 새 `test-uniqueplay-cancellation-integration.sh`의 Gradle 명령은 `test bootJar ... --tests` 순서여서 테스트 필터가 bootJar에 붙을 수 있다. 필터를 test에 적용한 뒤 bootJar를 실행하도록 순서를 조정해야 한다.

두 항목의 수정은 승인 대기이며 이 결과를 숨기거나 테스트 제외로 우회하지 않았다. 새 DB 검증 스크립트는 운영 연결 정보 없이 내부 Docker 네트워크와 전용 `cancellation_jpa` 등 일회용 스키마만 사용하도록 작성했다. 아직 이 스크립트로 컨테이너를 실행하지 않았다.

### 운영 사전 관찰

Portainer 관리자 세션으로 컨테이너 목록에 접근했다. 다음 운영 이미지를 확인했으며 교체·재시작은 하지 않았다.

- 백엔드: `synapse9983/aubl-backend:incremental-20260912-ea0b89d7740e`
- 워커: `synapse9983/aubl-uniqueplay-sync-worker:incremental-20260912-101af1ec62df`

다음 순서는 수정 승인, 실제 DB 검증 및 배포 빌드, 새 NAS 백업, 영속 볼륨 준비, 백엔드·워커·Hosting의 순차 배포, 운영 상태 확인, 지정 실행의 이력 보존 중단이다. 신규 수집·게시·공식 활성화는 자동으로 이어서 실행하지 않는다.
