# UniquePlay 증분 동기화 배포·백업·복구 실행서

작성일: 2026-09-12. 상태: **절차 수립 완료 / 실행 명세 미완성 / 운영 실행 미승인**.

이 문서는 이미 통과한 로컬 검증을 실제 운영 성공으로 확대 해석하지 않는다. 이번 작성 단계에서는 운영 조회, 백업 생성, Docker push, 배포, 수집·게시·활성화, 추가 테스트를 실행하지 않았다. 아래 절차는 실행 승인을 요청할 때 사용할 명세이며 현재 승인 자체가 아니다.

## 1. 범위와 기준 문서

- 목표는 기존 기록을 보존하는 UniquePlay 증분 동기화의 제한 도입이다. 실시간 기록 엔진 전체의 운영 승인이나 AUBL 규칙 프로파일 승인과 구분한다.
- 자체 기록은 실시간 참고 원천이고 UniquePlay는 최종 공식 원천이라는 정책을 유지한다. 배포 실패를 이유로 자체 기록을 공식 원천으로 전환하지 않는다.
- [기존 출시 준비 현황](./uniqueplay-incremental-release-readiness-2026-09-12.md), [워커 후보 이미지 명세](./uniqueplay-worker-candidate-2026-09-12.md), [워커 후보 검증 결과](./uniqueplay-worker-candidate-verification-2026-09-12.md)를 근거로 한다.
- 실제 실행값은 [실행 명세 JSON](./uniqueplay-incremental-execution-manifest-2026-09-12.json)에 기입한다. `null`과 `false` 승인 항목이 남은 상태로 시작하지 않는다. JSON은 실행 도구나 자동 승인기가 아니다.
- 확인된 과거 상태와 다음 실행의 예상값을 구분한다. 운영 상태는 배포 직전 승인된 읽기 전용 확인으로 다시 고정해야 한다.

## 2. 배포 대상 조합

| 대상 | 마지막 확인 또는 저장소 근거 | 이번 후보 | 남은 확정 사항 |
|---|---|---|---|
| 백엔드 | `synapse9983/aubl-backend:v25`, Portainer 환경 3 | 로컬 `aubl-backend:incremental-20260912-candidate` | 최종 registry 태그·digest, NAS 적용 이미지, 재현 원본 식별 |
| 워커 | `synapse9983/aubl-uniqueplay-sync-worker:v13`, 어댑터 `2026.09.05.13` | 로컬 `aubl-uniqueplay-sync-worker:incremental-20260912-candidate`, 어댑터 `2026.09.12.14` | 최종 registry 태그·digest와 NAS 반입 승인 |
| DB | `mariadb:11.8.5`, `lower_case_table_names=0` | DB 이미지는 유지, 새 백엔드의 V7 적용 | 실제 DB명, 현재 Flyway 이력·체크섬, 백업·복원 증거 |
| 웹 | Firebase 프로젝트·Hosting 사이트 `aubl-backup`, 공개 도메인 `aubl.club` | 로컬 전체 웹 후보 빌드 완료, Hosting 파일 47개·해시 고정 | 전체 웹 변경 범위 승인·최종 번들 검증·CI 대상 통일·Hosting version/release ID |

백엔드 로컬 후보의 이전 빌드 manifest는 `sha256:ea0b89d7740e3a3f1a2592eecfb360e3d49314a0ed6e1381b3c58f96b959b62d`다. 워커 후보 manifest는 `sha256:101af1ec62df94924e91ffd1d91878afec799da4231f1cf3cd3121614f15ed46`이며, 이번 격리 실행에서 Docker 이미지 ID도 이 값으로 확인됐다. 워커 config digest `sha256:9b8f1864c4604f6c1dd6efe346ad64f79433c0938f88e94c2d43e770c4a9d86f`와 혼동하지 않는다. 백엔드 Docker ID가 어떤 형식인지 이번 문서 작업에서는 추가 확인하지 않았다.

registry가 반환한 index/manifest digest, 대상 플랫폼 manifest, 로컬 config digest는 별개로 기록한다. 로컬 태그나 config digest를 registry 배포 주소라고 간주하지 않는다. 승인 후 검증한 산출물을 올리고 NAS에서 같은 대상 플랫폼 산출물인지 대조한다. `latest`, 기존 `v25`·`v13` 덮어쓰기, 검증 후 무기록 재빌드는 금지한다.

다음은 배포 대상이 아니다: `aubl-backend:full-flow-test-20260912`, `aubl-auth-emulator:15.17.0`, 임시 MariaDB·Firestore, 테스트 자료, Flutter, Firebase Functions·Rules·Indexes·Storage·Realtime Database 설정. 웹 배포는 Hosting으로 한정한다. `.firebaserc`의 Hosting 프로젝트를 운영 백엔드 서비스 계정의 Auth·Firestore 프로젝트 ID로 추정하지 않는다.

## 3. 확인된 검증과 미확인 경계

| 근거 | 확인한 범위 | 확인하지 않은 범위 |
|---|---|---|

| 웹 모드·시작일 UI 8건 | 로컬 응답 기반 모드 선택·날짜 입력·오류·폴백 차단 | 최종 Hosting 번들 및 실제 운영 로그인·모바일 |

전체 흐름의 1개 테스트 메서드 안에 두 수집 회차가 있다. 이를 독립 테스트 두 건이나 실제 경기 회귀로 세지 않는다. 이전 테스트와 이번 121건의 중복 커버리지를 단순 합산해 별도 승인 지표로 쓰지 않는다.

## 4. 설정 보존과 신규 작업 차단

| 구분 | 반드시 보존·대조할 항목 |
|---|---|
| 백엔드 | DB 대상·계정 참조, Firebase 자격 증명 마운트와 대상 프로젝트, CORS, 워커 URL·토큰, 네트워크·포트·볼륨·재시작 정책 |
| DB 이름 규칙 | `SPRING_JPA_HIBERNATE_NAMING_PHYSICAL_STRATEGY=org.hibernate.boot.model.naming.PhysicalNamingStrategyStandardImpl` |
| 워커 | `SYNC_SERVICE_TOKEN`, `SYNC_BACKEND_CALLBACK_URL`, 암호화 세션·키의 기존 보관 방식, 리그·시즌, 네트워크·포트·재시작 정책 |
| 운영에서 제외 | `FIREBASE_AUTH_EMULATOR_HOST`, `FIRESTORE_EMULATOR_HOST`, `AUBL_SCOPED_DB_HOST`, fixture 토큰·계정·프로젝트 |
| CI | 기존 `.github/workflows/firebase-hosting-merge.yml` 및 PR workflow의 트리거·배포 대상·승인 경계 |

민감한 설정은 승인된 비밀 저장소에 보존하고 문서에는 키 이름·참조 ID·대조 결과만 남긴다. Portainer 전체 환경 변수를 로그나 Git에 복사하지 않는다. 후속 소스 확인에서 Hosting merge workflow는 main push로 실행되고 Firebase 설정은 aubl-backup, 배포 대상은 aubl-web-9a141인 불일치를 확인했다. 외부 저장소 보호 정책·secret 내용은 미확인이다. 승인 전에 대상과 실행 경계를 정리하고 현재 main push/merge를 이번 후보의 배포 수단으로 사용하지 않는다.

배포 중에는 서버 또는 프록시 등 검증 가능한 위치에서 신규 수집·재검증·정정·게시·활성화 쓰기를 차단한다. 버튼 숨김이나 담당자 구두 합의만으로 차단 완료를 판정하지 않는다. 이 차단 수단은 현재 구현·설정 여부가 미확정이며 배포 진입 조건이다.

기존 진행 작업의 콜백까지 먼저 막으면 실행이 미완료로 남을 수 있다. 신규 진입만 우선 차단하고 기존 작업·콜백이 끝난 뒤 다음 단계로 간다. 강제 종료가 필요하면 해당 run ID와 상태·재시도 방침을 별도로 승인한다. 워커의 메모리 내 중복 실행 집합은 재시작 후 복구되지 않으므로 재시작을 실행 취소·완료 증거로 사용하지 않는다.

## 5. 배포 순서와 각 단계의 통과 조건

| 순서 | 작업 | 다음 단계 조건 |
|---|---|---|
| 0 | 실행 담당자·시간·중단 책임자·프로젝트·계정·범위를 확정하고 사용자 승인 확보 | 실행 명세 필수값 누락 없음, 허용 작업별 승인 있음 |
| 1 | 최종 웹 산출물 준비, 승인된 이미지 push와 NAS 사전 반입 | 세 산출물 식별 고정, 기존 이미지·Hosting version 복구 가능 |
| 2 | 신규 쓰기 차단, 기존 실행 drain, 활성 공식 리비전·체크섬·수집 시각 기록 | 진행 중 작업 0, 백업 기준점 고정 |
| 3 | DB·설정·공식 투영 백업과 복원 가능성 확인 | 아래 백업 매트릭스 충족, 미검증 백업을 성공으로 표기하지 않음 |
| 4 | 새 백엔드만 교체하고 V7 적용 | Flyway 이력·기동·인증·읽기 조회 정상, 기존 공식 리비전 불변 |
| 5 | 새 워커 교체 | 어댑터 버전·인증·백엔드 연결·세션 상태 확인, 자동 수집 시작 없음 |
| 6 | 마지막에 새 웹을 Hosting에 배포 | 확정된 bundle/version 일치, 날짜 입력·오류 표시·기존 조회 확인 |
| 7 | 지정 운영자에게만 제한 수집 허용 | 실행별 원천·시즌·모드·시작일·호출 한도 승인, 공개 전환은 계속 차단 |
| 8 | 후보 검토 후 별도 게시·활성화 승인 | 범위 전 기록 보존·중복 없음·체크섬·기준 리비전 재확인 |
| 9 | 관찰 기간 후 확대 또는 중단 | 데이터·권한·공식 원천 혼입 결함 없음, 사용자 별도 승인 |

백엔드는 먼저 scope 검증·병합 계약을 제공하고, 워커는 그 계약을 지킨 결과만 보낸다. 웹을 마지막에 배포하는 이유는 새 사용자가 아직 준비되지 않은 서버에 scoped 요청을 보내는 기간을 줄이기 위해서다. 중간 조합에서 실제 수집을 허용하지 않는다.

| 조합 | 판정 |
|---|---|
| 기존 웹 + v25 + v13 | 기존 운영 기준선. 증분 기능 제공 조합이 아님 |
| 기존 웹 + 신규 백엔드 + 기존/신규 워커 | 교체 중 일시 상태. 구형 웹이 legacy 수집을 시작하지 못하도록 쓰기 차단 유지 |
| 신규 웹 + v25 + 어느 워커 | scoped API 미지원. 오류를 표시하고 legacy API로 자동 폴백하지 않음 |
| 신규 웹 + 신규 백엔드 + v13 | 배포 완료로 보지 않음. scoped 콜백 계약을 운영 v13이 충족한다고 가정하지 않음 |
| 신규 웹 + 신규 백엔드 + 신규 워커 | 목표 조합. 세 이미지/번들만 갖춰졌다고 운영 검증 완료가 되는 것은 아님 |

백엔드 새 버전의 health가 정상이어도 신규 쓰기 차단을 해제하지 않는다. 실제 세션 확인은 읽기 확인이고, `/collect`는 네트워크 수집과 서버 상태 생성을 유발하는 별도 승인 작업이다.

## 6. 백업 범위와 완료 조건

| 백업 | 포함 대상 | 완료 증거 |
|---|---|---|
| MariaDB 애플리케이션 DB | 실행 원본·유효 후보·리비전·매핑·수동 정정·경기·기록·Flyway 이력 등 해당 DB 전체 | 정확한 DB명, 기준 시각, 도구 버전, 종료 코드, 암호화 보관 URI, checksum, 복원 결과 |
| Firestore | 공식 투영·메타데이터 및 복구에 필요한 자체 원본의 실제 컬렉션 목록 | 프로젝트·database ID, 포함 범위, 완료 operation, 보관 위치, 기준 리비전, 복구 대조 결과 |
| 실행 설정 | 기존 백엔드·워커 이미지 digest, 네트워크·포트·마운트·정책, 비밀 설정 참조 | 재생성 명세와 접근 가능한 이전 산출물. 비밀 값은 보호된 별도 저장소 |
| 웹 | 배포 전 live Hosting version/release 및 신규 번들 | 이전 version이 보존됨, 신규 산출물 hash와 배포 대상, 복귀 담당자 |
| 사고 증거 | 실행별 요청 ID, scope, 기준/신규 revision, checksum, 변경·판정 로그 | 개인정보·토큰을 제외한 접근 제한 증거 위치와 보관 기한 |

DB 논리 백업은 대상 테이블이 모두 InnoDB이고 관련 DDL이 멈춰 있는 경우 `mariadb-dump`의 `--single-transaction --quick`을 사용하도록 계획한다. 비트랜잭션 테이블이나 백업 중 DDL이 있으면 같은 일관성을 보장하지 못한다. 루틴·이벤트 등 추가 객체도 포함 범위를 정해야 한다. 복원 도구는 덤프 형식과 호환되는 MariaDB 버전을 사용한다. [MariaDB 공식 mariadb-dump 문서](https://mariadb.com/docs/server/clients-and-utilities/backup-restore-and-import-clients/mariadb-dump)

대상 미확정 상태에서 실행 가능한 운영 dump 명령은 만들지 않는다. 다음 조건을 먼저 충족한다.

1. DB명·서버·테이블 엔진·dump 권한·보관 용량을 승인된 읽기 확인으로 고정한다. NAS의 다른 DB를 임의로 포함하지 않는다.
2. 관련 DDL·동기화 게시 쓰기를 멈춘 뒤 백업한다. 다른 애플리케이션 쓰기의 허용 여부와 복구 시 보존 방법도 정한다.
3. 종료 코드 0과 checksum만으로 복원 가능하다고 판정하지 않는다. 같은 MariaDB 버전의 외부망 없는 별도 인스턴스에 복원하고 이력·원본·리비전·집계 및 필요한 관계를 대조한다.
4. 운영 원본을 복원 시험에 사용하려면 개인정보·접근 권한·보관·삭제 승인도 받는다. 운영 DB에 시험 복원을 하지 않는다.
5. 이번 로컬 합성 DB 검증은 운영 백업의 복원 시험을 대신하지 않는다. 시험 소요 시간으로 복구 목표시간을 합의한다.

Firestore export는 진행 중 변경을 포함할 수 있으며 export 시작 순간의 정확한 스냅샷으로 간주할 수 없다. 따라서 MariaDB와 같은 시각에 명령을 실행했다는 사실만으로 두 저장소가 같은 공식 리비전이라고 판단하지 않는다. 관련 쓰기를 통제하고 전후 기준 리비전을 대조하는 것을 이 서비스의 추가 운영 조건으로 둔다. export 대상·비용·권한·보관 위치와 자체 원본 포함 범위는 아직 미확정이다. [Firebase 공식 export/import 문서](https://firebase.google.com/docs/firestore/manage-data/export-import)

Hosting은 보존된 이전 live version으로 롤백할 수 있지만 해당 version의 콘텐츠가 남아 있어야 한다. 배포 전에 정확한 version/release를 고정하고 보존 정책을 확인한다. 웹만 복귀해도 MariaDB·Firestore 데이터는 복구되지 않는다. [Firebase Hosting 공식 릴리스·롤백 문서](https://firebase.google.com/docs/hosting/manage-hosting-resources)

## 7. 중단 기준

- 범위 밖 경기 변경·삭제, 이전 상세 유실, 중복 원천 ID 또는 경기 생성.
- 활성 revision·checksum의 예기치 않은 변경, API와 Firestore의 공식 기준 불일치.
- 새 웹의 legacy 수집 자동 폴백, 범위 미지원 워커의 결과 수용.
- 인증·권한 우회, 비관리자 원본 노출, 테스트·자체 기록의 공식 통계 혼입.
- 승인되지 않은 API·프로젝트·DB 접근, 예상하지 않은 마이그레이션 또는 설정 변경.
- 백업 실패·미완성, 롤백 산출물 부재, 허용 시간·호출 한도 초과.

한 번이라도 발생하면 신규 쓰기를 차단하고 증거를 보존한다. 반복 재시도·재수집·다른 시작일·전체 수집 전환으로 오류를 숨기지 않는다. 읽기 정합성이 불확실하면 정상으로 표시하지 않고 영향 범위를 격리한다. 정상적인 다른 원천까지 임의로 덮어쓰지 않는다.

## 8. 복구 의사결정

| 장애 지점 | 우선 조치 | 허용하지 않는 단축 처리 |
|---|---|---|
| 웹 기능 오류, 데이터 불변 | 쓰기 차단 상태에서 이전 Hosting version 복귀. 새 백엔드는 유지 가능 | 웹 롤백만으로 DB도 복구됐다고 선언 |
| 워커 오류, 게시·활성화 전 | 해당 run 중단·증거 보존, 이전 워커 이미지 복귀 가능. 새 scoped 요청은 계속 차단 | 구형 워커로 전체 수집을 자동 재시도 |
| 새 백엔드 기동 실패, V7 미적용 | 실제 스키마 상태를 확인하고 이전 이미지·설정으로 복귀 | 기동 실패만 보고 V7이 전혀 실행되지 않았다고 단정 |
| V7 적용 후 백엔드 오류 | 검증된 V7+v25 호환 복귀 또는 새 수정 버전 전진 배포 | V7 컬럼 삭제·Flyway 이력 삭제·임의 repair로 강제 기동 |
| 후보 저장 후, 공개 전환 전 | 기준 공식본 유지, 실패 run과 원본 보존 | 원본 후보 덮어쓰기·시즌 전체 삭제 |
| 게시·활성화 중 또는 이후 | 두 저장소 상태와 후속 쓰기를 확인하고 검증된 애플리케이션 복구 경로로 동일 공식본 재구성 | MariaDB 포인터 또는 Firestore 메타데이터만 수동 변경 |
| 데이터 손상으로 백업 복원 필요 | 전체 영향과 백업 이후 쓰기를 파악하고 별도 승인된 복구 실행 | 동기화 장애를 이유로 운영 DB 전체를 즉시 과거 덤프로 덮어쓰기 |

V7은 새 nullable 범위 컬럼을 도입하지만, 이것만으로 기존 v25의 호환성을 추정하지 않는다. 2026-09-12 후속 시험에서 **합성 V7 DB의 신규 후보 → v25 → 신규 후보 읽기 왕복 검증을 통과했다.** 실제 이미지의 기동·관리자 조회와 DB·공식 투영 보존을 확인했다. [검증 결과](./uniqueplay-v25-v7-rollback-verification-2026-09-12.md)를 근거로 신규 쓰기를 차단한 읽기 복귀를 검토할 수 있으며, 구형 수집·정정·게시 허용 또는 운영 데이터 복구까지 보장하지 않는다. 운영에서 전제 조건이 다르면 자동 롤백 대신 별도 판단한다.

적용된 versioned migration은 이력과 checksum으로 관리된다. 이미 적용한 파일을 바꾸거나 이력을 지우는 대신 신규 migration으로 전진 수정하는 것을 기본 방향으로 둔다. 실제 V7 실패 상태에서의 조치는 스키마·이력을 확인한 후 별도 결정한다. [Flyway 공식 versioned migrations 문서](https://documentation.red-gate.com/flyway/flyway-concepts/migrations/versioned-migrations)

공식 리비전 복구는 이미지 롤백과 다르다. 기대 리비전과 현재 리비전을 비교하고 동시 쓰기를 막은 상태에서, 원본 및 수동 정정의 보존과 MariaDB·Firestore 투영의 일치를 확인해야 한다. 기존 리비전 재활성화가 실제 코드에서 허용되는지와 그 경로의 복구 시험 결과는 아직 미확정이다. 메타데이터 값 하나를 SQL 또는 콘솔로 바꾸는 방법을 대체 절차로 제공하지 않는다.

전체 DB 복원은 동기화와 무관한 백업 이후 기록까지 잃을 수 있다. DB 전반의 쓰기 중단·차이 보존·검증된 재적용 계획 없이 수행하지 않는다. binlog/PITR의 활성 여부와 복구 시험이 확인되지 않았으므로 RPO 0이나 특정 RTO를 보장하지 않는다. 복구 허용 손실과 시간은 실행 명세에서 담당자가 확정해야 한다.

## 9. 제한 수집과 공식 전환의 별도 승인

1. 첫 운영 수집은 실행 1건으로 제한하는 안을 제시한다. 원천 리그·시즌·모드·시작일·상세 방문 예상량·최대 소요 시간은 사전 승인받는다. 이 제한은 현재 자동 강제 기능이 있다고 주장하는 것이 아니라 실행 명세의 조건이다.
2. 자동 모드의 기준은 활성 공식 스냅샷의 수집 시각에서 정한 KST 날짜다. 웹의 게시 시각·마지막 실패 시각·수집 완료 시각과 혼동하지 않는다. 경계 날짜는 포함하며 날짜 이전 정정·지연 상세는 더 이른 시작일을 명시해야 한다.
3. 시작일 지정은 상세 방문만 줄이며 일정·순위·시즌 누적은 여전히 전체 수집한다. 짧은 날짜 범위라고 사이트 호출량 전체가 작다고 가정하지 않는다.
4. 수집 승인은 서버 run·후보·진행 상태 저장을 포함하되 게시·활성화 승인을 포함하지 않는다. 실제 DB 저장 영향이 없는 읽기 전용 작업이라고 표현하지 않는다.
5. 범위 전 게임·상세 보존, 범위 내 변경, 누적 통계, 중복 ID, 원본·유효 후보 체크섬, 검수 경고를 검토한다. 기준 리비전이 달라지면 재검토하고 자동 덮어쓰지 않는다.
6. 후보 승인 후에도 게시·활성화는 별도 확인한다. 이미 게시된 공식 원본이나 시즌 전체를 테스트 결과로 수정하지 않는다. 실시간 기록 엔진의 운영 테스트 namespace 정책을 일반 시즌 수집에 자동 적용됐다고 간주하지 않는다.
7. 임시 run·계정·권한 정리 범위는 생성된 ID로 특정한다. 보존해야 할 감사 원본이나 기존 자료를 포괄 삭제하지 않는다. 삭제 실패 시 쓰기 차단과 비공개 상태를 유지한다.
