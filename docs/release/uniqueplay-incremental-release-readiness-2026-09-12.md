# UniquePlay 날짜 범위 동기화 배포 준비

## 현재 판정

운영 배포 미승인. 이 문서는 실행 명세 초안이며 배포·운영 DB 변경 권한을 부여하지 않는다.
검증 이력은 `docs/uniqueplay-incremental-sync.md`에 유지한다. 아래 미확인 항목을 생략해 완료 처리하지 않는다.

## 현재 운영 및 후보

| 구성 요소 | 확인된 운영 상태 | 배포 후보 상태 |
| --- | --- | --- |
| 백엔드 | synapse9983/aubl-backend:v25 | 로컬 incremental-20260912-http 이미지, 미업로드 |
| 워커 | synapse9983/aubl-uniqueplay-sync-worker:v13 | 범위 지원 소스만 변경됨. 새 릴리스 이미지 빌드·검증 필요 |
| DB | MariaDB 11.8.5, lower_case_table_names=0 | V7 신규 적용 필요. 운영 이력 재확인 필요 |
| 웹 | 신규 날짜 범위 화면 미배포 | 로컬 PC·모바일 viewport E2E 통과 |

백엔드 후보 manifest: `sha256:ea0b89d7740e3a3f1a2592eecfb360e3d49314a0ed6e1381b3c58f96b959b62d`.
`isolated-db-test` 및 `full-flow-test` 이미지는 테스트 소스·Gradle을 포함하므로 운영에 배포하지 않는다.

## 반드시 보존할 실행 계약

- 운영 명명 전략: `SPRING_JPA_HIBERNATE_NAMING_PHYSICAL_STRATEGY=org.hibernate.boot.model.naming.PhysicalNamingStrategyStandardImpl`.
- 운영 DB의 대소문자 설정은 변경하지 않는다. 테스트 실패를 해결하기 위해 기존 migration을 수정하거나 Flyway repair를 실행하지 않는다.
- 백엔드와 워커의 공유 토큰·콜백 대상·league/season 설정을 보존한다. 비밀값은 보고서에 복사하지 않는다.
- 기존 환경변수·볼륨·네트워크·재시작 정책과 세션을 보존한다. 신규 앱/계정 권한을 임의 확대하지 않는다.
- 백엔드와 워커 이미지는 linux/amd64로 고정하고, 배포할 태그 및 digest를 함께 기록한다.
- 새 화면은 scoped 경로만 사용한다. 오류 시 구형 전체 수집으로 자동 재시도하지 않는다.

## 검증 근거와 한계

- 완료: 날짜 필터와 워커 회귀, PC·모바일 viewport 입력, HTTP 보안/콜백 계약, 실제 JPA·MariaDB 저장/재조회, 전체 Flyway 및 V6→V7 업그레이드.
- 전체 앱·Firestore 에뮬레이터 통합은 별도 전체 흐름 테스트 결과를 기록한 후 판정한다.
- 합성 수집 HTTP 서버는 실제 NAS 워커의 Playwright 원천 탐색과 동일하지 않다. 외부 원천 수집 성공을 증명한 것으로 계산하지 않는다.
- 실제 모바일 기기, 운영 Firebase 토큰 및 실운영 네트워크/볼륨 조건은 별도 확인 대상이다.

## 배포 전 필수 확인

1. 전체 흐름 테스트의 실행·실패·제외 결과를 기록한다. 실패가 있으면 배포를 중단한다.
2. 범위 지원 워커의 새 버전 식별자를 확정하고 linux/amd64 이미지를 생성하여 테스트한다. 태그 중복 여부와 digest를 확인한다.
3. 프런트엔드 릴리스 빌드와 백엔드/워커의 실제 배포 대상 태그를 확정한다.
4. 운영 Flyway 이력과 백업 대상을 읽기 전용으로 확인한다. 복원 가능한 DB 백업의 경로·시각·담당자를 확정한다.
5. 수집 중인 실행이 없는지 확인하고, 배포 중 새 수집·게시·활성화를 막는 절차와 담당자를 정한다. 자동 재실행하지 않는다.
6. 대상 환경, 실행 시각, 작업자, 이전/신규 digest, DB 백업 및 복구 담당자를 사용자에게 제시해 승인받는다. 미기입 항목이 있으면 시작하지 않는다.

## 승인 후 적용 순서

1. 신규 수집을 중단하고 진행 중인 실행·기준 공식 리비전을 기록한다.
2. DB 백업 후 단일 백엔드 인스턴스로 V7을 적용한다. 기존 마이그레이션 checksum을 바꾸지 않는다.
3. 범위 지원 워커와 백엔드의 버전·인증·콜백 호환성을 확인한다. 확인 전에는 신규 수집을 열지 않는다.
4. 신규 프런트엔드를 배포한다. 운영 계정의 권한과 scoped 요청 경로를 확인한다.
5. 사용자가 별도 승인한 날짜 범위로 제한된 수집을 수행한다. 후보 검토 전에는 게시·활성화하지 않는다.
6. 이전 날짜의 경기·상세·공식 원본 보존, 대상 날짜의 변경분, 통계 누적 중복 없음, 활성화 전후 리비전을 대조한다.

## 중단·복구

- 범위 불일치, 이전 기록 삭제 후보, checksum 오류, 이중 집계, 원치 않은 공식 전환이 있으면 즉시 신규 실행을 중단하고 후보·로그를 보존한다.
- 서비스 복구와 데이터 복구를 구분한다. 구형 이미지로 바꾼다고 이미 활성화된 공식 데이터가 원복되는 것은 아니다.
- V7은 컬럼 추가지만 구형 이미지와의 실제 복귀 가능성은 검증 없이 단정하지 않는다. 자동 다운 마이그레이션이나 컬럼 삭제를 하지 않는다.
- DB 복원이 필요한 경우 승인된 백업·복원 절차를 사용한다. Firestore와 DB 리비전의 정합성을 함께 확인한다.
- 롤백용 기존 이미지·세션·설정은 보존하고, 테스트 자료만 범위를 특정해 정리한다.

## 최신 차단 사항

전체 앱 기동은 성공했으나 인증 에뮬레이터가 실제로 구성되지 않아 첫 관리자 요청이 401로 중단됐다. Auth 에뮬레이터 및 테스트 계정·토큰 발급을 구성한 뒤 전체 수집·공식 반영 흐름을 재실행해야 한다. 이 차단 사항이 해소되기 전에는 운영 배포를 승인하지 않는다. 자세한 실행 증거는 통합 검증 이력 문서에 기록했다.

## 추가 판정: Auth 포함 격리 전체 흐름 통과

2026-09-12 실행으로 앞서 기록한 Auth 에뮬레이터 미구성 차단 항목을 해소했다. Firebase CLI `15.17.0` Auth 에뮬레이터에 테스트 계정을 생성하고 관리자 클레임을 설정한 뒤, 로그인 API가 발급한 ID 토큰으로 실제 백엔드 HTTP API를 호출했다.

- 전체 Spring 앱, MariaDB `11.8.5`, Firestore·Auth 에뮬레이터를 격리 Docker 내부 네트워크에서 실행했다.
- 자동 최초 수집과 날짜 지정 재수집의 두 차례 흐름에서 검증·게시·활성화, 이전 상세 보존, MariaDB 재조회와 Firestore 공식 리비전 일치를 확인했다.
- JUnit 기준 1개 테스트 메서드 통과, 실패·오류·제외 0건이다. 두 수집 회차는 그 메서드 내부 시나리오이며 별도 테스트 수로 부풀리지 않는다.
- 익명 관리자 요청과 잘못된 워커 토큰 요청의 거부를 확인했다.
- 증거: `/tmp/aubl-full-flow.fjWMy9`, 요약 `/tmp/aubl-full-flow-auth-run.log`. 임시 경로이므로 장기 보관 증거로 간주하지 않는다.
- 테스트 컨테이너와 네트워크를 제거했다. 운영 API·DB 접근, 이미지 push, 운영 배포 및 실제 동기화·게시를 실행하지 않았다.

| 운영 백업·복구·실행 명세 | 기존 미기입 항목 충족 및 사용자 승인 필요 |

따라서 **로컬 전체 흐름 검증 통과 / 운영 배포 미승인** 상태를 유지한다. `aubl-auth-emulator:15.17.0`과 `aubl-backend:full-flow-test-20260912`는 테스트 전용 이미지이며 운영에 배포하지 않는다. 운영에는 `FIREBASE_AUTH_EMULATOR_HOST`·`FIRESTORE_EMULATOR_HOST`를 전달하지 않는다. 이 판정은 야구 기록 엔진 전체의 `READY_FOR_CONTROLLED_PROD_TEST` 선언을 대신하지 않는다.

## 워커 배포 후보 준비

어댑터 버전을 `2026.09.12.14`로 올리고 워커 README에 `collectionScope` 요청·콜백, KST 시작일 포함, 부분 상세와 전체 누적 기록의 구분 및 서버 병합 책임을 명시했다. 기존 Docker 런타임과 의존성 버전은 유지한다.

후보의 로컬 태그는 `aubl-uniqueplay-sync-worker:incremental-20260912-candidate`, 대상 플랫폼은 `linux/amd64`다. 성공한 빌드의 실제 digest와 생성 조건은 [워커 후보 이미지 명세](./uniqueplay-worker-candidate-2026-09-12.md)에 기록한다. 이 항목은 빌드 계획이며 성공 판정은 해당 명세의 실행 결과를 기준으로 한다.

현재 운영 이미지 `synapse9983/aubl-uniqueplay-sync-worker:v13`을 이 작업으로 교체하지 않는다. 신규 registry 태그, push 및 운영 배포 승인은 별도다. 후보 이미지 생성만으로 실제 NAS 수집이나 이번 버전의 회귀 테스트를 통과한 것으로 판정하지 않는다.

## 후보 검증 이후: 배포·백업·복구 계획

워커 후보의 격리 검증은 121건 모두 통과했고 실패·취소·제외·TODO는 0건이다. [실행 결과](./uniqueplay-worker-candidate-verification-2026-09-12.md)는 실제 원천 수집이 아닌 이미지 HTTP 경계·날짜 함수·합성 Chromium 시험이라는 한계를 유지한다.

[배포·백업·복구 실행서](./uniqueplay-incremental-deployment-runbook-2026-09-12.md)와 [실행 명세 JSON](./uniqueplay-incremental-execution-manifest-2026-09-12.json)을 추가했다. 순서는 승인·산출물 고정 → 신규 쓰기 차단·진행 작업 종료 → 백업·복원 준비 → 백엔드/V7 → 워커 → Hosting 전용 웹 → 별도 제한 수집 승인이다. 게시·활성화는 수집 승인과 분리한다.

운영 DB명, 백업 위치·복원 증거, 실제 Auth·Firestore 프로젝트, rollback digest·Hosting version, CI 및 서버 측 쓰기 차단, 담당자·시간·RPO/RTO는 아직 확정되지 않았다. 특히 V7 적용 후 v25 기동·읽기 호환성을 격리 검증하기 전에는 이미지 롤백 가능성을 보장하지 않는다. 문서 작성 과정에서 운영 조회·백업·push·배포 또는 추가 테스트는 실행하지 않았다. **계획 수립 완료 / 운영 실행 미승인** 상태다.

## 후속 완료: V7 DB에서 v25 읽기 복귀

위 계획 작성 이후 사용자 승인으로 `신규 후보 → v25 → 신규 후보`의 실제 이미지 왕복 검증을 수행해 세 단계 모두 통과했다. 범위 값이 있는 run 및 NULL인 구형 형태의 run을 포함한 관리자 조회, 검수 checksum, 전체 합성 DB 덤프와 Firestore 공식 리비전·경기 2건이 유지됐다. [상세 결과](./uniqueplay-v25-v7-rollback-verification-2026-09-12.md)를 실행 명세의 호환성 증거에 연결했다.

앞 절의 v25 기동·읽기 미검증 항목은 이 제한된 범위에서 해소됐다. 구형 writer의 쓰기 허용, 운영 백업 복원, 실제 NAS 수집과 배포 승인은 여전히 별도다. 다음 준비 과제는 최종 웹 산출물·배포 조합의 변경 범위 고정이며, 운영 실행 명세의 나머지 미확정 항목은 유지한다. 테스트 자원은 정리했으며 운영 접근·변경은 없었다.

## 후속 완료: 웹 후보 빌드 / 신규 차단: Hosting CI 대상 불일치

원래 dist를 보존한 임시 작업 디렉터리에서 production 웹 빌드와 OG 생성이 성공했다. Hosting 파일 47개, 소스 스냅샷·파일 manifest·배포 압축본 SHA-256을 [웹 후보 명세](./uniqueplay-web-candidate-2026-09-12.md)에 고정했다. 전체 웹 작업트리의 산출물이므로 UniquePlay만의 변경 범위 승인이나 최종 UI 회귀 통과로 간주하지 않는다. 빌드의 500 kB 초과 경고가 남으며 추가 타입 검사·lint·UI 테스트는 이번 단계에 실행하지 않았다.

`.github/workflows/firebase-hosting-merge.yml`은 main push 시 실행되며 Firebase 설정은 aubl-backup에서 읽지만 배포 action은 aubl-web-9a141을 대상으로 한다. 이번 의도한 Hosting 대상과 달라 **CI 대상 통일·사용할 서비스 계정 확인·명시적 승인 경계 마련 전 배포 보류**다. workflow·secret·운영은 변경하지 않았으며, 실행 명세에 이 불일치를 기록하고 웹 산출물 식별 항목만 채웠다.

## 수동 배포 승인 후 사전 확인

사용자는 CI를 사용하지 않고 백업 확인 → 백엔드/V7 → 워커 → 웹 순서로 수동 배포하는 범위를 승인했다. [사전 확인 결과](./uniqueplay-manual-deployment-preflight-2026-09-12.md)에서 실제 DB는 컨테이너 기본값 aubl_db가 아니라 **aubl**이며, V1~V6 성공·InnoDB 24개 테이블임을 확인했다. 2026 활성 공식 리비전과 현재 Hosting live version/release를 실행 명세에 기록했다.

백업 위치·완료·복원 증거가 미확정이므로 운영 교체는 아직 시작하지 않았다. 이미지 push, DB 마이그레이션, 컨테이너 변경, Hosting 배포 및 실제 수집·게시도 미실행이다. 수동 배포 승인은 실행된 배포 결과나 다른 운영 진입 조건의 면제를 뜻하지 않는다.
