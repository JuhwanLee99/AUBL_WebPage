# UniquePlay 운영 증분 수집 실행 결과와 후속 복구 과제

작성일: 2026-09-13 (KST)

## 1. 결론

`LIVE_SYNC_INCOMPLETE_STATE_DIVERGENCE`

사용자가 승인한 운영 증분 수집을 한 번 시작했으나 완료되지 않았다. 워커의 활성 실행 수는 0인데 백엔드 DB에는 해당 실행이 `RUNNING / CONNECTING`으로 남아 있고 후보 데이터가 없다. 이 표기는 문서의 검증 판정이며, DB 상태를 `FAILED` 등으로 변경한 것이 아니다.

기존 공식 리비전과 체크섬은 읽기 전용 DB 조회에서 동일하게 유지됨을 확인했다. 게시, 공식 활성화, 추가 수집, 전체 시즌 수집으로의 전환, 컨테이너 재시작 및 DB 수동 상태 변경은 수행하지 않았다. 배포 및 워커 연결 확인 통과와 실제 수집 성공은 구분한다. 현재는 신규 동기화의 운영 성공 판정을 내릴 수 없다.

## 3. 관측 증거

### 3.1 백엔드 DB와 관리자 화면

| 확인 항목 | 관측 결과 |
| --- | --- |
| `status` | `RUNNING` |
| `progress_stage` | `CONNECTING` |
| `error_code` | `NULL` |
| `candidate_json IS NOT NULL` | `0` |
| `updated_at` | `2026-09-13 00:10:49.465923` |
| 관리자 실행 상태 | 시작 단계에 머무름, 후보 체크섬 없음 |

조회는 MariaDB 세션을 읽기 전용으로 지정한 뒤 수행했다. 후보가 없으므로 수집 경기 수 0 표시를 '변경된 경기가 없어서 정상 종료'로 해석하지 않는다.

### 3.2 워커

컨테이너 안에서 로컬 `/health`를 조회한 결과는 다음과 같다.

```json
{"ok":true,"activeRuns":0,"adapterVersion":"2026.09.12.14"}
```

HTTP 상태는 200이다. 이 결과는 워커 프로세스의 응답과 관측 시점의 활성 실행 부재를 뜻하며, 해당 수집의 성공을 뜻하지 않는다. 워커 로그에서는 시작 안내만 확인되어 최초 실패 이유를 확정할 수 없었다.

워커의 콜백 주소에 읽기 전용 GET을 보내는 추가 진단을 시도했으나 실행 및 응답을 확인하지 못했다. 따라서 콜백 경로의 접속 성공, 인증 성공, 특정 HTTP 오류를 이번 결과로 주장하지 않는다. 실제 콜백은 POST이며 GET의 성공 또는 405만으로 POST 처리 성공을 증명할 수도 없다.

공식본 식별자와 저장 체크섬의 불변을 확인한 것이며, 모든 공개 화면과 선수별 누적 통계를 전량 재검증한 것은 아니다.

## 4. 코드 분석으로 확인한 결함과 아직 모르는 부분

검토 대상은 `services/uniqueplay-sync-worker/src/server.mjs`와 백엔드의 `UniquePlaySyncInternalController`, 실행 및 리비전 엔티티다. 이번 진단에서는 제품 소스와 테스트를 수정하지 않았다.

### 4.1 실패 통지 오류가 사라짐

워커는 수집 또는 후보 전달에서 예외가 발생하면 `/failed` 콜백을 호출한다. 이 콜백 자체가 실패할 때 `.catch(() => {})`로 예외를 무시하고, `finally`에서 `activeRuns`에서 실행을 제거한다. 이 경로에는 실패 이유를 남기는 로그가 없다.

따라서 백엔드는 `RUNNING`으로 남아 있는데 워커에는 활성 실행이 없는 상태가 생길 수 있다. 이번 관측은 이 결함과 일치하지만, 최초 수집 예외와 콜백 실패의 구체적인 원인까지 입증한 것은 아니다.

### 4.2 콜백 전달 보장이 없음

현재 콜백은 단일 POST 요청과 30초 타임아웃으로 구성되어 있다. 검토한 워커 진입 코드에는 재시도, 영속 보관, 전달 완료 확인 이후의 정리 절차가 없다. 백엔드 응답 유실과 실제 미반영도 구분할 수 없다.

후보 콜백과 실패 콜백을 단순 반복하면 중복 반영 또는 이미 성공한 실행의 실패 덮어쓰기 위험이 있으므로, 재시도만 덧붙이지 않고 서버의 멱등성과 최종 상태 전이 조건을 함께 설계해야 한다.

### 4.3 연결됨 표기의 검증 범위가 제한됨

워커 `/session`은 `loadStorageState()`에 성공하면 연결됨을 반환한다. 이는 저장된 세션 자료의 로드 가능성을 확인할 뿐, UniquePlay 원천 사이트에서 현재 로그인이 유효하고 실제 수집 권한이 있는지를 온라인으로 검증하지 않는다.

따라서 앞선 연결 검증의 `연결됨 / 인증 확인됨`을 실제 원천 인증 또는 수집 성공의 증거로 확대 해석하지 않는다. 이번 실패를 세션 만료로 확정할 근거도 아직 없다.

### 4.4 종료 상태 복구 경로가 필요함

관측된 실행은 DB와 워커의 상태가 불일치한다. 현재 운영에서 이 실행을 안전하게 종결시키는 복구 경로를 확인하거나 실행하지 않았다. DB 값을 직접 변경하거나 새로운 실행으로 우회하면 원인과 이력이 사라질 수 있어 보존했다.

## 5. 권장 후속 작업과 승인 경계

1. 수집 단계, 실행 ID, 콜백 종류, HTTP 상태 및 안전한 오류 코드를 구조화해 기록한다. 토큰, 세션 자료 및 원천 응답의 민감 정보는 로그에 남기지 않는다.
2. 콜백 실패를 재현해 원인을 확정한다. DNS, TLS, 네트워크, 서비스 인증, 요청 검증 및 서버 예외를 구분하고 오류를 숨기지 않는다.
3. 콜백을 영속 보관하고 동일 전달 식별자로 제한적 재시도한다. 서버는 중복 요청을 멱등 처리하고, 이미 확정한 후보 또는 최종 상태를 뒤늦은 실패 통지로 되돌리지 않는다.
4. 실행별 상태 조회 또는 heartbeat와 서버 측 조건부 복구를 연결한다. 지연 중인 실행과 실제 종료된 실행을 구별하며, 명시적인 관리자 복구는 기존 상태, 복구 근거, 수행자를 감사 이력에 남긴다.
5. 현재 정체 실행은 복구 방법 검증과 사용자 승인 후 종결한다. SQL 직접 변경, 자동 삭제, 무조건 실패 처리, 워커 재시작으로 우회하지 않는다.
6. 로컬 검증에서 콜백 타임아웃, 응답 유실 후 재전송, 후보 저장 후 응답 유실, 실패 콜백 실패, 워커 재시작 및 늦게 도착한 메시지를 다룬다. 중복 후보와 최종 상태 역전을 금지한다.
7. 수정 및 배포 승인을 받은 뒤 동일한 증분 범위로 한 번 재검증한다. 후보의 범위와 이전 기록 보존을 확인하기 전에는 게시하거나 공식 활성화하지 않는다.

이번 단계에서는 위 수정과 복구, 재수집을 수행하지 않았다. 진단용 워커 콘솔은 Disconnect로 종료했고 관리자 실행 화면은 후속 작업을 위해 유지했다. DB 진단 탭은 종료 시점에 이미 없어 별도 쉘 종료 확인은 하지 못했다.
