# UniquePlay 영속 접수·실제 DB 저장 검증 결과

작성일: 2026-09-13 (KST)

## 1. 판정과 범위

`LOCAL_DURABLE_STORAGE_GATE_PASSED_PENDING_PRODUCTION_ROLLOUT`

이번에 실행한 선별 검증은 **워커 116건, 백엔드 69건 모두 통과**했으며 실패·오류·제외는 0건이다. 백엔드에는 실제 MariaDB 11.8.5와 loopback HTTP를 이용한 콜백 저장·복구 12건, 마이그레이션 2건 및 기존 실제 DB 회귀 1건이 포함된다.

이는 콜백 영속 접수·저장 경로의 이번 사전 검증 통과다. 서비스 전체, 모든 야구 규칙, 실제 운영 로그인, 운영 워커에서 UniquePlay를 수집하는 전체 흐름을 모두 통과했다는 뜻은 아니다. 운영 이미지 배포, 운영 DB 변경, 정체 실행 복구, 원천 재수집, 게시·공식 활성화는 이번 작업에서 수행하지 않았다.

**현재 상태는 운영 전환 준비 단계이며 정상 운영 완료가 아니다.** 관리자 복구 화면 연결, 운영 영속 볼륨과 배포 전환, 실제 수집 및 A조 순위 검수가 남아 있다.

## 2. 승인받아 수정한 제품 코드

대상: `services/uniqueplay-sync-worker/src/durable-runs.mjs`.

1. 같은 실행 ID로 재요청해도 메모리에만 예약된 상태를 접수 완료로 응답하지 않는다. 진행 중인 최초 디스크 저장을 기다리고, 그 저장이 실패하면 모든 중복 요청도 실패한다.
2. 최초 디스크 저장이 진행 중인 실행을 `accepting` 상태로 관리한다. 실행별 `active`와 `/health`의 활성 수에 포함한다.
3. 최초 접수 중에는 관리자 fence와 전송 재시도를 `RUN_BUSY`로 거부한다. 같은 시점에 다른 실행을 시작하는 것도 계속 차단한다.
4. 최초 접수가 완료된 뒤 수집 소유권을 이어받으며, 같은 요청 17건이 동시에 들어와도 실제 수집은 한 번만 수행한다.

이전의 `duplicate request must wait for the first durable acceptance` 실패가 해소됐다. 여기에 동시 접수의 디스크 실패, 접수 중 복구·재시도, 다수 중복 요청 시 단일 수집 테스트를 추가했다.

## 3. 실제 HTTP·MariaDB 검증

신규 `UniquePlayDeliveryMariaDbTest`는 Spring의 실제 트랜잭션 프록시, 기존 후보 병합 서비스, MariaDB 저장소를 사용한다. 실제 HTTP 시험은 loopback HTTP 서버에서 제품 콜백 컨트롤러로 요청을 전달한다. 저장 결과는 ORM 캐시가 아니라 별도 JDBC 연결로 확인한다.

| 시나리오 | 독립적으로 확인한 결과 |
| --- | --- |
| 정상 후보 전달 | HTTP 200 ACK, 후보와 영수증 커밋, 과거 상세 2건 보존, 기존 공식 리비전 불변 |
| 영수증 INSERT 실패 | 실제 DB 트리거로 오류 주입, 앞서 처리한 후보·변경 항목까지 함께 롤백 |
| 바깥 트랜잭션 실패 | 후보와 영수증이 별도 커밋으로 남지 않고 함께 롤백 |
| 커밋 후 HTTP 응답 유실 | 동일 전달 ID로 재요청해 ACK 복구, 후보·변경 항목 중복 없음 |
| 동일 전달의 동시 HTTP 요청 | 실행 잠금으로 직렬 처리, 두 요청이 같은 결과를 받고 영수증은 1개 |
| 순번 2가 먼저 도착 | 선행 순번 누락을 409로 거부, 이후 1→2 순서로 정상 처리 |
| 후보 커밋 후 늦은 실패 | 409로 거부, 검수 후보와 기존 공식본 유지 |
| 잘못된 워커 인증 | 401, 후보·영수증·변경 항목 저장 없음 |
| 명시적 관리자 복구 | 실패 종결과 수행자 감사 이력 1회 저장, 동일 복구 재요청은 멱등 처리 |
| 복구 감사 INSERT 실패 | DB 복구 변경 롤백, 같은 fence ID로 재시도하여 정상 복구 |
| 워커 fence 증거 없음 | DB 상태와 영수증을 변경하지 않음 |
| 복구 전 갱신 시각 변경 | 워커에 연락하기 전에 충돌로 거부 |

시험용 워커 fence 응답은 모의 객체로 주입했다. 실제 워커 fence 및 접수 경계는 Node 테스트로 별도 검증했다. 하나의 실행에서 실제 Node 워커, 실제 인증된 운영 관리자, 운영 백엔드, 운영 DB를 모두 연결한 E2E와 혼동하지 않는다. Firestore 게시도 모의 객체로 차단하고 호출되지 않았음을 검증했다.

## 4. 마이그레이션과 호환성

- V6→V8: 마이그레이션 2개 적용, 기존 기록 보존, 재실행 시 추가 적용 0개.
- V7→V8: 영수증 테이블 추가 1개만 적용, 기존 후보 JSON·체크섬·상태·증분 모드·시작일 보존, 재실행 시 추가 적용 0개.
- 기존 실제 DB 회귀의 성공 마이그레이션 기대값을 7에서 8로 갱신했다.
- 전환 스위치 기본값에서는 구형 콜백의 호환성을 유지한다.
- `uniqueplay.require-durable-callbacks=true`에서는 구형 콜백만 410으로 차단하고 v2 콜백은 허용한다.

운영 전환 스위치는 아직 켜지 않았다. 기존 워커에 영향을 주는 실제 차단은 새 백엔드·워커 전환과 함께 별도 승인 및 순서 확인이 필요하다.

## 5. 실패를 숨기지 않은 검증 이력

### 5.1 최초 워커 실패 해소

이전 113건 중 실패 1건이었던 최초 저장·중복 접수 경계를 수정했다. 추가 접수·복구 경계까지 포함한 최종 116건이 모두 통과했다.

### 5.2 테스트 선언 오류

새 프로토콜 전환 테스트의 메서드 선언에서 `void` 뒤 공백이 빠진 것을 실행 전에 발견했다. 사용자 승인 후 해당 선언만 수정했으며 제품 코드 수정으로 처리하지 않았다.

### 5.3 첫 실제 DB 실행: 69건 중 56건 통과, 13건 실패

12건은 정리 대상 DB를 제한하는 안전 검사에서 실패했다. MariaDB JDBC 메타데이터가 기본 포트 3306을 생략하고 `jdbc:mariadb://delivery-db/delivery_jpa?user=root`로 정규화했는데, 하네스가 포트를 포함한 문자열 접두사를 요구했기 때문이다. 데이터 정리와 저장 시나리오 전에 차단됐다.

나머지 1건은 기존 실제 DB 테스트에서 발생한 테이블 대소문자 불일치다. 새 실행 스크립트에 기존 `scripts/test-uniqueplay-db-integration.sh`가 사용하던 `PhysicalNamingStrategyStandardImpl` 설정이 빠져 있었다.

사용자 승인 후 주소 검사를 URI의 프로토콜·호스트·허용 포트·DB 경로·실제 catalog에 대한 정확한 검사로 바꿨다. 운영 DB와 다른 호스트를 허용하도록 완화한 것은 아니다. 또한 기존 검증 스크립트와 동일한 Hibernate 테이블명 정책을 추가했다. 운영 DB의 테이블명이나 제품 엔티티는 바꾸지 않았다.

## 6. 운영 격리와 정리

재실행 스크립트: `scripts/test-uniqueplay-durable-integration.sh`.

- 캐시된 `gradle:jdk21`, `mariadb:11.8.5`만 사용하고 새 이미지를 자동 다운로드하지 않았다.
- Docker 내부 전용 네트워크를 만들고 공개 포트를 열지 않았다.
- 운영 DB 주소·자격증명과 Firebase 서비스 계정을 전달하지 않았다. `.env`는 검증 사본에 복사하지 않았다.
- 백엔드 원본은 읽기 전용으로 마운트하고, 빌드·검증은 임시 사본에서 수행했다.
- 테스트 DB는 새 컨테이너의 tmpfs에만 생성했다. 운영 DB에 테스트 경기나 실행을 생성하지 않았다.
- 첫 실행과 재실행 모두 종료 시 테스트 DB 컨테이너와 내부 네트워크 제거가 성공했다.

최종 정리 대상은 `aubl-durable-db-20260912164918-16273`, `aubl-durable-check-20260912164918-16273`이며 제거 결과를 `cleanup-success.log`에 보존했다. 테스트용 트리거도 시험 종료 시 제거했고 컨테이너 종료로 데이터 영역 전체가 폐기됐다.

## 7. 보존한 증거

프로젝트 내 `docs/release/evidence/uniqueplay-durable-2026-09-13/`에 보관했다.

- `verification-summary.json`: 클래스별 실행·실패·제외 수와 운영 변경 없음.
- `worker-acceptance.tap`: 워커 116건 결과.
- `backend-junit/`: 백엔드 9개 테스트 클래스의 JUnit XML.
- `backend-success.log`: 최종 컴파일·시험 성공 로그.
- `backend-initial-failure.log`: 13건 하네스 실패가 있던 첫 실행 로그.
- `cleanup-success.log`, `cleanup-initial.log`: 두 실행의 임시 DB·네트워크 제거 결과.

임시 원본 결과는 `/tmp/aubl-durable-integration.tcSFN3`, 선행 실패 결과는 `/tmp/aubl-durable-integration.GB3nVR`이다. 프로젝트 증거 사본이 있어 임시 경로 정리에 의존하지 않는다.

## 8. 운영 가능 판정까지 남은 작업

1. 관리자 복구 API를 실제 관리자 UI 또는 승인된 운영 도구로 호출하는 절차를 연결하고, 로그인·권한·최신 기대값·재시도 동작을 확인한다.
2. 신규 워커의 `SYNC_STATE_DIR`를 NAS의 전용 영속 디렉터리에만 연결한다. 실제 재시작 후 보존과 파일 권한을 확인한다. 컨테이너 내부 임시 파일시스템만으로 배포하지 않는다.
3. 최신 백업과 롤백 명세를 고정한 뒤 새 백엔드·워커를 순차 배포하고 V8 및 실제 콜백 연결을 확인한다. 기존 CORS·서비스 인증·DB 연결은 보존한다.
4. 승인된 시점에 구형 콜백 차단 스위치를 켠다. 그 전에는 구형 경로까지 포함한 종료 상태 보호가 완료됐다고 판단하지 않는다.
5. 운영 정체 실행의 최신 상태를 다시 확인하고 조건부 복구한다. 과거 실행 증거를 보존하며 SQL 직접 변경이나 임의 삭제로 우회하지 않는다.
6. 실제 증분 수집을 한 번 수행해 원천 접속·날짜 범위·후보 병합·이전 기록 보존을 검증한다. 현재 실패의 구체적인 최초 원인도 새 로그로 확인해야 한다.
7. A조의 기존 후보와 게시 데이터, 최신 원천 순위를 대조하고 관리자 검수를 완료한다. 이번 로컬 시험으로 운영 A조 순위가 정정된 것은 아니다.
8. 게시·공식 활성화는 별도 승인 후 수행한다. TrueNAS 저장 원본과 Portainer 실행 구성의 차이로 재배포 시 설정이 되돌아갈 수 있는 위험도 별도로 해소하거나 명시적으로 통제해야 한다.
