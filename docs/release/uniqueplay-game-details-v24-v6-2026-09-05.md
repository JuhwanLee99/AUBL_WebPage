# UniquePlay 경기 상세 연동 배포 보고서 — 백엔드 v24 / 워커 v6 이후

작성일: 2026-09-05 KST. 이 문서는 구현·검증·이미지 업로드와 실제 NAS 적용·운영 수집을 구분한다. **백엔드 v24·워커 v9를 Docker Hub와 NAS에 적용했다. 실제 미리보기에서 종료 117경기의 상세 결과를 모두 수집했으며, 합계 검증 오류 10건으로 게시를 차단했다. 공개 리비전은 유지됐다.** 운영 원천에서 확인한 표 추출 결함의 버전별 보완과 검수 결과를 아래에 기록한다.

## 1. 배포 목적과 범위

기존 일정·경기 결과·시즌 누적 기록 수집에 종료 경기의 양 팀 박스스코어와 선수별 경기 기록을 추가한다. Flutter 디자인 B안을 `getResult`에 통합한 상태에서 웹·앱이 같은 공식 상세 API를 사용하도록 연결했다.

- 수집은 관리자가 명시적으로 버튼을 눌렀을 때만 시작한다. 스케줄러와 앱 백그라운드 수집은 추가하지 않았다.
- 이닝별 점수, R/H/E/B, 교체 선수를 포함한 타자·투수 기록, 원천의 이닝별 타격 결과 문자열을 수집한다.
- 기존 AUBL 수동 경기 로그·라인업·라이브 기록을 삭제하거나 공식 상세로 덮어쓰지 않는다. 경기별 기록을 시즌 누적 기록에 중복 합산하지 않는다.
- 수집 후보는 검수·검증·리비전 생성·활성화를 거쳐야 공개된다. 이번 운영 확인의 범위는 **배포와 관리자 미리보기 수집까지**이며, 게시·활성화는 별도 판단 단계다.

## 3. 핵심 변경과 회귀 방어

### 수집·정제

- 기존 `sourceGameId`를 유지하면서 공개 박스스코어 URL의 실제 번호를 `providerGameId`로 별도 보존한다.
- 새 후보의 모든 종료 경기에는 `AVAILABLE` 또는 검증된 `NOT_PUBLISHED` 상세 결과가 하나씩 있어야 한다. 양 팀·외부 ID·점수·헤더·행 수가 맞지 않으면 수집 또는 검증을 차단한다.
- `null`, 실제 0, 미진행 이닝 `X`를 구분한다. 투수 `1.2`는 5아웃으로 보존하고 ERA는 원천 값을 사용한다.
- 원천 합계 행은 선수로 저장하지 않는다. 이닝별 결과 문자열을 임의로 분해해 정확한 타석·투구 타임라인을 만들어내지 않는다.
- 명시적 몰수·기권·부전승 카드이면서 양 팀 표에 정확한 헤더와 합계 행만 있는 경우에만 `NOT_PUBLISHED`를 허용한다. 일반 종료 경기의 빈 기록을 정상 0 기록으로 바꾸지 않는다.

### 검수·게시

- `GAME_RECORD` 비교 항목을 추가했다. `이전 공식 상세 유지`는 기존 공식 상세 스냅샷을 유지한다는 뜻이며, 수동 기록으로 대체하는 기능이 아니다.
- 검수 결정을 반영한 별도 불변 스냅샷과 체크섬을 보관한다. 원본 미리보기 체크섬 검증도 유지한다.
- 기존 공개본에 상세가 있는데 구 워커가 상세 필드를 누락하면 `DETAIL_SCHEMA_DOWNGRADE`로 차단한다. 이전 리비전으로의 명시적 복구는 지원한다.
- AUBL 경기 점수·상태 오버라이드가 공식 상세와 다르면 `DETAIL_GAME_OVERRIDE`로 검증·게시를 차단한다. 활성화 이후 결과가 달라져도 `REVIEW_REQUIRED`로 상세를 숨긴다. 구장·일시·운영 메모·라이브 URL 변경만으로 상세를 차단하지 않는다.

### 웹·앱

- `GET /api/games/source/{sourceGameId}/details?seasonId=`와 `GET /api/players/{playerId}/official-game-logs?seasonId=`를 사용한다.
- 활성 공식 리비전의 상세만 표시한다. 선수 연결이 모호하면 `IDENTITY_UNRESOLVED`로 처리하며 다른 선수나 수동 기록을 임의로 대신 표시하지 않는다.
- 공식 활성 리비전이 없는 `NO_ACTIVE_REVISION`에서만 기존 선수 기록 조회를 허용한다. 미수집·오류·검수 필요 상태는 수동 기록 fallback 사유가 아니다.
- 공개 경기 일정·점수·상태는 DB의 공개 값과 맞추고, 공식 상세 팀명은 원천 이름을 유지한다. 예정·진행 중인 동일 Firestore 경기의 라이브 기능은 유지한다.

백엔드 실행 JAR 빌드와 Flutter 정적 분석도 통과했다. 자동 테스트는 운영 UniquePlay 계정으로 시즌 전체를 수집하거나 NAS 데이터를 게시하지 않았다. Java 테스트 실행 환경과 배포 이미지 아키텍처는 별개이며, 배포 이미지는 두 구성 모두 `linux/amd64`로 준비했다.

v7 추가 검증: 워커 40개, 웹 API 9개, 경로 6개 통과. 백엔드 81개·Flutter 134개를 포함한 검증 기준선은 총 **270개**다. 백엔드·Flutter 소스는 v7에서 변경하지 않았다. 실제 경기 `56556`의 상대팀 DOM에서도 수정된 구조 필터가 타자·투수 표를 각각 1개만 식별하는 것을 읽기 전용으로 확인했다.

v7은 표 제목의 전역 동일 텍스트 개수가 아닌 고정 첫 행·2열 표 구조·정확한 통계 헤더로 식별한다. 준비 대기는 최대 15초 polling budget 내에서 파싱 가능한 동일 표 2회를 요구한다. 잘못된 표를 건너뛰지 않는다. 오류 메시지는 허용된 코드·단계·공개 해시/숫자 경기 ID만 포함하고 원문 예외나 사용자 정보를 전달하지 않는다.

두 번째 미리보기는 v7로 `964e3353-910d-47e3-8c35-20c6a85025ef`를 13:19:31에 시작해 13:21:10 `GAME_DETAIL_SCHEMA`, `READ_INITIAL`, 공개 경기 `56556`에서 중단됐다. 추가 진단으로 공개 표 셀의 혼합 DOM 구조를 확인했다. 기존 leaf-only 추출은 부모 직접 Text node의 타순·이름을 누락하고 자식 포지션·등번호만 읽었다. 전체 공개 셀 `textContent`의 NFKC/공백 정규화로 보완하고, 직접 텍스트와 자식 span이 섞인 합성 fixture를 추가한다. 원본 HTML·계정 UI 수집 범위는 확대하지 않는다.

v8에서는 위 혼합 셀 추출 보완을 적용했다. 워커 41개·웹 API 9개·경로 6개 통과, 변경 없는 백엔드 81개·Flutter 134개를 포함한 최종 테스트 기준선은 **271개**다. 웹 전체 ESLint, TypeScript, 프로덕션 빌드도 통과했으며 기존 500kB 초과 번들 경고만 남아 있다. 실제 운영 계정 수집 성공 여부는 아래 실행 결과로 별도 판단한다.

v9에서는 선택적 정보 행에 의해 바뀐 팀 탭 위치와 명시적인 빈 등번호 `()`를 지원했다. 정확한 양팀명·유일성·선택 상태 검증은 유지하며 정보 행의 내용은 수집하지 않는다. 워커 43개·웹 API 9개·경로 6개 통과, 변경 없는 백엔드 81개·Flutter 134개를 포함한 검증 기준선은 **273개**다.

후속 관리자 검수 UI에서는 합계 비교 helper 12개와 검증 경로 API fixture 2개를 추가했다. 최종 `npm run test:uniqueplay`는 워커 43 + 경로 6 + 검수 helper 12 + 웹 API 11 = **72개**를 통과했다. 앞서 검증했고 변경하지 않은 백엔드 81·Flutter 134개를 포함한 전체 기준선은 **287개**다. 웹 전체 `npm run check:ci`(ESLint·TypeScript·프로덕션 빌드)도 통과했고, 기존 번들 크기 경고는 남아 있다. 이 UI는 로컬 웹에서 확인했으며 호스팅 배포하지 않았다.

## 5. 스키마·비밀 정보 사전 검토

### 스키마

- 이번 변경에는 새 Flyway 마이그레이션·JPA 엔터티·테이블 변경이 없다.
- NAS의 기존 v23 시작 로그에서 7개 마이그레이션 검증 성공, `aubl` 스키마의 현재 버전 6, 최신 상태임을 확인했다.
- 기존 v23 JAR와 새 v24 JAR에 포함된 V1~V6 마이그레이션 파일의 SHA256이 모두 일치한다. 따라서 확인한 기존 DB·동일 설정을 사용하는 이번 배포에는 신규 마이그레이션이 없다.
- Hibernate는 `ddl-auto=none`이다. Flyway는 활성화되어 시작 시 `migrate()`를 호출하므로, 다른 DB나 환경으로 연결할 경우에도 검증 전용이라고 가정해서는 안 된다.
- 스키마 변경이 없다는 의미와 DB 쓰기가 없다는 의미는 다르다. 이후 승인된 미리보기 수집은 실행·후보·검증 감사 데이터를 기록하지만, 별도 게시·활성화 전에는 공개 리비전을 변경하지 않는다.

### 빌드 컨텍스트와 비밀 정보

- 기존 백엔드 Dockerfile의 `COPY . .`는 개발 디렉터리의 불필요한 SQL까지 빌드 컨텍스트에 전달할 수 있다. 이번 배포는 **검증된 실행 JAR와 런타임 Dockerfile만 포함한 별도 허용 목록 컨텍스트**를 사용한다.
- JAR의 비밀번호·워커 토큰 설정은 환경변수와 빈 기본값이며, Firebase 자격증명은 외부 경로를 요구한다. JAR에 하드코딩된 비밀 기본값, 세션·개인키·자격증명 파일은 확인되지 않았다.
- 워커 이미지는 애플리케이션 소스와 패키지 파일만 사용한다. 운영 세션·암호화 키·토큰·DB 비밀번호·Firebase 자격증명은 이미지·문서·커밋에 포함하지 않는다.

## 9. 롤백과 중단 기준

공개 GET 실패, 인증 실패, 워커 세션 접근 실패, 실제 연결 DB 불일치, 예상하지 못한 마이그레이션 또는 공개 리비전 변경이 확인되면 확대를 중단한다.

기존 이미지로의 복귀는 실행 중인 수집과 콜백 상태를 확인한 뒤 수행한다. 컨테이너 교체 시 DB·세션 볼륨을 삭제하지 않으며, 이미지 복귀를 위해 DB 복원·기록 삭제·리비전 활성화를 임의로 실행하지 않는다. 구 워커로 복귀하면 새 상세 기능이 없으므로, 상세가 게시된 시즌의 이후 수집은 `DETAIL_SCHEMA_DOWNGRADE`로 차단될 수 있다.

상세 구현 계약은 [경기별 상세 기록 연동 문서](../UNIQUEPLAY_GAME_DETAILS.md), 전체 배포·장애 이력은 [동기화 변경 이력](../UNIQUEPLAY_SYNC_CHANGELOG.md)을 기준으로 관리한다.
