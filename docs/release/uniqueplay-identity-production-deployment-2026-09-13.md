# UniquePlay 팀 식별·순위 비교 운영 배포 결과

작성일: 2026-09-13 (KST)

상태: `DEPLOYED_COLLECTION_VERIFICATION_BLOCKED`

## 1. 결론

- NAS DB 백업 후 Portainer에서 백엔드 이미지 교체를 완료했다.
- 팀명 매칭 개선 백엔드와 이전 공식 순위/원천 순위 비교 화면이 운영에 배포되었다.
- 새 수집은 `STANDINGS_RANK_CONFLICT`로 후보 생성 전에 실패했다. 따라서 운영 데이터에서 추가·삭제 감소 효과를 확인한 것으로 판정하지 않는다.
- 기존 후보와 활성 공식 리비전을 유지했다. 게시, 공식 리비전 생성, 활성화, 기존 후보 재생성·삭제는 실행하지 않았다.
- 배포 성공과 동기화 승인, 공식 순위 수정 완료는 서로 다른 상태다. 현재 동기화의 무조건적인 정상 운영 승인은 보류한다.

이 문서는 `uniqueplay-identity-comparison-2026-09-13.md`의 로컬 검증 이후 실제 배포 결과를 기록한다. 기존 로컬 검증 증거를 대체하거나 실패 이력을 지우지 않는다.

## 3. 배포 전 백업

- NAS 경로: `/mnt/ssd_500_p31/aubl_db/.aubl-deployment-backups/identity-20260913.H8ROTu/aubl.sql.gz`
- 컨테이너 경로: `/var/lib/mysql/.aubl-deployment-backups/identity-20260913.H8ROTu/aubl.sql.gz`
- SHA-256: `5620e39c719ba04ce5bf237e3085378994a3848b69da9651f108ae14fca34d75`
- 크기: `5,236,067` bytes.
- 권한/소유자: `0600`, `999:999`.
- 방식: `mariadb-dump --single-transaction --quick --routines --events --triggers --hex-blob --databases aubl` 후 gzip 압축.
- `gzip -t` 성공 및 동일 디렉터리 `SHA256SUMS` 생성 확인.
- NAS ACL에 맞춰 DB 컨테이너의 `mysql` 사용자로 실행했다. 기존 백업은 보존했다.
- 이번 백업의 복원 시험은 실시하지 않았다. 동일 NAS 내부 백업이며 외부 재해 복구 사본으로 간주하지 않는다.

## 4. 실제 배포 중 발생한 사항

1. 최초 이미지 교체에서 Portainer의 기본 이미지 입력이 적용되지 않아 기존 `cancel` 이미지로 컨테이너가 재생성됐다. 실제 이미지 확인에서 발견했으며 성공으로 처리하지 않았다.
2. 두 번째 요청 전 고급 이미지 입력으로 전환하고 전체 태그와 digest를 지정했다. 최종 컨테이너에서 신규 태그와 digest를 확인했다.
3. 교체 중 첫 공개 API 검사는 `Overview HTTP 502`로 종료됐다. 기동 완료 후 12:45 및 신규 수집 실패 후 12:47 공개 검사는 모두 통과했다. 무중단 배포였다고 주장하지 않는다.
4. 애플리케이션 로그에서 Flyway V8 유지, 추가 migration 불필요, 포트 8080 기동 완료를 확인했다.
5. Firebase CLI는 46개 파일을 대상으로 Hosting 배포 완료를 반환했다. Functions, Firestore 규칙, DB 배포는 실행하지 않았다.

## 5. 배포 후 검증 결과

### 공개 서비스

- 기존 공식 리비전 `291109ef-b73a-44ad-ab8c-121ac67812ca` 유지.
- 공개 경기 기록의 리비전 49개가 동일 공식 리비전과 일치.
- `/`, `/admin/unique-play-sync`, 새 번들 모두 HTTP 200.
- HTML `Cache-Control: no-cache`, 정적 번들 `public,max-age=31536000,immutable` 유지.
- 공개 API에는 공식 내용 체크섬이 없어 `officialChecksumPreserved: null`, `not_checked/checksum_not_exposed`로 기록한다.
- 이 확인은 공개 리비전/Hosting 검증이지 전체 DB 내용 무결성 검증이 아니다.

### 기존 후보 보존과 순위 표시

- 기존 실행: `4216cd04-6753-4568-afc7-982eeb72ac7c`.
- 상태: 게시 준비 완료, 추가 466 / 변경 12 / 삭제 후보 438 / 변경 없음 983 / 전체 1899.
- 체크섬: `8cd2d29e80c39eae880a8fd20f33942dbbf6862c44eedae3a5879087706c74c5` 유지.
- 기존 후보를 재생성하지 않고 조회했다. 기존 잘못된 추가·삭제 분류가 조회만으로 바뀌는 구조는 아니다.
- A조 화면에서 이전 순위 `1,1,1,1,1`과 원천 순위 `1,1,3,4,5`를 각각 확인했다.
- 이전/원천 승패무도 표시되며, 원천의 상위 두 팀 공동 1위를 임의의 순위로 분리하지 않았다.
- B~H조도 이전/원천 비교 표가 표시됐다. 변경 여부를 실제로 다시 분류하는 것은 신규 후보 생성 단계다.

기존 순위 검수 문서는 이 코드를 원천 순위와 승률의 모순을 차단하는 경계로 정의한다. 그러나 이번 로그에는 충돌한 조·팀·원천 행이 나오지 않았다. 따라서 이번 실패의 구체적인 원인을 특정 조의 오류, 파서 오류, 원천 데이터 오류 중 하나로 단정하지 않는다.

실패 실행은 감사 증거로 보존했다. 반복 재수집, 검증 조건 완화, 강제 순위 계산, 게시/활성화는 하지 않았다. 새 팀 식별 경로의 운영 추가·삭제 감소 여부는 아직 검증하지 못했다.

## 6. 이어서 할 작업과 승인 경계

1. 실패 실행의 순위 검수 입력과 실제 원천을 대조하여 충돌한 조·팀·수치를 특정한다. 필요하면 개인정보 없는 구조화된 진단을 보강한다.
2. 원천 변화, 파싱 문제, 규칙 검사의 오탐을 구분한다. 원천 순위를 임의로 수정하거나 검사를 우회하지 않는다.
3. 제품 수정이 필요하면 원인과 수정안을 제시하고 승인 후 회귀 검증한다. 이번 실행에서 검수 코드는 변경하지 않았다.
4. 문제 해결 후 신규 후보를 생성하여 이전 후보의 추가 466 / 삭제 438과 비교한다. 동일 기준 공식본과 수집 범위를 사용하고 서로 다른 시점의 원천 변화도 구분한다.
5. 세부 경기 기록 합계 경고와 삭제·충돌을 검토하고 서버 검증한다. 서버 검증 통과만으로 경고를 일괄 승인하지 않는다.
6. 게시·공식 리비전 활성화는 별도 사용자 승인을 받은 뒤 실행한다. 그 전까지 공개 A조 순위가 교정됐다고 보고하지 않는다.

## 7. 복구 참고 및 증거

문제 시 Portainer에서 이전 이미지 `synapse9983/aubl-backend:cancel-20260913-c9fb2b564e4d@sha256:26033a12d17a83b839454b0864166868d1bf3728aff3506471139ba8ed7b89a5`로 동일 설정을 유지해 교체할 수 있다. 이번에 DB migration을 실행하지 않았으므로 이미지 복귀와 DB 복원은 별개로 판단한다. 운영 DB를 자동 복원하거나 새 수집 흔적을 삭제하지 않는다.

로컬 사전 검증은 기존 보고서의 백엔드 100건, 비교 단위 12건, UI 8건, 타입 검사 통과를 사용했다. 이번 배포 작업에서 그 테스트를 다시 실행한 것으로 기록하지 않는다.

배포 로그와 공개 검사 증거는 `docs/release/evidence/uniqueplay-identity-production-2026-09-13/`에 보존한다. 운영 DB 비밀번호, 워커 토큰, 인증 세션, 환경 파일은 문서와 증거에 포함하지 않는다.
