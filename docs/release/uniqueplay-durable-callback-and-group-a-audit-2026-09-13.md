# UniquePlay 콜백 복구 구현과 A조 동률 진단

작성일: 2026-09-13 (KST)

## 최신 후속 검증

최초 저장·중복 접수와 접수 중 복구 경계를 승인 후 수정했다. 워커 116건, 실제 MariaDB·HTTP 검증을 포함한 백엔드 69건이 모두 통과했고 실패·오류·제외는 0건이다. 상세 결과와 보존한 증거는 `uniqueplay-durable-storage-verification-2026-09-13.md`에 기록했다. 운영 배포·복구·재수집·공식 전환은 아직 수행하지 않았다.

아래 내용은 최초 구현 시점의 이력이며, 남아 있던 워커 실패 1건과 실제 DB 검증 상태에 대해서는 위 후속 결과를 우선한다.

## 1. 최초 구현 시점의 판정

`IMPLEMENTED_PARTIALLY_VERIFIED_NOT_DEPLOYED`

실패 통지 누락에 대응하는 워커 영속 큐, v2 콜백 영수증, 조건부 관리자 복구 API를 로컬 소스에 구현했다. 기존 운영 실행 `2c0f5b0a-863a-46ea-a091-f1041306f516`은 이번 작업에서 복구하거나 재실행하지 않았다. 운영 컨테이너, 공식 DB 상태, 게시 리비전 및 공식 활성화도 변경하지 않았다.

워커 테스트는 **113건 중 112건 통과, 1건 실패**다. 최초 디스크 저장 중 같은 실행 요청이 들어오면 중복 요청이 저장 완료 전에 승인되는 경계가 재현됐다. 이 수정은 사용자에게 별도로 승인 요청했으며, 본 문서 작성 시점에는 아직 적용하지 않았다. 백엔드는 격리된 JDK 21 환경에서 **52건 통과, 실패·제외 0건**이다.

이 결과는 운영 재수집 또는 서비스 전면 운영 승인 조건 충족을 뜻하지 않는다. 특히 실제 DB 트랜잭션과 영수증의 원자성, v2 전체 HTTP 경로, 구형 콜백 차단 전환 및 운영 영속 볼륨 검증은 남아 있다.

## 3. 인터페이스와 저장 계약

### 3.1 워커와 서버 사이의 전달

```text
POST /api/internal/sync/unique-play/v2/runs/{runId}/deliveries/{progress|candidate|failed}
Authorization: Bearer <existing worker service credential>
X-Sync-Delivery-Id: <UUID>
X-Sync-Sequence: <positive integer>
X-Sync-Payload-SHA256: <SHA-256 of exact UTF-8 request body>
```

ACK는 `runId`, `deliveryId`, `sequence`, `payloadHash`, `outcome: APPLIED`를 모두 일치시켜야 한다. 응답 유실 후에는 동일 요청을 재전송한다. 동일 ID에 다른 본문을 연결하거나, 동일 순번을 다른 전달로 재사용하거나, 중간 순번을 건너뛰면 거부한다.

백엔드 신규 테이블은 `UNIQUEPLAY_SYNC_DELIVERY`, 마이그레이션은 `V8__uniqueplay_callback_receipts.sql`이다. 전달 ID 기본키와 실행별 순번 유일 제약을 사용한다. 복구 감사 영수증은 순번 0을 사용하고 일반 콜백은 1부터 시작한다. 기존 후보와 리비전을 자동 이관하거나 덮어쓰지 않는다.

`UniquePlayDeliveryService`의 트랜잭션 안에서 기존 비즈니스 처리를 호출하고 영수증을 함께 저장하도록 구현했다. 실제 MariaDB에서 후보 저장과 영수증 저장 사이의 장애를 주입해 함께 롤백되는지 확인하는 검증은 아직 남았다. 단위 테스트의 모의 저장소를 그 증거로 계산하지 않는다.

### 3.2 관리자 복구

```text
POST /api/admin/sync/unique-play/runs/{runId}/recover
{
  "recoveryId": "<same UUID when retrying>",
  "expectedStatus": "RUNNING",
  "expectedUpdatedAt": "<exact backend timestamp>",
  "note": "<operator evidence and reason>"
}
```

최근 5분 이내 갱신, 기대값 변경, 후보 존재 또는 이미 종료된 실행은 복구하지 않는다. 서비스 인증을 사용해 워커의 `/runs/{runId}/fence`에 접근하고 동일 복구 ID가 포함된 확정 응답을 받아야 DB를 변경한다. 워커는 수집·전송 중이거나 보관 중인 후보가 있으면 fence를 거부한다.

워커 fence 응답이 유실되면 DB는 변경하지 않는다. 같은 복구 ID로 재요청해 이전 fence 결과를 확인한다. fence 후에는 해당 실행 ID의 재수집과 자동 콜백 재개를 막고 기존 증거는 남긴다. 이 API는 개발된 상태이며 운영 관리 화면 버튼 연결과 실제 인증을 포함한 종합 검증은 후속 작업이다.

### 3.3 구형 콜백의 호환성과 전환

구형 경로를 무조건 410으로 차단하는 첫 변경안은 기존 워커를 중단시킬 위험 때문에 도구 안전 검토에서 거부됐다. 해당 변경은 적용되지 않았다.

대신 `uniqueplay.require-durable-callbacks` 전환 스위치를 추가했고 기본값은 `false`다. 운영 환경변수로는 `UNIQUEPLAY_REQUIRE_DURABLE_CALLBACKS`를 사용한다. `true`일 때에만 구형 `/api/internal/sync/unique-play/runs/**` 경로를 410으로 거부하고, v2 경로만 사용한다. 구형 소스는 보존한다.

**스위치가 꺼져 있으면 구형 콜백이 v2 영수증·fence 보호를 우회할 수 있으므로 복구·운영 승인 조건을 충족하지 않는다.** 새 백엔드·워커의 순차 전환과 구형 경로 차단은 운영 영향에 대한 별도 승인 후 실행해야 한다. 이번 작업에서는 스위치를 켜지 않았다.

### 4.3 추적한 처리 경로

1. 워커 `standingFromRow`는 고정 열의 순위와 팀명을 읽고 수치 열에서 승·패·무를 읽는다.
2. `normalization.mjs`는 읽은 순위를 숫자로 변환하며 승자승 순위를 계산하지 않는다.
3. 백엔드 `PublicSeasonOverviewService`는 게시된 `TeamSeason.standingRank`를 공식 순위로 사용한다. 공식 순위가 있으면 DTO에도 해당 값을 내보낸다.
4. 프런트 `homeData.ts`는 모든 공식 순위가 양수이면 그 값을 우선하고, 동일 순위인 행에 동률 표시를 한다. 진출 상태 역시 서버의 명시적 값을 우선한다.
5. `QualificationFinalizeService`는 `TIE_PENDING` 팀에 대한 관리자 진출권 결정을 요구하지만, 승자승·상대 전적을 자동 계산하거나 잘못된 `standingRank`를 고치는 경로는 아니다.

따라서 이번 오류는 **프런트에서만 새로 만들어진 동률이 아니다.** 현재 게시 데이터의 순위값과 진출 상태에 이미 문제가 있다. 다만 9월 11일 수집 당시 원천이 모두 1을 제공했는지, 수집 시 잘못 추출했는지, 게시 과정에서 잘못 반영됐는지는 당시 후보 원본과 `TeamSeason`을 함께 대조해야 확정할 수 있다. 아직 이 원인 구간을 확정하지 않았으며 화면에서 순위를 임의 재계산해 덮어쓰지도 않았다.

### 4.4 회칙 기준과 후속 조치

작업 공간의 `rules-admin-paste-2026-1.json`에는 예선 동률 판정이 승률, 승자승, 팀 간 득실차 등을 순서대로 적용하는 것으로 정리되어 있다. 반면 일부 소개 기본 문구에는 TQB가 포함돼 있어 기준 설명도 일치하지 않는다. 현재 [26-1 AUBL 회칙 공지](https://aubl.club/community/notices/i5s0fpyZwKtFR5dh0Z1k)는 회칙 파일 업로드 예정으로 표시되어, 이 공지만으로 적용 원문 전체를 새롭게 확보한 것으로 계산하지 않는다.

이번에 추가한 `auditStandings`는 정확한 승/(승+패) 비율로 명백한 순위 모순을 탐지할 뿐, 최종 동률 해소나 몰수·징계 판정을 대신하지 않는다. 원천의 서로 다른 승률이 같은 순위로 들어오면 수집을 `STANDINGS_RANK_CONFLICT`로 중단하고 후보를 만들지 않는다. 현재 A조 원천의 정상적인 상위 두 팀 공동 1위는 통과한다.

후속 순서는 기존 공식 후보 원본 대조, 새 수집 후보와의 비교, 적용 회칙·맞대결 근거 확인, 관리자 검수, 별도 게시 승인이다. 기존 리비전 직접 수정, 조 전체 강제 순위 변경, 자동 공식 활성화는 하지 않는다.

백엔드 제품 코드와 테스트 코드는 컴파일을 통과했다. 최초 로컬 실행은 Gradle 실행 비트와 JDK 21 부재로 테스트까지 도달하지 못했다. 기존 `gradle:jdk21` 이미지를 사용했고, 읽기 전용 프로젝트를 Gradle이 거부하여 필요한 소스를 별도 쓰기 가능 검증 사본으로 복사해 실행했다. 원본 마운트는 읽기 전용, 컨테이너 네트워크는 `none`, `.env`는 검증 사본에 복사하지 않았다. 운영 DB 접속이나 운영 데이터 생성은 하지 않았다.

## 6. 다음 작업과 운영 전환 조건

1. 승인 후 최초 디스크 저장 중 중복 요청도 동일 저장 완료를 기다리게 수정하고, 저장 성공·실패 양쪽 동시 요청 테스트를 통과시킨다.
2. v2 실제 HTTP와 MariaDB에서 후보·영수증 원자 커밋, 응답 유실, 동시 재전송, 복구 경쟁 및 늦은 통지를 검증한다.
3. 구형 콜백 전환 스위치의 기본 호환 상태와 승인된 차단 상태를 모두 검증한다. 스위치 활성화 전에 새 워커 전환 명세에 대한 승인을 받는다.
4. NAS에 전용 영속 경로를 마련해 `SYNC_STATE_DIR`로 마운트한다. 컨테이너 내부 파일시스템만 사용하는 배포는 허용하지 않는다. 한 디렉터리는 한 워커 프로세스만 사용하며 다중 인스턴스 운영은 이번 구현 범위가 아니다.
5. 백엔드 V8과 워커 v2를 통제된 순서로 배포하고, CORS와 기존 공식 조회를 유지한다. 현재 이미지·컨테이너·TrueNAS 저장 원본의 구성 차이는 별도로 관리한다.
6. 현재 정체 실행을 최신 DB 값으로 다시 확인하고, 후보가 없으며 실제 워커가 비활성임을 확인한 후 관리자 복구 API로 종결한다. 실행 ID와 감사 이력을 보존한다.
7. 같은 증분 기준으로 한 번 재수집하여 최초 실패 원인, A조 순위, 기준일 이전 기록 보존과 최신 후보를 확인한다. 게시와 공식 활성화는 별도 승인 전까지 하지 않는다.
