# 실시간 야구 기록·문자중계의 운영 전환 설계와 의사결정 기록

작성일: 2026-09-08  
상태: 구현 방향 승인, 단계별 구현 진행 중, 운영 테스트 진입 불가

## 1. 이 문서의 목적과 상태 표기

이 서비스에서 기록 모달은 단순한 입력 화면이 아니다. 경기장에서 발생한 플레이를 접수하고, 문자중계를 생성하며, 경기 상태와 선수 기록을 갱신하고, 서버에 보존하여 관전자에게 전달하는 하나의 기록 경로다. 따라서 모달 입력 성공과 서버 저장 성공을 혼동하거나, 문자중계와 점수판을 서로 다른 시점의 데이터로 공개해서는 안 된다.

이 문서는 통제된 운영 테스트까지의 승인된 계획, 초기 분석에서 발견한 문제, 비교한 대안, 선택 이유, 주요 인터페이스와 저장 정책을 함께 보존한다. 특히 선택의 이유를 남겨 이후 구현에서 편의상 길이 기반 저장, 임의 대기 후 전환, 구형 writer 복귀 등의 방식으로 되돌아가지 않도록 한다.

문서의 상태는 다음과 같이 구분한다.

- **확정 정책:** 사용자가 승인한 방향. 구현 시 유지해야 하는 요구사항이다.
- **설계 계약:** 확정 정책을 실제 동작으로 구체화한 설명이다. 아래 타입·API 이름은 구현 목표를 설명하는 예시이며 현재 제공되는 API라고 주장하지 않는다.
- **후속 확정:** 세부 수치·운영 설정·내부 표현처럼 구현 및 검증 과정에서 결정할 항목이다. 미정 상태로 운영 테스트를 시작하지 않는다.
- **구현 현황:** 실제 코드에 반영되었거나 검증된 범위만 별도로 표시한다.

현재 0·1단계의 일부만 구현되었다. 아래 전체 인터페이스, 다중 입력 큐, 분할 저장, 봉인 절차가 이미 연결된 것으로 해석하면 안 된다. 현재 실행 결과와 제한은 [0·1단계 구현·검증 보고서](records-controlled-production-stage01-2026-09-08.md)를 따른다.

## 2. 서비스 목적과 데이터 원천 정책

### 2.1 자체 기록과 공식 기록의 역할

**확정 정책:** 자체 모달 기록과 문자중계는 경기 중 실시간 참고 서비스를 위한 자료다. UniquePlay 동기화가 완료되면 검증된 UniquePlay 기록을 최종 공식 원천으로 사용한다.

동기화 이후 자체 기록은 버리지 않는다. 관리자만 원본을 열람하고 공식 기록과 비교하여 모달 입력, 규칙 처리, 집계, 문자중계 생성의 문제를 찾는 개선 자료로 사용한다. 자체 기록이 많거나 더 최근에 저장되었다는 이유로 공식 원천보다 우선하지 않는다.

| 시점 | 일반 관전자 | 권한 있는 기록원 | 관리자 |
|---|---|---|---|
| 공식 전환 전 | 공개가 허용된 경기의 서버 확정 참고본 | 세션 권한에 따라 입력 및 로컬 대기 상태 확인 | 참고본 및 감사 자료 확인 |
| 최종 봉인 후, 공식 전환 전 | 마지막 서버 확정 참고본 | 신규 입력 중지, 전환 상태 확인 | 봉인 및 공식 자료 검토 |
| 공식 전환 후 | 검증된 공식본 | 비관리자에게 자체 원본 접근 허용 안 함 | 자체 원본·공식본 비교 및 이슈 관리 |
| 운영 테스트 경기 | 지정 관전자만 허용 | 해당 실행에 등록된 전용 기록원만 허용 | 해당 실행 범위의 권한만 허용 |

공식 전환 후 비관리자 원본 차단은 화면 숨김만으로 구현하지 않는다. 읽기 API, Firestore 규칙, 구독, 캐시·오프라인 저장의 처리 정책까지 연결한다. 이미 전환 전에 전달된 정보를 사용자의 기억이나 외부 복사본에서 회수할 수 있다는 보장은 하지 않는다.

### 2.2 이번 승인 범위

- 별도 스테이징 없이 로컬·에뮬레이터 검증 후 운영 인프라의 격리된 테스트 영역으로 진행한다.
- KBO 2026 1군을 기준으로 정규시즌·포스트시즌 프로파일을 고정한다. AUBL·구장 로컬룰은 이번 범위에서 제외한다.
- 필수 미구현 규칙을 먼저 구현한다. 미구현 기능을 단순 `manualResolve`로 우회한 것을 완료로 계산하지 않는다.
- 지연·오프라인 중에도 입력을 계속할 수 있어야 한다. 다만 기기 내 영속 보관에 성공한 입력만 접수한다.
- 운영 테스트는 최대 3경기, 24시간 이하, 지정 계정만 접근하는 별도 namespace에서 진행한다.
- 운영 테스트 통과와 실제 AUBL 경기 서비스 전면 운영 승인은 분리한다.

## 3. 초기 분석: 무엇이 문제였는가

### 3.1 분석 방법과 증거의 한계

기존 코드 경로, 기존 단위·모달·권한 검증 결과, 저장·전환의 동작 조건을 함께 검토했다. 아래에는 코드에서 확인한 구조적 문제와 아직 실제 장애 시나리오로 재현하지 않은 위험을 구분한다. 테스트 개수가 많다는 사실만으로 실제 Provider 저장 경로와 인증·NAS 경로가 안전하다고 판정하지 않는다.

| 분석 대상 | 확인한 구조 또는 위험 | 서비스에 미치는 영향 |
|---|---|---|
| `src/shared/state/demoStore.effects.ts` | 경기 core와 중계·사건의 저장이 분리됨 | 일부 저장만 성공하면 점수판과 문자중계가 다른 시점을 나타낼 수 있음 |
| 같은 파일의 길이 기반 저장 판단 | 배열 길이가 변하지 않는 정정은 새 입력처럼 감지되지 않을 수 있음 | 안타를 실책으로 정정하거나 기존 사건을 수정해도 서버 반영 누락 가능 |
| 같은 파일의 ACK 이후 길이 갱신 | 완료된 요청의 스냅샷이 아니라 최신 상태 길이를 저장 완료 기준으로 사용하는 정적 위험 | 요청 대기 중 추가 입력을 전송 완료로 잘못 표시할 가능성. 실제 경합 재현은 후속 검증 대상 |
| `src/shared/lib/atomicScoring.ts` | 단일 pending 요청과 전체 payload 중심의 별도 원자적 계약이 존재 | 실제 다중 입력·장기 오프라인·긴 경기 요구를 그대로 충족하지 못함 |
| `src/shared/lib/atomicScoringFirestore.ts` | 독립적인 원자적 transport 경로 존재 | 해당 경로의 테스트 통과가 기존 Provider writer의 대체 완료를 뜻하지 않음 |
| `functions/record_sources.py` | 종료 상태와 일정 대기 시간을 사용하는 공식 전환 조건 | 마지막 요청 ACK·revision·해시 보존을 직접 증명하지 못함 |
| 초기 Firebase 실행 환경 | Firestore 에뮬레이터 설정만으로 Auth·Functions·API까지 분리되지는 않았음 | 로컬 검증으로 생각한 호출이 운영 자원에 닿을 위험 |
| NAS 직접 임포트 경로 | 프런트엔드 정책 외에 서버 직접 호출 경로 검토 필요 | 자체·테스트 기록의 공식 통계 혼입 방어를 UI만으로 보장할 수 없음 |

현재 환경 초기화와 닫힌 테스트 namespace 경계는 일부 개선했지만, 기존 Provider의 저장 문제와 공식 전환 봉인 문제까지 해결된 것은 아니다.

### 3.2 문자열 중심 기록의 한계

하나의 플레이에는 타격 결과, 여러 주자의 이동, 복수 실책, 아웃의 순서, 심판 판정, 기록원 판단이 함께 발생할 수 있다. 최종 notes나 문자중계 한 문장에서 모든 상태를 역산하면 원래 순서와 판단 근거가 사라진다.

따라서 구조화된 사건을 중심에 두고 문자중계와 집계를 파생시킨다. 외부 문자중계를 해석할 때는 원문·파서 버전·추론 결과·불확실성을 보존하고, 자동 추론이 확정 입력을 조용히 덮어쓰지 못하게 한다. 규칙상 판단이 필요한 경우와 아직 구현하지 못한 경우는 다른 상태로 취급한다.

### 3.3 핵심 위험의 공통 원인

기존 문제의 공통점은 **입력 한 건, 서버 요청 한 건, 화면 배열의 현재 상태, 공개 가능한 경기 버전 사이의 경계가 분명하지 않다**는 것이다. 새 설계는 이 네 가지를 서로 다른 식별자와 상태로 관리한다.

## 4. 품질 목표와 보장 범위

| 목표 | 설계상 의미 |
|---|---|
| 입력 보존 | 접수 표시 전에 입력과 로컬 재생에 필요한 정보를 영속 트랜잭션으로 보관 |
| 순서 보존 | 경기·작성 세션의 입력 순번과 플레이 내부 순서를 명시하고 역순 적용 방지 |
| 논리적 중복 방지 | 응답 유실 시 같은 요청을 재전송하되 서버 효과는 요청별 한 번만 반영 |
| 원자적 공개 | 상태·사건·문자중계가 같은 커밋의 데이터일 때만 관전자 화면 갱신 |
| 감사 가능성 | 원본, 정정 대상, 원인, 작성자, 규칙·변환 버전과 전후 커밋 추적 |
| 충돌 안전성 | 다른 작성자·revision 충돌 시 자동 덮어쓰기하지 않고 로컬 입력 보존 |
| 공식 원천 분리 | 자체 기록의 확정 저장과 UniquePlay의 공식 확정을 별개로 취급 |
| 운영 격리 | 테스트 역할·데이터가 일반 운영 권한·통계·검색에 확장되지 않음 |

네트워크 전송 자체를 exactly-once라고 약속하지 않는다. **최소 한 번 재전송될 수 있는 전달과 서버의 멱등 처리로 논리적 한 번 적용을 달성**한다. 접수 후 브라우저 저장소가 사용자에 의해 삭제되거나 기기가 파손되는 것까지 로컬 저장만으로 복구할 수는 없다. 서버 미전송 상태와 그 위험을 기록원에게 명확히 보여줘야 한다.

## 5. 대안 비교와 결정 근거

### ADR-01. 입력 완료를 언제 인정할 것인가

| 대안 | 장점 | 주요 문제 | 결정 |
|---|---|---|---|
| 서버 ACK까지 모달 입력 잠금 | 가장 단순한 서버 중심 흐름 | 지연·오프라인 동안 기록 중단, 빠른 연속 플레이 대응 불가 | 채택하지 않음 |
| 메모리 상태를 먼저 바꾸고 나중에 저장 | 반응이 빠르고 구현이 쉬움 | 새로고침·탭 종료 시 접수된 입력 유실 | 채택하지 않음 |
| localStorage의 단일 pending 요청 | 소규모 재시도 구현이 단순 | 여러 요청의 원자적 접수·갱신과 연속 입력 관리에 부적합 | 기존 호환 분석용, 새 큐의 목표 구조로 채택하지 않음 |
| IndexedDB 영속 다중 입력 큐 | 서버 대기 중에도 다음 입력 접수, 복구·순서 관리 가능 | 트랜잭션·용량·복구·충돌 UI 구현 필요 | **채택** |

선택 이유는 현장 입력의 연속성을 유지하면서, 화면에 성공으로 표시한 입력을 최소한 기기에 보존하기 위해서다. 로컬 영속 실패 시에는 접수 성공을 표시하지 않는다. 입력 초안은 가능한 한 유지하고 저장 공간·브라우저 상태를 안내한다.

### ADR-02. 무엇을 저장 완료로 판단할 것인가

| 대안 | 문제 또는 비용 | 결정 |
|---|---|---|
| 중계·사건 배열 길이 비교 | 같은 길이 정정, undo/redo, ACK 중 추가 입력을 정확히 구분할 수 없음 | 폐기 대상 |
| 마지막 수정 시각 비교 | 클라이언트 시계 및 경합에 의존, 실제 반영 내용의 증명이 아님 | 보조 표시만 허용 |
| 요청 ID만 확인 | 다른 payload·입력 범위를 잘못 완료 처리할 위험을 충분히 설명하지 못함 | 단독 사용 안 함 |
| 요청 ID + 입력 순번 범위 + payload 해시 + 확정 revision | 요청 스냅샷과 ACK를 직접 대조 가능 | **채택** |

ACK가 화면의 최신 상태를 승인하는 것이 아니라 **해당 요청에 고정된 입력만 승인**한다는 점이 핵심이다.

### ADR-03. 문자중계와 점수판을 어떻게 공개할 것인가

| 대안 | 장점 | 위험 | 결정 |
|---|---|---|---|
| 상태·중계·사건 독립 구독 | 기존 구조에 쉽게 연결 | 서로 다른 revision 혼합, 부분 저장 노출 | 채택하지 않음 |
| 관전자에게 기록원의 로컬 예측 상태 전달 | 체감 지연 최소화 | 서버가 거부한 점수·아웃이 공개되고 복구 복잡 | 채택하지 않음 |
| 서버 확정 manifest와 동일 revision의 projection 조회 | 일관된 경기 화면, 실패 시 이전 확정본 유지 | 전체 확정에 필요한 짧은 지연 및 조회 조립 비용 | **채택** |

실시간성은 잘못된 최신 화면을 즉시 보여주는 것이 아니다. 입력은 빠르게 접수하고 전송은 지연을 줄이되, 공개는 검증된 버전 단위로 한다. 구체적인 지연 목표·배치 크기는 후속 측정으로 확정하며 현재 근거 없는 수치를 약속하지 않는다.

### ADR-04. 긴 경기 데이터를 어떤 단위로 저장할 것인가

| 대안 | 장점 | 위험 또는 한계 | 결정 |
|---|---|---|---|
| 전체 경기 JSON 단일 문서 | 읽기·초기 구현 단순 | 경기·감사 이력 증가에 따른 용량·반복 전송 부담 | 채택하지 않음 |
| 용량을 넘으면 사건·중계 일부 삭제 | 당장의 저장 오류 감소 | 기록 원본 및 재생 가능성 상실 | 금지 |
| 상태·중계·사건을 임의로 나누어 순차 공개 | 파일 크기 감소 | 부분 업로드 시 일관성 상실 | 채택하지 않음 |
| 불변 블록 + manifest + 원자적 head·receipt 갱신 | 긴 경기 확장, 재사용·해시 검증, 완성본만 공개 | 블록 조립·완료 검증·고아 데이터 정리 필요 | **채택** |

기존 700KB 상한을 무작정 늘리거나 데이터 삭제로 회피하지 않는다. 블록별·커밋별·실행별 상한, 중첩 깊이, 개수, 업로드 유효시간은 서버 제한과 비용을 고려해 별도로 고정한다.

### ADR-05. 동시 작성과 충돌은 어떻게 해결할 것인가

| 대안 | 위험 또는 비용 | 결정 |
|---|---|---|
| 같은 UID면 모두 작성 허용 | 동일 계정의 두 탭·기기가 서로 상태를 덮어씀 | 채택하지 않음 |
| 마지막 저장 우선 | 기록 순서·정정 의도·투수 책임을 조용히 훼손 | 금지 |
| 자동 사건 병합 또는 CRDT | 일반 문서와 달리 아웃·주루·타순에 비가환 의존성이 있어 의미 충돌 해소가 어려움 | 초기 운영 범위에서 채택하지 않음 |
| 단일 작성 세션 + epoch + 명시적 인계 | 인계 UI와 충돌 보존 필요, 의미를 보존하는 통제 가능 | **채택** |

두 번째 탭은 기본적으로 읽기 상태이며 자동으로 기록권을 빼앗지 않는다. 세션 ID를 단순 복제해 동일 브라우저 탭들이 동시에 쓰게 만들지 않도록 탭 단위 소유권과 복구 절차도 구현해야 한다.

### ADR-06. 정정과 undo/redo를 어떻게 보존할 것인가

| 대안 | 위험 또는 비용 | 결정 |
|---|---|---|
| 원본 사건 직접 덮어쓰기·삭제 | 왜 결과가 바뀌었는지와 후속 영향 재현 불가 | 확정 원본에 사용 금지 |
| 최종 notes만 수정 | 중계와 집계가 분리되고 복잡한 재심 반영 불가 | 채택하지 않음 |
| 원본 보존 + 정정 사건 + 후속 재생 | 연쇄 검증·충돌 검토 필요 | **채택** |

이미 접수된 입력은 전송 전이라도 순번을 몰래 재사용하지 않는다. 확정된 입력의 undo는 과거 커밋 삭제가 아니라 취소·대체의 새 사건으로 남긴다. 아직 접수하지 않은 모달 초안의 취소는 기록 사건과 구분한다.

### ADR-07. 공식 기록으로 언제 전환할 것인가

| 대안 | 문제 | 결정 |
|---|---|---|
| 경기 종료 표시 직후 전환 | 대기 큐 및 마지막 전송이 남아 있을 수 있음 | 금지 |
| 15초 기다린 뒤 전환 | 네트워크 상태·요청 완료를 증명하지 못함 | 승인 근거에서 제거 |
| 큐 비움·최종 ACK·서버 봉인 후 전환 | 서버 상태 전이 및 실패 복구 구현 필요 | **채택** |

공식 자료 검증 실패나 API 장애 때 자체 기록을 공식 기록으로 격상하지 않는다. 이미 공식본이 있으면 이전 공식 revision을 유지한다. 최초 전환 전이면 마지막 참고본과 동기화 상태를 유지한다.

### ADR-08. 운영 테스트를 어디서 어떻게 실행할 것인가

| 대안 | 장점 | 위험 또는 비용 | 결정 |
|---|---|---|---|
| 별도 스테이징 | 운영 데이터와 강한 환경 분리 | 별도 인프라 및 설정 일치 유지 필요 | 이번 계획에서는 선택하지 않음 |
| 일반 경기 컬렉션에 테스트 배지만 추가 | 구현이 간단 | 검색·통계·직접 API에서 혼입 위험 | 금지 |
| 운영 내 별도 namespace + 서버 실행 허용 목록 | 실제 인프라 경로 검증과 데이터 범위 분리 | 인프라 부하·권한 오류 위험은 여전히 존재 | **채택** |

namespace 분리는 별도 인프라 격리와 같지 않다. 따라서 실행 시간·경기 수·호출 한도·중단 수단·책임자까지 승인 명세로 제한한다.

## 6. 주요 인터페이스 설계

### 6.1 공통 기록 범위

설계 계약의 개념 타입:

```ts
type RecordingScope = {
  matchId: string;
  testRunId?: string;
};

type WriterIdentity = {
  writerSessionId: string;
  lockEpoch: number;
};
```

모든 저장·조회·캐시·구독·큐·공식 비교 요청에 같은 범위를 전달한다. `testRunId` 누락이나 변경으로 일반 경기 경로에 자동 fallback하지 않는다. 테스트 경기와 일반 경기의 ID 체계 및 서버 등록 정보를 교차 검증한다.

서버는 인증 토큰에서 UID를 얻고 등록된 실행·참여자·권한·만료·중단 상태를 확인한 후 내부 경로를 결정한다. 클라이언트가 보낸 UID, 역할, 임의 collection path는 권한 근거가 아니다. 관리자 SDK처럼 Rules를 우회하는 서버 경로에도 동일 정책을 적용한다.

캐시 키와 큐 키는 최소한 환경·프로젝트·인증 주체·경기 범위를 구분해야 한다. 같은 경기 ID가 다른 테스트 실행에 존재해도 섞이지 않아야 한다. 로그아웃 후 다른 사용자에게 이전 큐를 자동 전송하거나 보여주지 않는다.

### 6.2 사건 계약과 원본 신뢰도

```ts
type ScoringEventEnvelope = {
  schemaVersion: number;
  eventId: string;
  scope: RecordingScope;
  ruleProfileId: string;
  ruleProfileVersion: string;
  playId: string;
  playSequence: number;
  orderInPlay: number;
  source: string;
  evidence: unknown;
  outcome?: unknown;
  runners?: unknown[];
  penalty?: unknown;
  substitution?: unknown;
  officialAdjust?: unknown;
  correction?: {
    targetEventId: string;
    expectedTargetVersion: number;
    reason: string;
  };
};
```

위 `unknown`은 문서에서 세부 사건별 union 정의를 생략했다는 뜻이지, 검증 없는 payload를 허용한다는 뜻이 아니다. 실제 구현에서는 사건별 타입과 서버 스키마 검증이 필요하다.

- 선수 이름·등번호가 아니라 불변 선수 ID와 출전 구간 ID로 과거 기록을 귀속한다.
- 타석 중 교체, 승계 주자, 투수 책임은 현재 화면 라인업에서 역산하지 않고 당시 책임 정보를 보존한다.
- `orderInPlay`는 동일 플레이의 실책·진루·아웃·판정 순서를 보존한다. 단순 최종 베이스 배치로 원래 순서를 대체하지 않는다.
- 심판 판정과 기록원 판단을 구분한다. 하나의 타구에 야수선택과 복수 실책이 함께 기록될 수 있어야 한다.
- 파서 결과에는 원문 참조, 파서 버전, confidence, ambiguity와 승인 상태를 남긴다. 낮은 신뢰도는 명시적 검토 대상이다.
- 같은 플레이의 후보 사건을 비교할 때는 출처 우선순위와 확정·무효·미확정 상태를 함께 평가한다. 상위 원천이 무효·미확정이라고 하위 후보를 임의로 부활시켜 집계하지 않는다.
- 동일 원본·규칙 프로파일·엔진 버전으로 재생한 결과는 같아야 한다. 규칙·엔진 변경을 과거 경기의 묵시적 재해석으로 적용하지 않는다.

기존 액션 API는 어댑터를 통해 `applyScoringEvent(event)` 중심으로 연결한다. 구형 기록은 읽기 변환을 허용하되 자동 덮어쓰기는 금지한다. 필수 정보가 없는 구형 기록의 불확실성은 보존한다.

### 6.3 로컬 접수 계약

```ts
type LocalAcceptedInput = {
  scope: RecordingScope;
  writerSessionId: string;
  localSequence: number;
  inputId: string;
  event: ScoringEventEnvelope;
  baseCommitId: string;
  acceptedAt: string;
};
```

`localSequence`는 세션의 접수 순서이며 서버 경기 revision과 다르다. 새 세션에서 순번이 겹칠 수 있으므로 세션 ID와 함께 식별한다. `acceptedAt`은 표시·감사 보조 정보일 뿐 경기 순서나 권한 만료의 기준이 아니다.

모달 초안 검증 → 다음 로컬 상태 계산 → 입력과 재생에 필요한 상태를 IndexedDB 트랜잭션으로 저장 → 트랜잭션 성공 후 접수 표시 순서로 진행한다. 로컬 projection은 재생으로 복구 가능한 체크포인트여야 하며 독립적인 원천이 아니다.

### 6.4 전송 요청과 ACK

```ts
type CommitRequest = {
  scope: RecordingScope;
  writer: WriterIdentity;
  requestId: string;
  expectedRevision: number;
  firstInputSequence: number;
  lastInputSequence: number;
  payloadHash: string;
  manifestId: string;
};

type CommitAck = {
  scope: RecordingScope;
  writer: WriterIdentity;
  requestId: string;
  firstInputSequence: number;
  lastInputSequence: number;
  payloadHash: string;
  committedRevision: number;
  commitId: string;
  replayed: boolean;
};
```

서버는 요청의 연속 순번, 요청 범위, 작성 세션·epoch, expected revision, 블록 완전성 및 payload 내용을 검증한다. 해시 일치만으로 야구 규칙의 의미적 정합성이나 작성 권한을 인정하지 않는다.

동일 요청 ID·동일 내용의 재시도는 기존 영수증을 반환한다. 동일 요청 ID에 다른 내용이 오면 거부한다. ACK를 현재 큐 상태에 대입하기 전에 범위·세션·순번·해시가 고정 요청과 일치하는지 확인한다.

서버의 전체 최신 head와 해당 요청이 확정된 revision은 다른 값일 수 있다. 이미 완료된 요청의 영수증을 재조회했을 때 다른 커밋이 이후에 생겼다면, 과거 ACK로 최신 서버 상태를 덮어쓰지 않는다. 최신 head를 별도 조회하고 다음 입력의 기반 revision을 검토한다.

### 6.5 커밋 manifest와 관전자 조회

```ts
type CommitManifest = {
  schemaVersion: number;
  scope: RecordingScope;
  parentCommitId: string | null;
  revision: number;
  ruleProfileVersion: string;
  engineVersion: string;
  projectionVersion: string;
  blocks: Array<{
    id: string;
    kind: 'events' | 'state' | 'feed' | 'stats';
    hash: string;
    byteLength: number;
  }>;
  payloadHash: string;
};
```

실제 필수 projection 종류와 블록의 증분 구조는 구현 시 확정한다. 어떤 형태든 공개 head가 참조하는 manifest의 필수 데이터가 완성되지 않았다면 공개하지 않는다는 정책은 고정한다.

관전자 조회는 head에서 커밋을 선택하고 그 커밋의 필수 블록을 조립·검증한 뒤 화면 전체를 교체한다. 새 head를 받은 즉시 기존 중계에 새 점수판만 섞지 않는다. 조회 중 더 새 revision이 생겨도 이미 선택한 커밋을 완성하거나 전체 조회를 새로 시작한다.

### 6.6 최종 봉인과 공식 전환 계약

봉인 요청에는 경기 범위, 작성 세션·epoch, 최종 revision, commit ID, payload hash를 포함한다. 서버는 현재 head와의 정확한 일치 및 종료 조건을 검증하고 더 이상의 일반 기록 쓰기를 거부하는 상태로 원자적으로 바꾼다.

전환 요청은 이 봉인과 검증된 UniquePlay 원천 ID·revision·해시를 연결한다. 상세 필드명과 callable 또는 HTTP API 형태는 후속 구현에서 확정하되, 클라이언트의 `queueEmpty: true`만 믿고 승인하지 않는다.

## 7. 실시간 기록의 정상 흐름

```text
모달 초안
  -> 사건별 입력 검증 및 플레이 순서 검토
  -> 규칙 엔진의 로컬 상태 전이 / 미리보기
  -> IndexedDB에 입력 + 복구 정보 원자적 저장
  -> 기록원 화면: 접수됨, 서버 전송 대기
  -> 순서가 고정된 요청 생성 및 영속 보관
  -> 불변 블록 업로드
  -> 서버 검증 + head/receipt 원자적 커밋
  -> 요청별 ACK 확인 및 로컬 완료 상태 영속 반영
  -> 관전자: 해당 커밋의 동일 revision 화면 공개
```

입력 접수와 전송은 분리한다. 단, 같은 경기의 커밋 순서는 직렬화한다. A 요청 ACK를 기다리는 동안 B 입력은 로컬에 접수할 수 있지만 B가 A보다 먼저 확정되어서는 안 된다. 서로 독립적인 블록 업로드의 병렬화는 별도 최적화 문제이며 경기 커밋 순서를 바꾸는 근거가 아니다.

예시:

1. 입력 101~103을 요청 A로 고정하고 전송한다.
2. A 응답 대기 중 입력 104~105를 별도로 영속 접수한다.
3. A의 ACK가 101~103과 해당 해시를 확인한다.
4. 101~103만 완료 처리한다. 104~105는 전송 대기로 남는다.
5. A의 확정 revision을 기반으로 다음 요청 B를 만든다.

전송 중인 A의 payload나 해시를 최신 화면에 맞춰 변경하지 않는다. 전송 시도 전에 요청 ID·내용을 영속 보관하여 새로고침 후에도 같은 A를 재시도할 수 있게 한다.

## 8. 영속 큐, 장애 및 충돌 처리

### 8.1 상태 모델

| 상태 | 의미 | 사용자에게 보여줄 동작 |
|---|---|---|
| 초안 | 아직 접수되지 않음 | 모달 수정·취소 가능 |
| 로컬 접수 | 기기 보관 완료, 서버 미확정 | 대기 건수와 마지막 서버 확정 시점 표시 |
| 전송 중 | 불변 요청을 전송 중 | 다음 플레이 입력 가능 |
| 재시도 대기 | 일시 장애·응답 유실 | 같은 요청 유지, 중복 입력 유도 금지 |
| 서버 확정 | 올바른 ACK를 로컬에도 반영 | 해당 요청 범위만 저장 완료 표시 |
| 충돌 | expected revision·작성 세션 불일치 | 자동 덮어쓰기 중단, 원본·대기 입력 보존 |
| 권한 차단 | 로그아웃·권한 회수·만료·공식 전환 | 전송 중단, 다른 계정으로 자동 전송 금지 |
| 접수 실패 | IndexedDB 저장 실패 | 성공 표시 금지, 초안 보존 및 원인 안내 |

권한 차단 이후의 추가 입력 허용 여부는 일반적인 오프라인과 구분한다. 권한이 명시적으로 회수되거나 경기가 봉인된 것을 알게 되면 새로운 유효 기록 접수를 계속하지 않는다. 기존 대기 입력은 삭제하지 않는다.

### 8.2 장애별 복구

| 장애 | 보존·복구 정책 |
|---|---|
| 서버 커밋 전 네트워크 끊김 | 같은 요청 재시도. 실제 커밋 유무는 요청 영수증으로 확인 |
| 서버 커밋 후 ACK 유실 | 동일 ID·동일 내용으로 재전송, 기존 영수증 사용. 새 사건으로 다시 입력하지 않음 |
| ACK 수신 후 로컬 완료 저장 실패 | 로컬 요청 유지. 다음 복구에서 멱등 재조회하여 완료 상태 재반영 |
| 새로고침·브라우저 재시작 | 영속 큐와 기반 커밋을 읽어 재생. 메모리 배열 길이로 완료 상태 추정 금지 |
| 권한·토큰 만료 | 재인증 필요 상태 표시. 인증이 복구되어도 실행 범위와 작성권을 다시 확인 |
| 기록원 인계 | 이전 epoch의 신규 커밋 차단. 남은 로컬 입력은 검토·인계 대상으로 보존 |
| 다른 경기 이동 | 이전 경기 큐를 새 경기로 전송하지 않음. 경기별 대기 상태 안내 |
| 로컬 용량 부족 | 신규 입력 접수 실패를 명시. 미전송 원본을 공간 확보 목적으로 자동 삭제하지 않음 |
| 오래된 기반 revision | 원본과 최신 서버본 비교 후 명시적 해결. 야구 상태를 무시한 자동 rebase 금지 |

서버가 앞선 입력을 거부하면 그 입력을 전제로 작성된 후속 입력도 자동 전송하지 않는다. 거부 입력을 지워 순번만 이어 붙이는 대신, 이후 사건을 재검토하고 필요한 정정·재생 절차를 수행한다.

재시도는 일시 장애와 영구 오류를 구분한다. 백오프·상한·대기 표시 기준은 후속 확정 사항이다. 요청 영수증 보존 기간은 허용 오프라인 기간과 재시도 기간을 포괄해야 하며, 영수증을 지운 뒤 오래된 요청을 새 커밋으로 오인하지 않도록 해야 한다.

## 9. 긴 경기의 불변 블록 저장

### 9.1 쓰기 절차

1. 서버가 인증·경기 범위·세션·실행 상태를 검증하고 업로드 범위를 허용한다.
2. 클라이언트 또는 서버가 고정된 데이터 블록을 준비하고 각 블록의 크기·해시를 계산한다.
3. 블록을 비공개 준비 영역에 업로드한다. 업로드 완료만으로 관전자에게 공개하지 않는다.
4. 서버가 누락, 다른 경기·실행의 참조, 해시 불일치, 용량·개수 초과, 구조·규칙 오류를 검사한다.
5. 완성된 manifest를 준비하고 expected revision과 writer epoch를 재확인한다.
6. head와 요청 영수증을 원자적으로 갱신한다. 성공한 head가 가리키는 커밋만 확정본이다.

외부 저장소의 블록 업로드 자체를 Firestore 트랜잭션에 포함할 수 있다고 가정하지 않는다. 원자성의 대상은 **검증이 끝난 불변 데이터에 대한 공개 포인터와 영수증의 전환**이다. 참조된 블록이 이후 변경·삭제되지 못하도록 저장 계층 정책이 함께 필요하다.

### 9.2 읽기 및 정리 절차

해시·범위·버전 검증이 실패하거나 필수 블록을 읽지 못하면 마지막 정상 커밋을 유지하고 장애를 표시한다. 부분 데이터로 화면을 재조립하지 않는다.

실패한 업로드의 고아 블록은 별도 정리 대상으로 기록한다. 정리 시 현재 head뿐 아니라 과거 보존 커밋·봉인·감사 참조·진행 중 업로드를 확인해야 한다. 만료 시간만 보고 참조 중인 원본을 삭제해서는 안 된다. 보존 기간과 삭제 정책은 운영 실행 전에 확정한다.

## 10. 종료, 봉인, UniquePlay 전환

```text
실시간 기록 중
  -> 종료 요청 / 신규 접수 정지
  -> 로컬 큐 비움
  -> 최종 요청 ACK 확인
  -> 서버 head의 revision·commit ID·해시 확인
  -> 서버 봉인
  -> UniquePlay 공식 원천 검증
  -> 공식 revision 공개 및 비관리자 원본 접근 차단
```

봉인과 새 쓰기가 경합하면 한쪽만 성공해야 한다. 봉인이 먼저 성공하면 늦은 쓰기를 거부한다. 쓰기가 먼저 성공하여 head가 달라졌다면 이전 head를 대상으로 한 봉인을 거부하고 새 최종 ACK부터 다시 확인한다.

서버는 다른 기기에 아직 남아 있는 미전송 입력의 존재를 자동으로 알 수 없다. 따라서 명시적 작성권 인계와 인계 전 큐 상태 확인이 필요하다. 이전 epoch의 입력은 이후 조용히 합쳐지는 것이 아니라 별도 검토 대상이며, 최종 종료 책임자는 미해결 인계 입력이 없는지 확인해야 한다.

봉인된 자체 기록은 감사 원본으로 보존한다. 공식 전환 뒤 자체 원본을 수정해야 할 때는 일반 기록을 재개하는 방식이 아니라 관리자 이슈·정정 워크플로우로 분리한다. 봉인 해제나 경기 재개가 필요한 예외의 승인 계약은 별도로 확정한다.

공식 갱신은 새 UniquePlay revision의 원천 검증이 끝난 뒤 한 번에 공개한다. 실패하면 이전 공식본을 유지한다. 테스트에서는 이미 게시된 UniquePlay 자료를 읽기 전용 참조하며 실제 원천 기록·시즌 누적을 수정하지 않는다.

## 11. 운영 테스트 안전 경계

### 11.1 실행 명세

운영 테스트를 여는 서버 실행 등록에는 프로젝트·API 대상, 실행 ID, 경기 ID, 계정 UID와 역할, 허용 작업, 호출 한도, 승인 시각, 만료 시각, 배포 버전, 중단 책임자, 정리 대상이 필요하다. 하나라도 비어 있으면 시작하지 않는다.

클라이언트 계약의 현재 숫자 검증은 서버에서 집행되는 실제 한도가 아니다. 등록된 실행의 총 호출·저장·업로드 예산을 어떤 방식으로 원자적으로 제한할지는 서버 구현 및 검증 과제다.

세 경기는 정상 전체 경기, 장애·복구·인계, 공식 전환·관리자 비교에 배정한다. 일반 시즌 전체 재수집, 실제 경기 정정, 운영 원천 데이터 변경은 허용하지 않는다.

### 11.2 중단과 정리

범위 밖 쓰기, 비참여자 노출, 누락·중복, revision 불일치가 한 번이라도 발생하면 신규 쓰기를 차단하고 관련 요청·영수증·커밋 증거를 보존한다. 구형 저장 경로 또는 자체 기록 공개로 자동 복귀하지 않는다.

테스트가 생성한 데이터·권한만 정리한다. 삭제 실패 시 비공개·쓰기 차단·테스트 식별 상태를 유지하고 남은 ID와 이유를 보고한다. 정리 완료 판정에는 재조회 확인이 필요하며 실제 실행 승인 범위 안에서 수행한다.

## 12. 구현 순서와 기존 시스템 호환성

| 단계 | 작업 | 완료 조건 |
|---|---|---|
| 0 | 결과 취합 복구, 기존 증거 보존, 2026 규칙 원문·개정·정정 등록 | 조항별 출처·버전·기대값 고정, 실패·제외·정적 위험 구분 |
| 1 | 환경 선택, 서버 테스트 범위·계정 인가, 만료·중단·예산 | 로컬의 운영 접근과 테스트의 일반 경기 접근 모두 거부 |
| 2 | 선수·출전·책임·순서·정정·프로파일 계약 | 이름·교체 이후 귀속 보존, 동일 원본 재생 동일 결과 |
| 3 | 필수 미완료 규칙 및 모달·중계·집계 연결 | 적용 대상 필수 미구현 0건 |
| 4 | 실제 Provider writer 교체, 영속 큐·ACK·분할 저장·관전자 조회 | 경합·정정·재시도·긴 경기에서 유실·중복·부분 공개 없음 |
| 5 | 인증·세션 인계·봉인·공식 전환·NAS 방어 | 마지막 커밋 보존, 비관리자 원본 및 공식 혼입 차단 |
| 6 | 실제 앱·에뮬레이터·실제 자료·모바일 종합 검증 | 필수 실패·제외 및 중대 결함 0건 |
| 7 | 기본 비활성 배포, 실행 명세·중단·정리 준비 | 사용자 승인된 실행만 제한적으로 개방 가능 |

신규 경기는 새 writer만 사용하고 이중 쓰기를 하지 않는다. 기존 운영 경기 자동 이관, 구형 writer 자동 복귀는 금지한다. 대체 검증을 마친 미사용 함수는 사용자 요청에 따라 삭제하지 않고 주석으로 보존하되, 실행 경로에서는 분리한다. 검증되지 않은 함수를 미사용으로 단정하지 않는다.

## 13. 검증 설계와 독립 기대값

### 13.1 규칙·모달 검증

각 조항을 정상·경계·모순 입력과 연결하고 독립 기대값을 작성한다. 제품 reducer의 출력을 그대로 기대값으로 만들어 자체 정합성만 검사하지 않는다.

검증 경로는 모달 입력 → 미리보기 → reducer → 문자중계 → 타자·투수·수비 집계 → 서버 저장 → 재조회다. 교체·어필·정정·재개는 여러 플레이에 걸친 시나리오로 검증한다. 실제 경기 20개와 실제 문자중계 500문장은 출처·사용 범위·기대값을 함께 확보하며 합성 사례로 대체하여 완료 수를 채우지 않는다.

### 13.2 저장·전송 필수 시나리오

| 검증 시나리오 | 반드시 확인할 결과 |
|---|---|
| 첫 ACK 보류 중 두 번째·세 번째 플레이 | 앞선 요청 범위만 완료, 뒤 입력은 영속 대기 |
| 같은 길이 정정 및 undo/redo | 새 의미 변경이 별도 입력·커밋으로 보존 |
| 커밋 전 장애·커밋 후 응답 유실 | 요청 재전송 후 효과 한 번, 원본 유실 없음 |
| 새로고침·종료·복구 | 큐의 순서·내용·request ID 유지 |
| 로컬 저장 실패 | 성공 표시 없음, 미전송 데이터 삭제 없음 |
| 같은 UID의 두 탭·기기와 명시적 인계 | 한 세션만 작성, 이전 epoch 거부 |
| 토큰 만료·로그아웃·권한 회수 | 전송 차단 및 큐 보존, 다른 계정에 노출 없음 |
| 부분 블록·잘못된 해시·용량 초과 | 새 head 공개 없음, 이전 확정본 유지 |
| 긴 연장 경기·대량 연쇄 정정 | 동일 revision 재구성 및 집계 일치 |
| 관전자 조회 중 새 커밋 | 중계·점수·사건의 혼합 revision 없음 |
| 마지막 쓰기와 봉인 경합 | 최종 커밋 누락 없음, 봉인 후 늦은 쓰기 거부 |
| 공식 API 장애·새 공식 revision | 미완성 전환 없음, 이전 공식본 유지 |
| NAS 직접 임포트·공개 조회 | 자체·테스트 기록이 공식 누적에 들어가지 않음 |
| 관리자·기록원·지정 관전자·비참여자·익명 | 서버를 포함한 접근 행렬 일치 |

기존에 제외된 실제 전체 RPC 장애 2건은 계속 필수 잔여 검증이다. 다른 테스트에서 제외가 0건이라는 이유로 해소된 것으로 계산하지 않는다.

### 13.3 운영 진입 기준

필수 테스트 실패·제외 0건, 알려진 필수 규칙 미구현 0건, 저장 유실·중복·원본 노출·공식 통계 혼입 결함 0건이 모두 필요하다. 그 후에만 `READY_FOR_CONTROLLED_PROD_TEST`로 전환한다. 테스트 수 자체, 일정 경과, 모달이 열리는 사실은 승인 근거가 아니다.

## 14. 현재 구현과 후속 확정 사항

### 14.1 2026-09-08 현재 구현·검증된 범위

- 결과 취합 정규식 복구와 과거 결과 별도 보관.
- 로컬 실행 설정 사전 검증, Firebase 로컬 연결 초기화, 로컬 API 프록시·CSP 경계.
- 테스트 실행 범위의 클라이언트 사전 검증 계약.
- 테스트 namespace 전체 클라이언트 접근 거부. `production-test` 실행 모드는 여전히 차단.
- 오류 클래스의 `erasableSyntaxOnly` 호환 수정.
- 타입 검사 및 경계 88건, 기록 회귀 922건, Firestore 에뮬레이터 95건 통과. 이 결과는 이번 범위만 증명한다.

실제 Auth·Functions 에뮬레이터 통합, 서버 실행 등록·인가·호출 한도, NAS 내부 호출 격리, 새 Provider writer, 다중 입력 큐, 분할 저장, 봉인은 아직 완료되지 않았다. 실제 앱 브라우저 E2E를 이번 변경 후 다시 실행한 결과로 보고하지 않는다.

### 14.2 구현 전에 또는 구현 중 확정해야 할 세부사항

- KBO 2026 전체 규칙집·개정·정정 원문의 버전·해시·조항별 기대값. 변경 안내만으로 전체 규칙을 확정하지 않는다.
- 서버 API 방식과 canonical serialization·해시 형식·스키마 버전 이행 규칙.
- 블록별·커밋별 크기, 개수, 업로드 유효시간, 고아 블록 정리와 감사 보존 기간.
- 입력 배치 크기·최대 대기 시간, 재시도 백오프, 허용 오프라인 기간과 영수증 보존 기간.
- 탭 단위 세션 소유권, 세션 재개·인계·기기 분실 시 남은 큐 처리 절차.
- 공식 전환 후 클라이언트 캐시 정리와 관리자의 원본 조회 보존 정책.
- 봉인 이후 정당한 경기 재개·관리자 정정에 대한 별도 승인 계약.
- 실제 모바일 복구 성능, 전송 지연 측정 기준과 운영 알림 임계값.
- 운영 실행의 정확한 프로젝트·API·UID·경기·배포 버전·중단 책임자.
