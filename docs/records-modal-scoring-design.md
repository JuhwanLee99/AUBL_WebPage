# 모달 기반 야구 기록: 분석, 설계 및 단계별 구현

작성일: 2026-09-08

## 1. 결론과 문서 범위

현재 시스템은 기본 기록 기능과 새 안타·주루 매트릭스를 갖추었지만, 모든 야구 상황을 일관되게 처리하는 엔진은 아니다. 이 문서는 현재 코드 검토 결과, 권장 모달 흐름, 복합 플레이 모델, 구현 단계와 승인 기준을 함께 관리한다.

기록 버튼이 있다는 것, 중계에 문장을 남길 수 있다는 것, 점수판이 변한다는 것, 공식 개인 기록이 정확하다는 것은 서로 다른 수준의 지원이다. 기능별로 입력·상태 전이·중계·집계·정정까지 연결되어야 지원 완료로 간주한다.

- 심판 판정과 기록원의 기록 판정은 분리한다. 애매한 상황은 메모만으로 확정하지 않고 확인 대기로 남긴다.

## 4. 권장 모달 흐름

1. 시작 상태 고정: 경기 ID, 상태 버전, 타석 ID, 타자·투수 ID, 카운트, 아웃, 주자와 책임 투수를 캡처한다.
2. 실제 발생 내용: 투구 여부, 볼/스트라이크, 타구 종류·방향, 라이브 볼/데드 볼을 입력한다.
3. 수비 행위 순서: 포구, 송구, 태그, 포스, 실책, 방해 등의 행위를 반복 추가한다. 자동 기본 순서는 확정 사실과 구분한다.
4. 타자·주자 이동: 같은 주자에게도 여러 이동 구간을 추가한다. 각 구간에 원인 행위와 실제 발생 순서를 연결한다.
5. 판정: 타자 기록, 루타수, 야수별 실책, 타점, SH/SF, 아웃 종류와 득점 인정을 확정한다.
6. 통합 미리보기: 이전/이후 점수·아웃·주자, 중계 문장, 타자·투수·수비 기록 변화, 미확정 항목을 함께 표시한다.
7. 단일 확정: 동일 플레이 ID로 모든 변화를 한 번에 반영한다. 상태 버전이 달라지면 다시 검토하도록 한다.

단순 플레이는 기본값으로 짧게 기록하고 복합 플레이에만 단계 추가 UI를 펼친다. 진행 중 모달을 바꿔도 입력 초안은 유지한다. 취소는 경기 상태를 바꾸지 않으며, 실행 취소는 플레이 전체를 취소한다.

## 5. 복합 플레이 모델: 다음 단계 설계안

아래 모델은 설계안이며 현재 타입으로 구현된 것이 아니다.

```ts
type RecordedPlay = {
  playId: string;
  plateAppearanceId: string | null;
  expectedStateVersion: number;
  pitch: { thrown: boolean; result: string } | null;
  actions: FieldingAction[];
  movements: RunnerMovementSegment[];
  batterResult: BatterScoringDecision | null;
  errors: FieldingErrorDecision[];
  runs: RunDecision[];
  judgments: UmpireJudgment[];
  review: ReviewMetadata;
};
```

- 수비 행위마다 `actionId`, 순서, 야수 ID, 대상 주자, 대상 루, 송구 경로를 갖는다.
- 실책마다 `errorId`, 원인 행위, 책임 야수, 종류, 추가 진루와 아웃 기회 상실을 연결한다. 한 악송구로 여러 주자가 움직여도 실책 ID는 하나다.
- 주자 이동마다 시작/도착 루와 원인 행위를 연결한다. 단타로 1루, 실책으로 2루, 추가 진루 중 아웃을 한 주자에게 연속 표현한다.
- FC는 무제한 체크하는 타자 기록이 아니다. 선택 수비 행위는 여러 개일 수 있지만 타자 기록과 각 진루 원인은 일관되게 결정한다.
- 안타와 실책의 병존은 허용하지만 같은 진루를 양쪽에 중복 배정하지 않는다.
- 타석 종료는 최대 한 번, 실제 투구 수는 투구 여부에 따라 한 번만 변한다.
- 타격방해 등 선택권이 있으면 선택한 결과와 기각한 대안도 보존한다.

## 6. 대표 수용 시나리오

| 시나리오 | 모달에서 확인할 내용 | 검증해야 할 결과 |
|---|---|---|
| 단타 + 외야수 실책 | 안타 인정 구간과 추가 진루 | H=1, E=1, PA/AB 각 1 |
| FC + 후속 송구 실책 | 선행 주자 아웃, 타자 진루 구간 | FC·아웃·E·진루가 한 사건 |
| 서로 다른 야수의 연속 실책 | 실책별 행위와 영향을 받은 주자 | 실책 개수와 책임 야수 일치 |
| 단타 후 타자주자 2루 태그 아웃 | 안타 인정, 후속 아웃 순서 | 안타 보존, 아웃 추가, 득점 시점 판정 |
| 도루 + 송구 실책 | 도루 목표 루, 추가 진루 | 도루와 실책 진루 구분 |
| K + WP/PB + 추가 송구 실책 | 삼진·출루 원인·추가 진루 | 실제 투구 1, 타석 1, 각 기록 분리 |
| 희생번트 + 실책 출루 | 번트 의도, 정상 수비 가정 | SH와 E의 병존 판정 |
| 제3아웃과 홈 도달 | 순서, 포스/태그/어필, 선행 관계 | 득점 인정·무효와 타점 동시 결정 |
| 투수 교체 전 출루 후 득점 | 책임 투수와 FC 승계 여부 | 팀 실점과 투수별 실점 합 일치 |
| 정정·되돌리기·재적용 | 원본, 수정본, 버전 | 중계·점수·집계가 동일 버전 |

## 7. 이번 구현: 1차 오기록 방지

### 추가한 처리

- 희생타의 아웃 수와 주자 조건 검사. 기존 희생플라이 입력은 3루 주자 득점 상황으로 범위를 명시한다.
- 무사·1사 1루 점유 시 낫아웃 출루 차단. 낫아웃 실패 문구는 삼진 아웃으로 분류한다.
- 병살·삼중살의 남은 아웃 수, 필요한 주자 수, 선택 중복 검사.
- 기존 FC·실책·병살·주자 진루에서 제3아웃 동반 득점의 순서가 불명확하면 반영하지 않는다. 적법한 플레이도 이 경로에서 보류될 수 있으며, 이를 임의로 무득점 처리한 것은 아니다.
- 일부 두 액션 모달에서도 예상되는 제3아웃 동반 득점을 첫 액션 전에 차단한다. 원자적 모달 전환 완료를 의미하지 않는다.
- H/E 집계는 구조화 사건을 우선 사용하고 같은 사건 ID를 중복 집계하지 않는다. 대응 사건이 없는 중계는 사건 단위 보조 추론만 한다.
- WP/PB/BK를 별도 사건 유형으로 저장하고 타석 유지/볼넷 등 `outcome`을 분리한다. 기존 `error` 필드는 호환성 때문에 상세 입력을 담는 컨테이너로 남아 있다.
- 일반 WP/PB는 실제 볼/스트라이크를 한 번 반영하고 타석을 유지한다. 4구째 WP/PB는 타자 1루와 안전진루 외의 추가 진루가 있는 제한된 경우를 지원한다.
- 기본 보크는 타자 유지, 실제 투구 없음, 모든 주자 한 베이스 진루만 지원한다.
- 수비 실책 중 타자 유지와 타자 아웃은 실책 출루 타석으로 분류하지 않는다.
- 다중 주자 아웃 모달을 전역 단축키 차단 목록에 추가한다.

### 여전히 제한되는 처리

- 제3스트라이크와 WP/PB의 결합, WP/PB/BK와 주자 아웃·추가 방해의 결합은 이번 기존 모달에서 차단한다. 별도 액션을 연달아 넣는 것을 동등한 대안으로 안내하지 않는다.
- 실책 여러 개와 동일 주자의 연속 이동은 다음 모델에서 구현한다. 현재 사건 하나의 실책을 여러 개로 확장한 것은 아니다.
- 모든 기존 출루의 책임 투수 갱신, FC 책임 승계, 전체 투수 아웃·타점 집계, SH/SF 분리는 아직 미완료다.
- 동일 ID의 동등 우선순위 충돌, 사건 ID 없는 과거 기록, 잘못 기록된 과거 WP/PB 타석은 별도 검수가 필요하다. 이번 변경이 과거 경기를 공식적으로 정정하지 않는다.
- 기존 모달 전체의 상태 버전 검사, 입력 초안 보존, 공통 포커스 관리, 원자적 확정은 다음 단계다.
- 자책점은 추정 상태이며 이닝 재구성 알고리즘은 구현하지 않았다.

## 8. 구현 순서와 승인 기준

1. 현재 단계: 위 1차 오기록 방지와 순수 함수·격리 전이 함수 회귀 테스트.
2. 다음 단계: FC·실책·희생타·낫아웃을 공통 복합 플레이 모델로 연결. 단일 모달 확정·취소와 발생 순서 보존.
3. 집계 통합: 타자·투수·수비 기록, 책임 승계, 타점, SH/SF를 하나의 원천에서 계산.
4. 정정 통합: 원본 보존, 정정 버전, 동일 입력의 멱등성, 모든 화면과 CSV 재생성.
5. 저장 검증: 앞 단계의 로컬 시나리오를 통과한 뒤 별도 테스트 경기로 저장·재조회 검증.

승인 기준: 동일 플레이의 중계와 기록 일치, 유효하지 않은 입력의 무변경 반려, 실제 투구·타석 중복 없음, 주자 소실 없음, 인정 득점과 타자 득점 합 일치, 투수 실점과 미확인 책임 합 일치, 취소 후 완전 복구, 재적용 시 중복 없음.

## 9. 테스트와 운영 데이터 보호

- `npm run test:scoring`: 순수 함수 테스트와 실제 레거시 전이 함수의 격리 실행을 포함한다.
- 격리 테스트는 TypeScript AST에서 지정한 함수만 추출한다. React store 모듈을 import하지 않고 Firebase·인증·네트워크·저장 API를 실행하지 않는다. 저장 연동이나 전체 UI 테스트를 대체하지 않는다.
- 타입 검사와 변경 대상 린트를 함께 수행한다. 테스트 개수는 전체 야구 규칙 지원 개수와 다르다.
- 이번 작업에서는 운영 경기나 기록을 생성·변경하지 않는다.
- 향후 저장 테스트는 `[테스트] 기록 엔진 검증`으로 명시된 별도 경기만 사용한다. 생성 ID를 추적하고 그 실행의 기록만 정리한다. 삭제하지 못하면 테스트 표시를 유지하고 남은 ID를 보고한다.

## 10. 2차 재점검 결론과 설계 변경 이력

재점검일: 2026-09-08. 이번 요청은 설계 구체화, 검증 증거 보강, 미사용 래퍼 함수의 주석 보존이다. 복합 플레이 엔진 전체를 이번에 구현한 것은 아니다.

**판정: 종전 설계만으로 빠짐없는 기록을 보장할 수 없다.** 5절의 `RecordedPlay`는 시작점일 뿐, 타구 없는 사건, 사후 어필, 경기 중단, 교체, 판정 선택과 정정의 적용 범위가 충분하지 않았다. 아래 계약이 5절의 간략 설계보다 우선한다. 확장된 설계도 구현·규칙별 독립 검증을 마치기 전에는 전체 상황 대응 완료라고 표현하지 않는다.

| 설계 결정 | 종전의 한계 | 이번에 구체화한 기준 |
|---|---|---|
| D01 사건 범위 | 모든 입력을 타구 플레이로 취급 | 투구·주루·판정·교체·경기 운영·정정을 별도 사건 종류로 지원 |
| D02 타자 결과 | 결과 하나로 출루 상태와 기록을 표현 | 물리적 안전/아웃, 타석 종료, 안타·SH/SF 등 기록 판정을 분리 |
| D03 발생 순서 | 주자당 하나의 결과, 고정 숫자 순서 | 주자별 연속 구간과 행위 간 선후 관계; 동시·불명확 상태도 보존 |
| D04 실책 | 실책 종류와 야수 하나 | 실책 ID별 원인 행위·책임자·영향 구간·정상 수비 가정 |
| D05 판정 | 단일 penalty 문자열 | 적용 대상·효력 발생 시점·선택권·취소 범위를 가진 판정 목록 |
| D06 책임 | 현재 투수 또는 이름 기반 매핑 | 불변 선수/등장 ID, 출루 시 책임, FC 승계와 교체 근거 |
| D07 사후 변경 | 현재 플레이만 수정 | 과거 사건을 참조하는 어필·판독·기록 정정과 영향 범위 재계산 |
| D08 미확정 | 경고 또는 자유 메모 | 저장 가능한 검토 초안과 확정 경기 상태를 분리; 추측으로 반영 금지 |
| D09 완전성 | 버튼·테스트 개수로 표현 | 상황 → 입력 → 판정 → 상태 → 중계 → 기록 → 테스트의 추적 가능성으로 판단 |

근거 재확인은 2025 규칙의 9.03, 9.08~9.16 및 2026 KBO 공개 변경 안내를 사용했다. 아래 시나리오와 데이터 모델은 시스템 설계용으로 작성한 것이며 규칙집 원문을 대체하지 않는다. 공식 기록의 SH/SF, 자살·보살, 투수 책임과 판정 선택권을 하나의 결과 문자열로 합치지 않는 것이 핵심이다.

## 12. 사건 단위와 저장 계약의 구체화

### 12.1 모든 사건에 필요한 공통 필드

| 필드 | 계약 |
|---|---|
| `schemaVersion` | 계약 버전. 구버전 변환 결과와 원본을 함께 추적 |
| `gameEventId`, `matchId` | 사건과 경기의 불변 ID |
| `kind` | `play`, `ruling`, `substitution`, `game_control`, `correction` 중 하나 |
| `playId`, `plateAppearanceId`, `pitchId` | 해당하지 않으면 null. 투구 없는 사건에 가짜 투구/타석을 생성하지 않음 |
| `expectedStateVersion` | 입력 시작 시점. 확정 시 최신 버전과 일치해야 함 |
| `revision`, `supersedesRevision` | 원본 불변, 정정 버전 연결 |
| `ruleProfileId`, `ruleProfileVersion` | 대회·시즌·규칙집·구장 특례의 고정 버전 |
| `source`, `evidence`, `confidence` | 출처, 원문/판정 근거, 추론 신뢰도. 신뢰도가 권한을 대신하지 않음 |
| `reviewStatus` | `draft`, `needs_review`, `confirmed`, `rejected`, `superseded` |
| `reviewerId`, `reviewedAt`, `reason` | 확인자, 확인 시각, 변경 사유. 서버 권한과 함께 검사 |

선수 식별은 이름/등번호 대신 `playerId`를 사용한다. 같은 선수가 역할을 바꾸거나 재출전하는 경우 `appearanceId`로 구분하고, 루상 주자는 `runnerParticipationId`로 출루부터 소멸까지 추적한다.

| `outs[]` | 대상, 발생 노드, 아웃 종류, 포스의 당시 상태, 어필 대상 | 실제 아웃과 제3아웃 판정에 채택된 아웃 구분 |
| `runs[]` | 홈 도달 노드, 인정/무효/미확정, 사유, 타점 귀속 | 도달 사실을 즉시 득점으로 단정하지 않음 |
| `responsibility[]` | 원천 출루, 책임 투수, 승계 관계와 근거 | 주자 교체나 FC 뒤에도 책임 이력 보존 |
| `rulings[]` | 적용 대상, 효력 시점, 진루권, 귀루, 아웃, 선택권 | 채택 대안만 상태에 적용 |

`sequence`는 UI 정렬용 번호와 실제 발생 순서의 증거를 구분한다. 현재 엔진의 1~4 순서 제한과 주자당 단일 이동을 새 계약에 가져오지 않는다. 행위 수를 네 개로 제한하지 않으며, 메모리·전송량 한도는 플레이 의미를 자르는 대신 초안 분할 보관으로 처리한다.

동시 발생이거나 시점이 불명확한 경우 임의 순번을 만들지 않는다. 득점 판정에 영향을 주는 순서가 미확정이면 최종 점수 반영을 막고 확인을 요구한다. 확정된 판정으로 결과가 결정되는 경우에는 근거를 남겨 처리한다.

### 12.3 타자의 상태와 기록은 별개다

다음처럼 실제 상태와 기록 결정을 함께 표현한다. 예시는 개념 계약이며 현재 앱에 구현된 타입이 아니다.

```json
{
  "batterDisposition": {
    "runnerParticipationId": "runner-batter-A",
    "status": "safe",
    "lastTouchedBase": 1,
    "plateAppearanceEnded": true
  },
  "battingDecision": {
    "contactKind": "bunt",
    "reachedBy": "error",
    "hitBases": 0,
    "sacrifice": "bunt",
    "reviewStatus": "confirmed"
  },
  "errors": [
    {
      "errorId": "error-1",
      "actionId": "throw-1",
      "fielderId": "player-P",
      "affectedMovementIds": ["move-batter-first"],
      "reason": "기록원이 정상 수비 가정을 확인한 사례"
    }
  ]
}
```

이 구조에서는 희생번트 판정과 실책 출루가 함께 남을 수 있다. PA/AB/SH/SF/RBI 등 최종 집계값은 확인된 결정에서 계산하며, 서로 모순되는 합계를 별도 수기 숫자로 덮어쓰지 않는다.

### 12.4 판정·교체·운영·정정 사건

| 종류 | 추가 필수 항목 | 영향 범위 |
|---|---|---|
| 판정 | 대상 노드/터치, 판정 종류, 시점, 선택 대안과 채택 대안 | 한 행위, 플레이 전체 또는 참조한 이전 플레이 |
| 교체 | 퇴장/입장 선수의 appearanceId, 타순·역할, 당시 카운트 | 이후 타석·투구·루상 책임; 과거 기록 소유자는 유지 |
| 경기 운영 | 시작/중단/재개/종료 종류, 유효 기록의 끝점 | 규칙 프로필에 따른 경기·기록 인정 범위 |
| 정정 | 원본 사건/버전, 대체 내용, 사유, 확인자 | 영향받은 시점부터 파생 결과 재계산 |

사후 어필은 이전 터치 노드와 판정에 채택할 아웃을 참조한다. 이미 세 아웃이 있었다는 이유로 어필 입력 자체를 버리거나, 네 번째 아웃을 투수 이닝에 더하지 않는다. 상세 판단은 규칙 모듈과 확인된 심판 판정에 맡긴다.

범용 판정 입력은 자유 메모 저장만을 뜻하지 않는다. 심판의 판정, 적용 대상과 시점, 상태 변화와 기록 영향이 구조화되어야 한다. 엔진이 자동 지원하지 못해 기록원이 보정한 경우 `manual_override`와 근거를 남기며, 이를 자동 규칙 대응 완료로 계산하지 않는다.

## 13. 모달 화면과 입력 제어 계약

| 단계 | 화면에서 입력/표시할 내용 | 다음 단계 조건 |
|---|---|---|
| 시작 | 현재 경기·타자·투수·주자, 초안 복원 | 경기 ID와 상태 버전 고정 |
| 사실 | 투구 유무, 타구, 포구·페어/파울, 라이브/데드 | 필요한 관찰 또는 판정 정보 존재 |
| 행위 | 수비 행위 추가·삭제·이동, 대상 연결 | 참조 대상 유효, 순서 관계에 모순 없음 |
| 주루 | 주자별 여러 구간, 귀루/터치/아웃, 원인 선택 | 최종 결과와 중간 경로를 혼동하지 않음 |
| 판정 | 아웃 종류, 실책 목록, 진루권, 선택권 | 결과에 영향 주는 미확정 항목 해결 |
| 기록 | 타자 기록, 실책별 야수, RBI, 책임 투수, 확인 상태 | 중복·누락·상충 판정 없음 |
| 미리보기 | 전후 상태, 중계, 개인/팀 기록 변화, 경고 | 필수 불변식 통과 및 확인 권한 |
| 확정 | 단일 확정 버튼, 중복 클릭 방지 | 최신 버전 일치, 한 번의 원자적 저장 |

간단 모드의 단타·아웃·볼넷 등도 동일한 초안 모델을 생성한다. 복합 모드는 별도 계산 엔진이 아니라 같은 모델의 상세 편집 화면이다.

초안은 `draft → preview → needs_review/ready → committing → committed`로 진행한다. 실패는 `draft` 또는 `needs_review`로 돌아오며 사용자의 입력을 유지한다. 초안 저장은 확정 경기 로그·실시간 중계·공식 집계를 바꾸지 않는다. 과거 확정 사건의 정정은 새 버전을 만들고 원본을 보존한다.

모달 공통 규칙: 배경 경기 단축키 차단, 포커스 가두기와 복귀, Escape는 초안 취소 확인이지 경기 undo가 아님, 작은 화면에서도 주자·원인·순서를 함께 확인 가능, 라벨과 오류 메시지를 스크린리더에 제공. 상태 변경·잠금 상실·경기 교체 시 확정 버튼을 막고 재검토한다.

## 14. 대표 복합 사례를 통한 모델 검증

아래 예상값은 명시된 사실과 기록원 판정을 전제로 한 **승인용 fixture 설계**다. 아직 새 통합 모달에서 실행된 테스트가 아니다.

| ID | 시작과 행위 순서 | 반드시 보존할 결과 |

| F01 | 1사 2루, 단타로 기존 주자 득점, 이후 외야수 실책으로 타자 2루 | 안타 1·실책 1·득점 1, 타자 루타수는 1, 안타로 인정한 득점의 RBI 연결 |
| F02 | 1사 1·3루, FC로 1루 주자 아웃, 후속 실책으로 타자 추가 진루 | FC·두 번째 아웃·실책·진루를 한 사건에 보존; 타점은 별도 확인 결정 |
| F03 | 타자 출루 때 첫 실책, 이후 별개의 행위에서 다른 야수 실책 | 실책 ID 두 개와 각각 영향을 준 구간, PA/AB는 타석 결과로 한 번만 |

| F07 | 2사 1루 비어 있음, 제3스트라이크 WP로 타자 1루, 추가 송구 실책으로 2루 | 삼진·WP·별도 실책·연속 이동; 실제 투구 수는 한 번 |

## 15. 상태·기록 불변식의 구체화

- V01 모든 참조 ID가 존재하고, 서로 다른 경기의 선수 등장·타석·판정을 연결하지 않는다.
- V02 발생 순서 관계가 순환하지 않는다. 화면에서 행을 옮겼다는 이유만으로 실제 발생 순서를 확정하지 않는다.
- V03 주자의 연속 이동은 앞 구간의 도착점에서 시작한다. 귀루와 리터치는 허용 가능한 명시적 행위다.
- V04 최종 유효 루상 배치와 중간 물리적 위치를 구분한다. 순간적으로 같은 베이스에 도달한 상황을 데이터에서 지워버리지 않는다.
- V05 일반 라이브 플레이에서는 시작 주자와 새 타자주자의 최종 운명을 모두 설명한다. 주자를 조용히 덮어쓰거나 소실시키지 않는다. 교체·진루권·판정 취소에는 별도 변환 규칙을 둔다.
- V06 실제 아웃과 제3아웃 판단에 사용하는 아웃을 구분한다. 추가 어필을 이닝 4아웃으로 집계하지 않는다.
- V07 공수 교대는 해당 플레이 판정 완료 후 한 번만 적용한다. 새 공수의 카운트·루상 상태는 규칙 프로필의 초기 상태와 일치한다.
- V08 홈 도달 후보마다 인정·무효·미확정 상태가 있다. 인정된 후보만 점수와 선수 득점에 반영한다.
- V09 타점은 특정 인정 득점 ID를 참조한다. 득점이 취소되면 연결된 타점도 다시 판단한다.
- V10 타석 종료와 PA 증가는 최대 한 번이다. 타자가 계속 타격 중인 실책·WP/PB·주루 사건은 타석을 완료시키지 않는다.
- V11 안타 인정 구간과 추가 진루 구간을 분리한다. 최종 2루에 있다는 이유로 단타를 2루타로 바꾸지 않는다.
- V12 SH와 SF를 분리하고 타수·출루율 등의 계산에 정확히 사용한다. 실책과 희생 기록의 조합은 별도 판단 가능해야 한다.
- V13 실제 투구와 벌칙 카운트를 구분한다. 투구 없는 자동 판정·교체·보크에 가짜 투구 수를 더하지 않는다.
- V14 E는 실책 ID, 자살·보살은 채택된 아웃과 참여 근거에 따라 집계한다. 중계 행 수를 기록 개수로 사용하지 않는다.
- V15 실제 플레이의 팀 득점은 선수 득점 합과 일치한다. 몰수 표시 점수처럼 실제 득점이 아닌 값은 별도 필드로 둔다.
- V16 투수 실점 합과 미확인 책임 실점의 합은 실제 팀 실점과 일치한다. 미확인 책임을 0이나 현 투수에게 임의 귀속하지 않는다.
- V17 자책점은 추정/미확정/확정을 구분한다. 팀 자책점과 개인 투수 자책점의 단순 합을 무조건 같다고 강제하지 않고 적용 규칙을 명시한다.
- V18 동일 입력 ID의 재전송은 한 번만 반영한다. 같은 ID의 내용 충돌은 조용한 덮어쓰기가 아니라 검수 대상이다.
- V19 반려·초안·취소 대안은 확정 집계에 들어가지 않는다. 정정 전후의 원본과 사유는 보존한다.
- V20 중계·스코어보드·타자·투수·수비·CSV는 동일한 확정 로그 버전에서 생성한다.

위 V01~V20 전부가 현재 코드에 적용된 것은 아니다. 현재는 부분적인 형태 검증, 새 안타/주루 전이, 보수적 기존 입력 차단, 일부 사건 단위 집계가 구현된 상태다.

## 16. 설계 과정과 검증 절차

1. 규칙 프로필 확정: KBO/KBSA 기본 규칙과 AUBL 대회 규정, 구장 특례를 구분한다. 판본과 예외를 문서화한다.
2. 사례 등록: 11절 ID에 사실관계·변형·필수 입력·예상 판정을 연결한다. 미지원 사례는 자유 메모 완료로 닫지 않는다.
3. 표현 가능성 검토: 하나의 모델로 사건을 손실 없이 표현할 수 있는지 확인한다. 새 필드가 필요하면 공통 계약과 마이그레이션 계획을 먼저 변경한다.
4. 화면 검토: 기록원이 발생 순서대로 입력할 수 있는지, 뒤늦게 실책을 추가해도 입력을 잃지 않는지, 미확정 사항이 보이는지 검토한다.
5. 독립 예상값 승인: 심판 판정과 기록원 판단을 분리해 expected 상태·중계·집계 차이를 승인한다.
6. 함수 검증: 유효 입력, 반려 입력, 경계값, 중복·순서 변경·정정·재적용을 테스트한다.
7. 통합 검증: 같은 확정 사건으로 상태·중계·개인·팀 기록·CSV를 생성하고 V01~V20을 대조한다.
8. 브라우저 검증: 모달 초안·뒤로가기·취소·동시 변경·키보드·모바일·권한 상실을 실제 UI로 확인한다.
9. 저장 검증: 별도 테스트 경기에서 저장·재조회·재접속·중복 전송·정정 버전을 확인한다.
10. 결과 기록: 통과·실패·미실행을 구분한다. 규칙 전체 대응은 모든 필수 연결이 검증되어야 승인한다.

현재 진행 위치는 3~6단계의 일부다. 7~9단계 전체를 수행했다는 뜻이 아니다. 알려진 기존 오류와 결과가 달라지는 수정은 단순한 구버전 동치보다 독립 승인된 예상값을 우선한다.

## 18. 다음 검증에서 반드시 추가할 항목

- 기본 상태 조합은 8개 루상 배치 × 3개 아웃 수 × 12개 카운트 = 288개다. 사건별 적법성 조건으로 나누어 테스트하고, 모든 사건을 모든 조합에서 허용하지 않는다.
- F01~F10마다 정상 흐름, 순서 반전, 필수 판정 누락, 중복 전송, 수정 후 재생, 취소 후 복구를 별도 fixture로 만든다.
- 같은 주자의 1루→2루→귀루→아웃, 네 개를 넘는 행위, 동시 발생과 순서 불명확을 포함한다.
- 한 행위가 여러 주자에게 영향을 주는 경우와 여러 행위가 같은 주자에게 영향을 주는 경우를 교차 검증한다.
- 동일 ID·동일 내용은 중복 방지, 동일 ID·다른 내용은 충돌 보류, 다른 ID·같은 문장은 실제 반복 사건일 수 있음을 검사한다.
- 이름은 같고 playerId가 다른 선수, 등번호 변경, 같은 선수의 역할 변경, 대주자와 FC 책임 승계를 검사한다.
- 상태의 점수와 중계의 득점 문구, 사건의 인정 득점, 타자 득점·RBI, 투수 실점, 수비 기록을 함께 대조한다.
- 20경기 전체 재구성과 실제 스타일의 중계 500건 검증은 미실행이다. 합성 문구 변형 테스트로 이를 대체했다고 보고하지 않는다.
- 브라우저·Firestore 테스트와 운영 통계 격리 검증도 미실행이다. 테스트 경기 생성 전 공개 노출과 공식 통계 포함 여부를 확인해야 한다.

## 21. 복합 플레이 모달 구현과 검증 절차 (2026-09-08)

### 21.2 승인 후 보완 및 재검증

사용자 승인으로 선택적 반려 목록 타입 오류 두 곳과 낫아웃 실패 판정을 수정했다. 출루와 실패를 분리하고, 타자주자 1루 도달 전 제3아웃의 득점 취소 및 처리 중 진루의 WP/PB 중복 기록 방지를 추가했다. `records-composite-play-implementation.md` 8절에 재검증 전 기대값을 기록했고, 이어 실제 실행 결과를 추가한다. 운영 데이터는 변경하지 않는다.

후속 실행 결과: **269개 테스트 전부 통과**, 전체 TypeScript 검사 통과, 변경 파일 11개 ESLint 통과. 기존 21.1절의 TS18048 두 건 및 낫아웃 실패 구분 보완은 완료했다. 운영 데이터 변경은 없고 실제 저장 왕복·브라우저 E2E·나머지 전체 규칙 지원 제한은 별도다. 세부 사례와 로그는 구현 문서 8.2절을 참조한다.
