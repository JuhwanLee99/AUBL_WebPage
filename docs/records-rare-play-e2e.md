# 희귀 복합 플레이 프런트엔드 E2E 검증

작성: 2026-09-08. 실행 전 기대값과 실행 후 관측 결과를 구분한다.

후속 상태: 이 문서의 30건 통과는 [운영 준비도 보완](./records-production-hardening.md) 이전 기준선이다. 이후 제품 변경의 회귀 재실행 및 추가 기대값 H01~H15 검증은 아직 수행하지 않았다.

## 1. 검증 경계와 운영 안전

실제 `CompositePlayButton`을 브라우저에서 조작한다. 현재 운영 소스의 reducer·gateway·상태 적용·실행 취소/재실행 함수 선언을 실행 시 추출하고 실제 경기 진행 보조 함수와 정규화 함수를 연결한다. 두 페이지의 실제 `buildPlayerStats`, 종료 타자 집계와 `StatsTable`을 사용한다. 기존 순수 함수/VM 테스트와 달리 입력·네이티브 dialog·React 상태 변경·DOM 표시까지 통과해야 한다.

전체 운영 사이트 로그인부터 Firebase 저장까지의 E2E는 아니다. 인증만 고정된 메모리 사용자로 대체하고 앱의 운영 Provider/effects를 import하거나 mount하지 않는다. 재조회는 별도 브라우저 컨텍스트의 `sessionStorage`와 실제 hydrate/normalize 경로다. 실제 기록원/관전자 페이지 라우터 대신 두 집계 결과를 한 테스트 페이지에 표시한다.

- 정상 운영 Vite 설정과 `.env`를 읽지 않는 별도 서버를 `127.0.0.1` 임의 포트에 연다. `/api` 프록시를 구성하지 않는다.
- Firebase·운영 effects·backendClient·AuthProvider import를 거부한다.
- 브라우저 요청은 같은 로컬 origin의 GET만 허용한다. 외부 요청, POST 등 쓰기 메서드와 `/api`를 차단하고 시도 자체도 실패로 기록한다. 서비스 워커는 차단한다.
- 모든 경기 식별자는 `LOCAL_E2E_ONLY_`로 시작하고 기존 사용자 브라우저/인증/저장소를 재사용하지 않는다.
- 실행 결과는 `outputs/scoring-e2e/<실행시각>/`에 저장한다. 테스트 종료 후 브라우저와 로컬 서버를 닫고 이번 실행용 임시 Vite 캐시만 제거한다.

## 3. 성공 시나리오의 종단 검증 절차

1. 격리된 fixture 경기를 열고 실제 버튼으로 모달을 연다.
2. 타격·투구·복수 실책·주자별 연속 이동·수비 경로·어필·책임투수를 UI로 입력한다. 테스트가 완성된 사건을 reducer에 직접 넣지 않는다.
3. 최종 확인이 활성화되고 모달 너비가 viewport 안에 들어오는지 확인한다. 모달 스크린샷을 남긴다.
4. 적용 버튼을 눌러 dialog 종료를 기다린다. 한 사건, 한 해당 중계 행, 한 history 단위인지 확인한다.
5. 점수·아웃·공수·주자·타순·H/E, 실제 gateway의 transition/source, 두 페이지의 개인 기록과 종료 타자 집계를 독립 기대값과 비교한다.
6. 실제 reducer의 실행 취소로 경기 상태를 되돌리고 재실행해 같은 사건이 복원되는지 확인한다.
7. 테스트 전용 로컬 저장 후 페이지를 새로 고친다. 실제 hydrate/normalize 후 사건 원본과 양쪽 통계·종료 집계가 동일한지 확인한다.
8. 브라우저 런타임 오류나 차단된 외부 요청 시도가 없는지 확인하고 결과 스크린샷·trace·JSON 보고서를 남긴다.

테스트 기대값은 `scenarios.mjs`의 상수이며 엔진 계산 결과로 생성하지 않는다. 검증용 DOM의 JSON은 읽기 전용으로 렌더링된 현재 상태/집계다. 테스트 중 개별 함수를 호출해 결과를 만들어 넣지 않는다.

## 4. 재현 명령 및 산출물

```sh
npm run test:scoring:e2e
npm run test:scoring:e2e -- --scenario=R05 --viewport=mobile
```

Playwright는 프로젝트 설치본 또는 Codex 번들 런타임에서 찾는다. 다른 환경에서는 `AUBL_PLAYWRIGHT_MODULE`에 Playwright 모듈 경로를 지정할 수 있다. Chrome 경로는 `AUBL_E2E_BROWSER`로 지정할 수 있으며, 미지정 시 macOS Chrome 또는 Playwright 기본 Chromium을 사용한다. 실행 과정에서 패키지나 브라우저를 자동 다운로드하지 않는다.

결과 폴더에는 `results.json`, `report.md`, 사례별 `*-trace.zip`, 모달/결과 스크린샷이 생성된다. 실패 시 DOM과 실패 스크린샷도 남긴다. 생성 결과는 `outputs/`의 기존 ignore 정책을 따른다.

## 5. 실행 결과

위 시나리오와 기대값을 먼저 작성했다. 실제 실행 결과는 아래에 이어 기록한다. 미실행/실패를 통과로 표시하지 않으며 테스트 환경 결함과 제품 동작 결함을 구별한다.

### 5.1 첫 실행의 환경 실패와 승인된 하네스 수정

- 샌드박스 내 첫 실행은 로컬 포트 bind가 `EPERM`으로 차단되어 브라우저 검증 전 중단됐다.
- 로컬 서버/임시 Chrome 실행 권한을 얻은 뒤 실행했으나, 생성된 가상 모듈의 상대 import를 `/@fs/` 경로로 변환할 때 `.ts` 확장자를 생략한 하네스 오류가 발생했다. 데스크톱 R01~R08은 모달 로딩 대기 시간 초과로 끝났으며 나머지는 중단했다. 제품의 야구 판정 실패로 분류하지 않는다.
- 사용자에게 원인을 설명하고 **테스트 하네스 수정 후 재실행** 승인을 받았다. 실제 파일 확장자를 해석하도록 변경하고, 공통 fixture 로딩 실패 시 남은 실행을 중단하도록 했다.
- 종료 타자 집계는 기록이 있는 선수만 포함하는 sparse map이므로, 미기록 선수의 항목 부재는 0 기대값만 만족하도록 테스트를 명시했다. 비영(非零) 기대값은 항목 부재 시 계속 실패한다.
- 이 단계에서는 제품 코드를 수정하지 않았다. 최초 브라우저 실행 폴더: `outputs/scoring-e2e/2026-09-08T05-24-00-959Z/`. 중단된 실행의 `results.json`과 개별 trace/스크린샷은 유지한다.

### 5.2 대표 사례를 통한 하네스 보정

- 모달이 실제로 표시되는 것을 실패 스크린샷으로 확인했다. 중첩 `<label><select>`의 전체 라벨에는 옵션 문자열도 포함되어 정확 일치 탐색이 실패했다. 제품을 바꾸지 않고 테스트의 라벨 검색 방식을 보정했다.
- R01 대표 사례는 입력·적용·집계·Undo/Redo를 통과했으나 재조회 전체 객체 비교에서 실패했다. 차이는 득점/통계가 아니라 원시 fixture에 없던 `isElite: false`가 실제 hydrate에서 기본값으로 추가된 것이었다.
- 재조회 비교를 느슨하게 하지 않고, fixture의 최초 진입도 실제 hydrate로 정규화하도록 하네스를 변경했다. 전체 집계 객체의 엄격 동등성 비교는 유지한다.
- 관련 중간 보고서: `outputs/scoring-e2e/2026-09-08T05-27-18-827Z/report.md`.

### 5.4 판정과 남은 범위

이번 실행에서 선택한 30개 프런트엔드 E2E의 기록 계약 위반은 관측되지 않았다. 수정한 것은 테스트 하네스뿐이며 제품 코드를 통과 목적에 맞춰 변경하지 않았다. 기대 점수·아웃·기록 수치를 낮추거나 재조회 비교를 제거하지 않았다.

관전자 문자중계에는 실책의 영문 종류와 사건 UUID가 그대로 보이는 점이 표본에서 확인됐다. 기록 정확도와 별도로 관전자용 문구 정리/상세 감사 정보 분리를 후속 UX 항목으로 남긴다.

운영 로그인·실제 Firebase 저장/재조회·네트워크 지연/충돌·전체 페이지 라우팅·WebKit/실기기·과거 경기 전량 재생은 아직 이 결과에 포함되지 않는다. 이전 설계 문서의 타순 위반/교체 책임/사후 재심/경기 운영 등 미완료 범위도 유지한다. 30개 통과는 전체 KBO 상황의 완전한 지원 또는 운영 배포 승인을 뜻하지 않는다.
