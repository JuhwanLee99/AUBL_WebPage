# UniquePlay 수동 동기화 구현·배포 이력

이 문서는 2026 AUBL 시즌의 UniquePlay 데이터 수집, 검수, 게시 기능을 구축하면서 확인된 장애와 수정 이력을 운영 평가·보고서 작성에 재사용할 수 있도록 정리한다. 인증 토큰, 암호화 키, 세션 원문, 데이터베이스 비밀번호 등 비밀 정보는 기록하지 않는다.

## 1. 목표와 운영 원칙

- AUBL 관리자가 명시적으로 `수집 시작` 버튼을 눌렀을 때만 UniquePlay 데이터를 수집한다.
- 스케줄러와 주기적 자동 수집은 사용하지 않는다.
- 수집 결과는 곧바로 공개하지 않고 `수집 → 변경 비교 → 충돌 해결 → 검증 → 리비전 생성 → 활성화` 순서로 처리한다.
- 후보 데이터에 차단 오류가 있거나 체크섬이 달라지면 현재 공개 리비전을 유지한다.
- UniquePlay 개인 계정의 비밀번호를 저장하지 않는다. 수집 워커에는 UniquePlay 도메인 쿠키와 허용된 인증 저장소 항목만 암호화해 전달한다.
- Google 계정 쿠키, 원본 HTML, 전화번호, 이메일과 같은 개인정보는 후보 데이터나 로그에 남기지 않는다.

## 2. 구성

| 구성 요소 | 역할 | 배포 위치 |
| --- | --- | --- |
| React 관리자 화면 | 수동 실행, 진행률, 변경 비교, 매핑, 검증, 게시·활성화 제어 | AUBL 웹 |
| Spring 백엔드 | 실행 원장, 후보·체크섬, 검증, 감사 리비전, MariaDB·Firestore 게시 | NAS 컨테이너 |
| Playwright 수집 워커 | 암호화 세션 복원, A~H조·일정·결과·개인 기록 수집, 허용 목록 정제 | NAS 컨테이너 |
| MariaDB | UniquePlay 시즌 데이터와 동기화 감사 원장 | NAS |
| Firestore | 공개 일정·결과 projection | Firebase |

백엔드 작업본은 웹 저장소와 분리된 `AUBL_WebPage_BE-test` 디렉터리에서 빌드했다. 해당 디렉터리는 작업 당시 Git 저장소가 아니므로 아래 이미지 버전과 이 문서가 배포 추적 기준이다.
v22의 재현 가능한 소스 변경은 `docs/release/aubl-backend-v22-mapping-persistence.patch`에도 함께 보관한다.

## 3. 이미지 버전별 변경점

### 백엔드 `synapse9983/aubl-backend:v20`

- 새 동기화 실행의 `createdAt` 초기화 누락을 수정했다.
- 워커의 내부 콜백 경로가 일반 사용자 인증 필터에서 차단되지 않도록 내부 서비스 인증 경로를 분리했다.
- 수집 요청의 초기 500 오류는 해소했으나, 후보 JSON 콜백에서 Jackson 2·3 타입 혼용으로 다시 500 오류가 발생하는 것이 확인됐다.

### 백엔드 `synapse9983/aubl-backend:v21`

- Spring Boot 4 환경에 맞춰 JSON 처리를 Jackson 3 `tools.jackson` API로 통일했다.
- 명시적인 Jackson 2 databind 의존성을 제거했다.
- `fields`, `fieldNames`, `findValuesAsText` 등 Jackson 2 전용 호출을 Jackson 3 대응 API로 교체했다.
- 후보 저장, 체크섬 검증, diff 생성까지 정상 진행되는 것을 확인했다.
- 전체 Gradle 테스트를 통과한 뒤 NAS에 배포했다.

### 백엔드 `synapse9983/aubl-backend:v22`

- 관리자가 `AUBL 항목에 연결(MAP_ENTITY)` 결정을 저장하면 해당 실행 항목뿐 아니라 `EXTERNAL_ENTITY_MAPPING` 원장에도 같은 트랜잭션에서 즉시 upsert하도록 변경했다.
- 팀·경기의 명시적 연결만 영구 매핑으로 저장한다. `UniquePlay 값 사용`, `AUBL 값 유지`와 같은 실행별 검수 판단은 기존 게시 정책을 유지한다.
- 게시 단계의 매핑 저장도 같은 upsert 함수를 재사용하므로 반복 실행과 재게시가 멱등하게 동작한다.
- Java 21 컨테이너에서 매핑 회귀 테스트와 백엔드 전체 Gradle 테스트를 통과했다.
- NAS 실행 환경에 맞춘 `linux/amd64` 이미지로 다시 빌드해 Docker Hub digest `sha256:d535941ff19775759cdd535f37db2c770d94ea900b6f48edd6f60df0c067db39`로 업로드했다.
- 2026-09-04 18:28 KST에 NAS의 `ix-aubl-backend-aubl-backend-1` 컨테이너를 v22로 교체했다. 컨테이너 실행 상태와 공개 `/api/seasons` HTTP 200 응답을 확인했다.

### 수집 워커 `synapse9983/aubl-uniqueplay-sync-worker:v4`

- UniquePlay 인증이 쿠키가 아니라 로컬 스토리지의 인증 항목을 함께 필요로 한다는 점을 반영했다.
- 세션 캡처 시 UniquePlay 도메인 쿠키와 `@accessToken`, `@userInfo`만 허용하고 Google 및 다른 도메인의 상태를 제거했다.
- React Native Web의 텍스트 노드 대신 실제 클릭 가능한 조상 요소를 선택하도록 탐색을 보강했다.
- 요약 카드와 상세 표의 중복 헤더 중 정확한 열 구성을 가진 표를 선택하도록 수정했다.
- A~H 조 선택, `조별일정확인`·`게임결과` 탭, 경기 카드 루트 탐색을 수정했다.
- 투수 `삼진` 열을 AUBL 표준 키 `탈삼진`으로 변환했다.
- 선수명과 팀명이 한 필드로 합쳐지던 고정 열 파싱을 수정하고 선수·팀 소속 검증을 추가했다.
- 결과적으로 선수·팀 관련 `PLAYER_TEAM` 차단 오류는 제거됐으나 경기 결과 목록의 일부만 수집하고 `콜드승`, `몰수게임`을 종료 경기로 보지 못해 `GAME_COUNT_MISMATCH`가 남았다.

### 수집 워커 `synapse9983/aubl-uniqueplay-sync-worker:v5`

- 스크롤 컨테이너를 화면 높이가 아니라 실제 스크롤 가능 거리(`scrollHeight - clientHeight`)가 가장 큰 요소로 선택하도록 수정했다.
- 목록이 이동 가능한 동안에는 행 수가 잠시 유지돼도 수집 종료로 판단하지 않고, 실제 목록 끝에서 3회 안정화될 때까지 계속 수집하도록 변경했다.
- `콜드승`, `몰수게임`, 기권·부전승 표현을 `COMPLETED`로 정규화했다.
- 워커 단계에서도 순위표 경기 수와 종료 경기 출전 수를 팀별로 대조하고, 불일치 시 조·팀·기대값·실제값을 포함한 차단 오류를 만든다.
- 전체 실데이터 미리보기에서 125경기(종료 117, 예정 8), A~H 40팀, 타자 846명, 투수 247명을 수집했다.
- 순위표 경기 수 불일치 0건, 워커 차단 오류 0건을 확인했다.
- Docker Hub digest `sha256:4ffccb674cc91deab9a4b29c8877193510d5fb3e624877f3b82f4cae09ae6692`로 업로드했다.
- 2026-09-04 18:04 KST에 NAS의 `aubl-uniqueplay-sync-worker` 컨테이너를 v5로 교체하고 실행 상태와 인증 세션 연결을 확인했다.

## 5. 검증 결과

### 정적·단위 검증

- 워커 Node 테스트: 13개 통과
- ESLint: 워커 어댑터, 검증기와 관련 테스트 통과
- 웹 TypeScript typecheck: 통과
- 백엔드 Gradle 전체 테스트: 통과(v21 빌드 기준)
- 백엔드 v22 매핑 회귀 테스트 및 전체 Gradle 테스트: 통과(Java 21 컨테이너)

추가된 핵심 회귀 테스트는 다음과 같다.

- UniquePlay 도메인 인증 정보만 남기고 Google 쿠키를 제거한다.
- 가상 표는 행 수가 3회 안정화될 때까지 읽는다.
- 경기 목록은 스크롤이 가능한 동안 중간의 동일 샘플 때문에 조기 종료하지 않는다.
- 선수명이 비었거나 선수가 해당 조 팀에 속하지 않으면 차단한다.
- 순위표 경기 수와 종료 경기 출전 수가 다르면 차단한다.
- 콜드승·몰수게임은 종료 경기로 정규화한다.

v5 NAS 배포 후 관리자가 시작한 실행 `ef66a5d6-a7cb-4c35-a740-a393ebc8946e`도 총 1,266개 비교 항목(신규 1,226, 변경 없음 24, 팀 매핑 충돌 16)을 생성했다. 이전 v4 후보보다 경기 항목이 111개 늘어 전체 경기 수집 수정이 실제 운영 워커에 반영된 것을 확인했다.

v22 배포 후 이 실행의 16개 팀 충돌에 기존 AUBL 팀 ID 연결 결정을 다시 저장했다. 미해결 항목은 16건에서 0건으로 감소했고 서버 검증을 통과해 `게시 준비 완료` 상태가 됐다. 운영 화면에는 F·G조 진출 경계 동률 경고만 남았다. 이 검증은 후보 데이터와 영구 매핑 저장을 확인하기 위한 것이며, 리비전 생성과 활성화는 실행하지 않았다.

## 7. 배포와 롤백 절차

1. 워커 테스트와 ESLint를 실행한다.
2. `linux/amd64` 워커 이미지를 새 불변 태그로 빌드한다.
3. Docker Hub에 업로드하고 manifest digest를 기록한다.
4. Portainer에서 워커 컨테이너 이미지를 새 태그로 변경하고 재생성한다.
5. `/health`와 관리자 화면의 `세션 다시 확인`에서 연결 상태를 확인한다.
6. 관리자가 버튼을 눌러 새 수동 수집을 시작한다.
7. 후보 수치, 차단 오류, 충돌과 체크섬을 검토한다.
8. 검증이 통과해도 리비전 생성과 활성화는 별도 관리자 확인 후 수행한다.

문제가 발생하면 Portainer에서 직전 이미지 태그로 되돌려 재생성한다. 후보 리비전은 활성화 전까지 공개 데이터에 영향을 주지 않는다. 이미 활성화한 경우에는 이전 게시 리비전을 다시 활성화해 공개 projection을 복구한다.

## 8. 운영상 남은 확인 사항

- 다음에 관리자가 명시적으로 시작하는 새 수동 실행에서 이번에 저장한 16개 팀 매핑이 자동으로 재사용되는지 최종 확인한다.
- 현재 후보는 검증을 통과했지만, 별도 운영 승인 전에는 리비전 생성과 활성화를 실행하지 않는다.
- 운영 검증에 남은 F·G조 진출 경계 동률은 회칙에 따라 관리자 판정을 기록한다. 별도 로컬 미리보기에서 확인된 A조 경계도 게시 전 다시 대조한다.
- 자동 스케줄러는 도입하지 않는다. 향후 필요할 때도 현재 수집 파이프라인 앞에 별도 승인된 스케줄러만 추가한다.
- 임시 로컬 세션 파일과 전용 Chrome 프로필은 배포 검증 완료 후 정확한 경로를 확인해 폐기한다.
